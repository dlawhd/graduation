# 새 배포 확인부터 50명 조회 시험까지

- 작성일: **2026년 10월 19일**
- 작업 날짜·시각 기준: **한국 시간(KST)**
- 정리 시작점: **“새 배포 완료 → 설정 유지 → 메모리 여유 확인. 아마 새 배포는 완료했을 거야. 한 번 확인해 보고 다음 바로 가자.”**
- 정리 끝점: 관리 지표의 대기 시간을 5초로 변경한 뒤, **50 VU·60초 조회와 종료 후 회복 확인을 마친 시점**
- 대상: 서버나 성능 시험을 처음 배우는 사람

반복된 진행 요청과 같은 용어 설명은 합쳤다. 실패 기록은 빼지 않았다. 질문을 보낸 정확한 시각은 확정하지 않고, 실행 기록에서 확인한 날짜와 순서를 사용했다.

이전 과정은 [서버 부하 시험 준비부터 10명 조회 재시험까지](LOAD_TEST_JOURNEY_2026-10-19.md)에 있다. 이 문서는 그 뒤의 후속 기록이다. 예전 문서에 적힌 “50 VU 미실행”은 당시의 상태이며, 아래 새 결과와 구분한다.

## 1. 한눈에 보는 결론

**실제 EC2(AWS에서 빌려 쓰는 서버)에서 전용 계정 50개로 60초 동안 조회 시험을 완료했다. 조회 2,906건의 검증 오류는 0건이었다.**

하지만 **“실제 회원 50명이 모든 기능을 오래 써도 문제없다”는 뜻은 아니다.** 로그인 준비 중 느린 요청과 DB 연결이 잠깐 꽉 차는 현상이 남아 있다.

API(화면이나 다른 프로그램이 서버에 기능을 요청하는 통로)를 통해 조회하고, DB(자료를 저장하는 시스템)에서 필요한 내용을 읽어 오는 흐름을 검사했다.

| 확인한 것 | 마지막 결과 |
| --- | --- |
| 4개 → 10개 계정 순차 준비 | 완료 |
| 10 VU·60초 조회 | 584건, 검증 오류 0건 |
| 50 VU·60초 조회 | 2,906건, 검증 오류 0건 |
| 50 VU의 세 조회 API p95 | 약 57~65ms, 목표 500ms 이내 |
| 마지막 실행의 자원 수집 | 정상 표본 151개, 수집 실패 0개 |
| 각 단계 종료 후 약 1분 회복 확인 | 정해 둔 회복 조건 충족 |
| 아직 남은 문제 | 준비 중 내 정보 조회 최대 4.61초, 순간 DB 연결 10개 모두 사용·대기 2개 |
| 아직 하지 않은 것 | 100·200·300 VU, 장시간 조회 완료, 쓰기·실시간 통신 부하 |

VU(사람처럼 정해진 행동을 반복하는 가상 사용자)는 실제 회원 수와 다르다. p95(약 95%의 요청이 끝나는 시간)는 가장 느린 요청 하나의 시간이 아니라 응답 시간의 분포를 보는 수치다. 1,000ms는 1초다.

## 2. 우리의 목표는 무엇이었나?

식당에 손님을 조금씩 늘려 보내며, 주문이 빨리 나오고 내용도 맞는지 확인하는 것과 같다.

우리 서비스에서는 저금통 목록·상세·쪽지 목록이 주문에 해당한다. 서버가 빨리 답했더라도 다른 사람의 자료나 잘못된 개수를 주면 실패다.

목표는 다음과 같았다.

1. 새 배포에서도 기존 메모리·DB 설정이 유지되는지 확인한다.
2. 실제 두 사용자의 계정·개인 자료 대신 전용 시험 계정을 사용한다.
3. 적은 요청부터 시작해, 안전할 때만 동시에 요청하는 수를 늘린다.
4. 느려지거나 감시가 끊기면 시험 도구를 중단한다.
5. 결과와 실행 조건을 함께 보존해 나중에 비교할 수 있게 한다.

장기적으로는 사용자 500명을 고려하고 있지만, 이번 결과는 특정 조회 시나리오의 50 VU 결과다. 300개 시험 계정을 준비해 둔 것과 300 VU를 실행한 것도 서로 다르다.

## 3. 처음에 확인한 새 배포와 설정

배포 확인은 “Git에 올렸으니 끝”이 아니다. 서버가 실제로 어떤 실행 이미지를 사용하고 있는지도 확인해야 한다.

| 항목 | 이 과정에서 확인한 기준 |
| --- | --- |
| 기록 기준 Git 커밋 | `9f0b37cbbac4ffe4932de8a5dbf38346951fac6d` |
| 실제 실행 이미지 | 아래 이미지 식별값을 기준으로 후속 시험 중 동일 여부 확인 |
| Java 메모리 | G1(긴 정지를 줄이려는 메모리 정리 방식), Heap 상한 224MiB 유지 |
| DB 캐시 | 8MiB / 32MiB / 128MiB 유지 |
| DB 연결 상한 | Hikari(자바 서버에서 DB 연결을 빌려주고 돌려받는 도구) 최대 10개 |
| 관리 지표 접근 | 일반 API 포트에서 접근 차단, 내부 관리 경로로 수집 |
| 실제 서버 크기 | 기존 1GiB급 서버 유지. 운영체제에 보이는 RAM은 약 914MiB |

측정에 사용한 이미지의 고유 식별값:

```text
sha256:de16e1a06c4047dd8ac13055bba7c6dc560538c4c4d138ef1a3d55422992d0fe
```

Heap(자바 객체를 담는 메모리 공간)은 서버 전체 메모리의 일부다. Heap이 여유로워도 운영체제·DB·다른 자바 영역까지 합치면 서버 전체는 부족할 수 있다.

MiB·GiB는 메모리 크기 단위이며 1GiB는 1,024MiB다. Git(코드 변경 이력을 기록하는 도구)의 커밋은 그때의 변경을 묶어 저장한 기록이다.

G1과 DB 캐시 조정은 앞선 작업에서 적용한 설정이다. 이번 기록의 시작 이후에 모두 새로 바꿨다는 뜻은 아니다. 실행 중 도구를 수정한 경우에는 Git 커밋만 믿지 않고 파일 해시(내용이 같은지 확인하는 식별값)도 따로 기록했다.

## 5. 왜 짧은 시험은 성공하고 다른 때는 실패했나?

### 메모리는 책상, 디스크는 서랍이라고 생각하자

RAM(프로그램이 지금 일할 때 사용하는 메모리)을 책상이라고 생각하면 쉽다. 책상이 좁으면 일부 자료를 서랍에 넣었다가 다시 꺼내야 한다.

스왑(RAM의 자료 일부를 디스크로 옮겨 보관하는 기능)이 이와 비슷하다. 다시 꺼내는 동안 디스크를 기다리면 CPU(계산을 담당하는 자원)가 한가해 보여도 응답은 늦을 수 있다.

30분 지속 시험을 준비하다 실패한 구간에서는 다음이 함께 관측됐다.

| 관측한 것 | 수치·의미 |
| --- | --- |
| 실패 요청 | 저금통 목록 조회, 약 3.04초 후 요청 도구가 포기 |
| CPU 최대 | 약 12.68%. 계산 능력을 계속 꽉 채워서 중단된 상황은 아님 |
| 가용 메모리 최저 | 약 89.13MiB. 바로 사용할 수 있는 메모리가 많지 않음 |
| 디스크 대기 최대 | 약 66.73% |
| 스왑에서 읽어 온 양 최대 | 약 14.95MiB/초 |
| GC 누적 시간 증가 | 관측 중 11회·344ms. GC(더 쓰지 않는 자바 객체 메모리를 정리하는 작업)가 있었지만 이것만으로 3초 지연 전체를 설명할 수 없음 |

확인한 사실은 **요청 실패와 큰 디스크·스왑 이동이 같은 구간에 있었다**는 것이다. 해당 요청의 내부 코드나 DB 조회가 각각 몇 초 걸렸는지까지 확정한 것은 아니다.

또한 뒤의 관리 API 실패까지 모두 같은 원인이라고 단정하지 않는다. 실패한 관리 API 구간은 자원 자체를 못 읽었으므로 “정상이었다”거나 “메모리가 0이었다”고 채우면 안 된다.

## 6. 3초를 5초로 바꾸면 무엇이 달라지나?

음식이 나오는 속도는 그대로인데, 손님이 기다려 주는 시간을 늘리는 것과 같다. **더 기다려서 성공한 것과 서버가 빨라진 것은 다르다.**

| 구분 | 최종 시험 조건 | 역할 |
| --- | --- | --- |
| 일반 시험 요청 | 승인된 모드에서 5초 | 로그인·내 정보·저금통 조회 등의 응답 대기 |
| 관리 API 요청 | 3초 → 5초 | 서버의 CPU·Heap·DB 연결 상태를 읽는 감시 경로 |
| 관리 API를 실행하는 바깥 명령 | 4초 → 6초 | 안쪽 요청이 5초를 쓰기 전에 바깥에서 먼저 끊지 않도록 여유 1초 부여 |
| 다른 Docker(프로그램을 컨테이너 단위로 실행하는 도구) 명령 | 4초 유지 | 컨테이너 상태 확인 등은 기존 제한 유지 |
| 조회 응답 성능 목표 | API별 p95 500ms 이하 유지 | 기다리는 최대 시간과 별도로, 평소 응답이 충분히 빠른지 판정 |

관리 API와 일반 API는 서로 다른 경로와 설정을 사용했다. 그래서 일반 요청을 5초로 바꿔도 관리 API는 여전히 3초에 멈췄던 것이다. 사용자가 승인한 뒤 관리 경로도 별도로 바꿨다.

실제 앱 전체의 요청 제한이나 인증 보안 정책을 바꾼 것은 아니다. 기존 시험 도구의 3초 모드도 남겨 두었다. 5초 모드는 정해진 실행 범위를 명시해야 사용할 수 있다.

## 7. 안전장치는 그대로 유지했다

| 조건 | 처리 |
| --- | --- |
| CPU 70%·Heap 75%·DB 연결 사용률 80%를 각각 초과한 상태가 30초 지속 | 부하 도구 중단 |
| DB 연결 사용률 70% 이상 | 경고 기록 |
| Heap 90% 이상 또는 가용 메모리 64MiB 미만 | 즉시 중단 판단 |
| 지표 수집 실패·15초 이상 지표 미수신 | 중단. 모르는데도 계속 요청하지 않음 |
| 컨테이너 교체·예상 밖 재시작·OOM(메모리 부족으로 강제 종료됨) | 중단 |

감시기는 자신이 시작한 k6(가상 요청을 보내는 시험 도구)만 중단한다. 서비스와 DB를 꺼서 멈추는 방식이 아니다.

회복 확인에서는 마지막 6개 표본의 가용 메모리 100MiB 이상, Heap 75% 이하, DB 연결 대기 0개, 평균 디스크 대기 5% 이하, 평균 스왑 읽기·쓰기 각각 1MiB/초 이하 등을 확인했다. 약 5초 간격의 표본이므로 사이의 모든 순간을 본 것은 아니다.

## 8. 마지막 10 VU·50 VU 조회 결과

### 시험 조건

- 실제 EC2를 대상으로 개발자 PC에서 요청했다.
- 가상 사용자마다 다른 전용 계정을 사용했다.
- 조회는 각 단계 **60초**, 응답을 받은 뒤 **1초 휴식**이었다.
- 저금통 목록·상세·쪽지 목록을 약 30%·30%·40% 비중으로 조회했다.
- HTTP 200(성공 상태 코드)뿐 아니라 사용자·자료 ID·개수·순서·페이지 정보도 확인했다.
- 로그인 준비와 로그아웃은 조회 응답 시간에서 분리했다.

그래서 지금의 결론은 **“정해진 짧은 조회 시험 조건은 충족했고, 상위 부하 전에 확인할 경고도 찾았다”**다.
