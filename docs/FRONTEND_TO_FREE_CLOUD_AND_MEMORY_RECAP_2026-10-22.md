# Memory Jar — 화면 개선부터 무료 서버 확인·메모리 진단까지

작성일: **2026년 10월 22일, 한국 시간**

정리 범위: 사용자가 **“계속 하던거 해보자 ㅋㅋ”**라고 말한 부분부터, **“대체 배포 경로는 어떻게 만드는가?”**를 설명하고 **변경 없이 문서로 정리하기로 한 시점**까지.

> 한 줄 결론: 화면 개선 작업을 이어가다가 서버 비용과 성능을 함께 검토했다. Oracle은 조회 시점에 자리가 없었고, Google은 기존 무료 체험이 종료된 화면을 확인했다. 그래서 기존 AWS를 유지하며 메모리를 실제 측정했고, 배포 실행기를 없애는 대체 경로를 제안했다. **대체 배포는 아직 만들거나 적용하지 않았다.**

이 문서는 요청·결정·측정 결과를 모은 진행 기록이다. 모든 화면이 운영에 반영됐거나, 성능 문제가 해결됐다는 완료 보고서가 아니다.

## 1. 시간이 없으면 이것부터 읽기

**지금 멈춘 위치:** 기존 AWS와 배포 방식은 그대로다. 사용자가 먼저 기록을 정리하자고 했으므로 이 문서만 새로 작성한다.

## 3. 처음에는 화면을 더 편하게 만드는 일을 했다

### 3-1. 사용자가 요청한 방향

핵심은 **“꾸미기만 하는 것이 아니라, 읽기 쉽고 쓰기 편하게 만들자”**였다.

| 화면 | 요청한 개선 방향 |
| --- | --- |
| 내 저금통 보관함 | PC 3열을 유지하며 설명은 약 14px, 날짜·인원은 12~13px로 키우기 |
| 보관함 정보 순서 | 그림 → 이름 → 설명 → 열리는 날짜·인원. 테마·역할은 보조 정보로 두기 |
| 보관함 상태 표시 | 의미가 애매한 진행 막대 대신 남은 날짜와 열리는 날짜를 직접 보여주기 |
| 보관함 버튼 | 새 저금통 버튼은 대표 초록색, 카드 문구는 ‘저금통 보기’로 통일 |
| 제작 단계 | 현재 단계는 선명하게, 모바일은 현재 단계부터 간단히 보여주기 |
| 그림판 | 도구가 화면을 밀어내지 않게 정리하고 그리기·되돌리기·미리보기 유지 |
| 설명 | 반복 안내는 도움말로 묶기 |
| AI 스타일 | 9개는 유지하되 선택한 카드만 테두리·체크로 분명히 강조 |
| 쪽지 작성 | 제목·내용에 집중하고 날짜·장소·태그는 선택 항목으로 접기 |
| 채팅 | 제목·테두리 중복을 줄이고 대화 영역을 넓히기. 어려운 연결 용어는 쉬운 안내로 바꾸기 |
| 알림 | 아이콘·내용·시간 위치를 통일하고 안 읽은 항목만 강조 |
| 공통 메뉴 | ‘Jars’를 ‘내 저금통’으로 바꾸고 로그아웃은 내정보 안으로 이동 |
| 글꼴·상태 표시 | 글꼴을 실제로 불러오고 문의의 접수·확인 중·답변 완료를 글자와 색으로 구분 |

모바일만이 아니라 PC 웹에도 적용해 달라는 요청이었다. 기존 애니메이션·인증·버튼 동작을 임의로 없애자는 요청은 아니었다.

### 3-2. 현재 로컬 코드에서 확인한 내용

- 보관함은 PC 3열, 중간 화면 2열, 작은 화면 1열을 정의한다. 설명 14px, 날짜·인원 12~13px, ‘저금통 보기’와 초록색 생성 버튼 코드가 있다.
- 제작 화면에 접을 수 있는 도움말이 있고, AI 선택 카드에는 선택 테두리·체크 표시가 있다.
- 새 스타일은 **네온 드로잉, 크롬 미러, 리소 프린트**다. 초기 제안이었던 종이 콜라주·자수·스테인드글라스를 최종 추가 스타일로 기록하지 않는다.
- Pretendard 글꼴을 로컬 폰트 파일에서 불러오는 CSS가 있다.
- 문의 상태는 접수·확인 중·답변 완료 등을 글자·아이콘·색으로 구분하는 코드가 있다.
- 상단 메뉴의 ‘내 저금통’과 내정보 내부 로그아웃 코드가 있다.

**주의:** 코드가 있다는 사실과 모든 기기에서 화면 검증을 마쳤다는 사실은 다르다. 이 문서를 쓰면서 전체 UI 시험을 다시 실행하지 않았다. 성공·오류·빈 화면 표현의 서비스 전체 통일까지 끝났다고 선언하지 않는다.

현재 HEAD(체크아웃한 커밋)는 `a36d5d4554bd184086dcbc27e0944d3e06c0ee1c`이고 제목은 **‘feat: 저금통 화면 가독성과 제작 흐름을 개선하고 AI 스타일 3종 추가’**다. 앞선 운영 조회에서도 API의 버전 표시가 이 커밋과 일치했다. 이것만으로 별도 프론트 배포나 모든 미커밋 작업의 반영까지 입증되지는 않는다.

### 3-3. 이어서 요청한 쪽지·메뉴·지도

사용자는 참고 사진을 주고 다음을 요청했다.

1. 쪽지 작성창을 종이 느낌으로 정돈하기.
2. ‘내 저금통’ 버튼 글씨를 가운데 맞추기.
3. 내정보 메뉴를 읽기 쉽게 정리하기.
4. 장소를 직접 적거나, 지도에서 골라 넣을 수 있게 하기.

현재 로컬에는 작성창 CSS, 장소 입력 컴포넌트, 카카오 지도 로더, 메뉴 변경이 있다. **일부는 미커밋·미추적 상태이므로, 전부 저장·배포가 끝났다고 쓰면 안 된다.**

지도 코드는 다음 방식이다.

- 직접 입력은 지도를 쓰지 않아도 가능하다.
- 지도 버튼을 누를 때 카카오 지도 SDK(지도 기능을 제공하는 도구)를 불러온다.
- 장소 검색·지도 클릭 후 ‘이 장소 사용’으로 입력칸에 반영한다.
- 지도 설정이나 연결에 문제가 있어도 직접 입력은 유지한다.
- 기존 `location` 문자열에 장소를 저장한다. 좌표용 DB 구조를 새로 만들지 않았다.

실제 운영 연결에는 JavaScript 키·허용 도메인·프론트 빌드 설정이 필요하다. **연결 코드 존재와 실제 키·도메인에서의 성공은 구분한다.** 실제 키나 비밀값은 이 문서에 넣지 않는다.

## 4. 화면 작업에서 서버 문제로 관심이 옮겨갔다

사용자는 화면 작업을 잠시 멈추고 **Oracle Cloud를 먼저 하자**고 정했다.

출발점은 작은 AWS 서버 한 대에 다음이 함께 있다는 점이었다.

| 구성 | 하는 일 |
| --- | --- |
| 운영체제·기본 서비스 | 서버 운영, 접속, 로그 등 |
| Java·Spring Boot | Memory Jar 요청 처리 |
| MariaDB | 데이터 저장·조회 |
| Docker | 백엔드·DB 컨테이너 관리 |
| 배포 실행기 | 새 버전 배포 작업 수신·실행 |

여기서 중요한 설명을 바로잡았다. **컴파일·테스트·이미지 빌드는 이미 GitHub 제공 서버에서 한다.** AWS의 배포 실행기는 완성된 이미지를 내려받고 교체한다. ‘무거운 빌드를 모두 AWS에서 한다’는 전제로 절감량을 계산하면 안 된다.

목표였던 50 → 100 → 150 → 200 → 300 VU의 조회 시험은 그대로지만, 서버를 확보하거나 RAM을 늘린 것만으로 통과를 선언하지 않기로 했다.

이전 기록에서는 50 VU 준비 과정의 첫 로그인에서 시간이 초과돼 동시 조회가 시작되지 않았다. **‘50명 조회 실패’와 ‘50명 시험의 준비 실패’는 다르다.** 이 과거 시험을 이번에 재실행한 것으로 기록하지 않는다.

## 5. Oracle: 오사카에 자리가 있는지 직접 확인했다

### 5-1. 생성 실패와 자리 조회는 다르다

앞선 Oracle 생성 로그에는 `Out of host capacity`가 있었다. 이후 Cloud Shell(브라우저에서 명령을 입력하는 창)에서 용량 보고서를 조회했다.

| 종류·조건 | 제공된 결과 |
| --- | --- |
| A1, 2 OCPU·12GB | 자리 부족 |
| A1, 1 OCPU·6GB | 자리 부족 |
| AMD Micro, RAM 1GB | 자리 부족 |

OCPU는 Oracle의 CPU 할당 단위다. AMD Micro의 정확한 이름은 `VM.Standard.E2.1.Micro`다.

AMD 조회 결과의 핵심은 다음과 같았다.

```json
{
  "count": null,
  "shape": "VM.Standard.E2.1.Micro",
  "status": "OUT_OF_HOST_CAPACITY"
}
```

판단 근거는 `count: null`이 아니라 **`OUT_OF_HOST_CAPACITY`**다. 명령을 잘못 입력했다거나 우리 서비스 코드가 틀려서 나온 결과로 보지 않는다.

이 결과는 **조회 당시**의 상태다. 이 문서 작성 시 다시 조회한 것이 아니며, 다른 나라까지 모두 자리가 없다는 뜻도 아니다.

### 5-2. 다른 나라와 새 계정을 검토했지만 진행하지 않았다

- 계정에서 확인한 구독 리전(사용 가능하도록 등록한 지역)은 오사카 한 곳이었다.
- 다른 나라의 실시간 자리를 확인한 자료는 없었다. ‘어느 나라에는 확실히 있다’고 보장하지 않았다.
- 홈 리전(계정의 기본 지역)과 상시 무료 자원 조건 때문에, 지역 선택을 단순 버튼 변경으로 해결할 수 있다고 설명하지 않았다.
- 사용자는 새 계정을 만드는 계획을 취소했다. 다른 아이디로 혜택을 다시 받는 것을 해결책으로 추진하지 않았다.
- 오사카는 나중에 재확인할 수 있지만, 자동 감시·자동 생성·예약을 설정한 것은 아니다.

**결론:** Oracle DB 서버를 확보해 옮기는 계획은 실행하지 못했다. 기존 AWS·데이터·도메인은 유지했다.

## 6. 무료 서버 여러 대를 연결하는 방법도 검토했다

질문은 ‘AWS 1GB, Google 1GB, Oracle AMD Micro 1GB를 나눠 쓰면 되지 않을까?’였다.

**가능한 구조이지만, 1GB 세 대가 하나의 3GB 서버가 되지는 않는다.** 책상 세 개에 일을 나누는 것이지, 한 프로그램이 세 책상의 RAM을 자동으로 합쳐 쓰는 것은 아니다.

| 후보 배치 | 기대 효과 | 주의점 |
| --- | --- | --- |
| AWS에 백엔드 유지 | 서비스 연결을 크게 바꾸지 않음 | 여전히 작은 서버의 한계가 있음 |
| Oracle 오사카에 MariaDB | AWS에서 DB 부담 분리 | 서버 확보, 통신 속도, DB의 CPU 성능부터 확인 필요 |
| Google에 보조 관리 작업 | 일부 관리 작업 분리 | 새 서버가 꼭 필요한지, 미국 위치·IP 요금을 검토해야 함 |

서버마다 운영체제가 필요하고, 컨테이너를 실행하는 서버마다 Docker가 필요하다. Java의 실행 환경이나 Docker 하나를 모든 서버가 공유하는 방식은 아니다.

현재 코드는 DB 주소를 환경변수로 받을 수 있어 원격 MariaDB 연결 구조는 가능하다. 하지만 배포 도구는 백엔드·DB가 같은 서버에 있다고 가정하고 검사한다. **DB 주소만 바꾸고 끝낼 수는 없다.** 배포·감시·암호화·백업·복구도 바꿔야 한다.

외부 DB는 백엔드만 접속하도록 제한하고 통신을 암호화해야 한다. 또한 인증 상태 확인에도 DB를 조회하므로, 먼 나라에 DB를 두면 요청마다 대기 시간이 추가될 수 있다.

Oracle AMD Micro는 RAM 1GB라도 기본 CPU 몫이 1/8 OCPU이고 여유 CPU를 추가 사용하는 형태다. **같은 1GB라도 처리 성능까지 같은 것은 아니다.**

## 7. AWS 증설도 검토했지만 결제·변경하지 않았다

AWS를 2GB 또는 4GB로 키우면 서버 간 통신 구조를 바꾸지 않고 메모리를 늘릴 수 있다고 설명했다.

하지만 사용자는 **‘좋아져도 결국 더 큰 서버를 계속 쓰면 비용이 늘지 않느냐’**고 짚었다. 맞는 지적이었다.

- 짧게 증설해 원인을 확인하는 것과, 늘린 서버를 계속 운영하는 것은 다르다.
- 서버 요금뿐 아니라 디스크·공인 IP·전송량·CPU 추가 요금·기존 크레딧도 확인해야 한다.
- 정확한 추가 견적은 확정하지 않았다. 후보 이름만으로 실제 청구액을 단정하지 않았다.
- 실제 서버 유형 변경·중지·재시작은 하지 않았다.

**결론:** 추가 비용 없이 할 수 있는 확인을 먼저 하기로 했다.

## 8. Google: 상시 무료와 신규 체험을 구분했다

### 8-1. 상시 무료 VM은 큰 서버 무료 제공과 다르다

당시 확인한 Google 공식 조건은 미국 지정 지역의 `e2-micro` VM, 표준 디스크와 제한된 전송량이었다. 서울·일본의 큰 RAM 서버를 상시 무료로 제공하는 조건은 아니었다.

외부 IPv4(인터넷에서 서버에 접속하는 주소)는 VM 무료 한도와 별도다. 당시 공식 단가 시간당 $0.005를 30일 내내 사용하면 주소 비용만 약 $3.60이다. 세금·다른 자원·전송량을 포함한 총액은 아니다.

따라서 다음을 구분했다.

- **AWS 백엔드 + 미국 Google DB:** RAM은 분리되지만 장거리 DB 통신이 추가된다.
- **모두 Google의 작은 무료 VM으로 이전:** 백엔드와 DB가 다시 작은 서버 한 대를 공유한다.
- **Google에 관리 작업만 분리:** 가능하지만 무거운 빌드는 이미 GitHub에 있어 효과가 제한적이다.

### 8-2. 신규 $300·90일 체험을 확인했다

신규 체험이라면 더 큰 서버에서 백엔드·DB를 함께 시험할 수 있다고 검토했다. 하지만 이것도 영구 무료 운영은 아니다.

처음 보여준 화면은 무료 제품 소개 페이지여서 계정 자격을 판단할 수 없었다. 직접 체험·결제 화면으로 들어간 뒤, 사용자가 제공한 화면에서 **‘무료 체험 기간이 종료되었지만…’**이라는 표시를 확인했다.

**이 계정은 기존 체험이 종료된 상태로 판단했다.** 새 $300 체험이 열린 것으로 취급하지 않았고, 새 서버도 만들지 않았다.

- ‘업그레이드’는 무료 체험 재시작 버튼이 아니다.
- 화면의 ₩0은 표시 기간의 비용이지 앞으로 모든 사용이 무료라는 뜻이 아니다.
- 기존 체험 종료 후 상시 무료 자원을 사용하려면 결제 계정 상태와 무료 범위를 별도로 확인해야 한다.
- 유료 전환·카드 정보 변경·새 계정 생성은 이번 작업에서 하지 않았다.

## 9. AWS를 그대로 두고 실제 메모리를 측정했다

### 9-1. 접속 실패를 숨기지 않고 다시 확인했다

처음에는 SSH(원격 서버 접속)가 시간 초과돼 실시간 진단을 하지 못했다. 과거 기록을 새 측정값으로 사용하지 않았다.

사용자가 접속을 준비했다고 알려준 뒤 다시 연결에 성공했다. 에이전트가 보안 그룹 규칙을 바꾸거나 접속 허용 범위를 넓히지는 않았다.

이후 **2026년 10월 22일 17:49~17:50 KST**, 약 1분 동안 13개 표본을 확인했다. 내부 관리 지표와 운영체제 메모리 정보를 읽었고, 로그인·동시 조회·이메일·유료 AI 요청은 실행하지 않았다.

이것은 **새 시험 부하를 주지 않은 짧은 관찰**이다. 실제 사용자 요청이 전혀 없었다고 보장하거나 진단 요청의 작은 영향까지 없었다고 말하지 않는다.

### 9-2. 프로세스별 결과

MiB는 메모리 크기를 나타내는 단위로, 여기서는 읽기 쉽게 ‘약 몇 MB 규모인가’를 비교하면 된다. 정확한 MB와 MiB는 서로 다르다.

| 대상 | RAM에 올라온 양 | 스왑으로 나간 양 |
| --- | ---: | ---: |
| Java 백엔드 | 약 260~269MiB | 약 240~249MiB |
| MariaDB | 약 12MiB | 약 70MiB |
| 배포 실행기 주 프로세스 | 약 36MiB | 약 43MiB |
| Docker 관리 프로세스 두 개 | 약 65MiB | 약 14MiB |

서버 전체 RAM은 약 **914MiB**, 13개 표본의 사용 가능한 메모리는 약 **214~247MiB**였다. 전체 스왑은 약 548 → 539MiB였다. 앞선 접속 직후 한 번 확인한 값과 관찰 시작 값은 시점이 다르므로 하나의 고정값으로 섞지 않는다.

표의 프로세스 RAM은 RSS(그 프로세스에 올라온 물리 메모리)다. 공유 메모리와 운영체제 영역이 있으므로 표를 단순 합산해 서버 전체 사용량이라고 하지 않는다.

### 9-3. ‘Java는 224MiB만 쓴다’는 생각은 틀렸다

| Java 내부 항목 | 첫 1분 관찰·인접 조회에서 확인한 값 |
| --- | ---: |
| 힙 최대값 | 224MiB |
| 힙 사용량 | 약 73~76MiB, 33~34% |
| 힙에 확보한 공간 | 약 204MiB |
| 비힙 사용량 | 약 195MiB |
| 직접 버퍼 | 약 0.42MiB |

`-Xmx224m`은 **힙의 최대값**이지 Java 전체의 최대값이 아니다. 클래스 정보·실행 코드·스레드 등은 별도로 필요하다.

힙과 비힙의 사용량은 JVM 내부 기준이고, RAM·스왑은 운영체제 기준이다. 서로 단순 합산해 정확한 전체 점유라고 계산하지 않는다. 비힙 집계가 모든 힙 밖 메모리를 빠짐없이 측정하는 것도 아니다.

### 9-4. 당시 함께 확인한 사실과 한계

- 관찰 중 GC(불필요한 Java 객체를 정리하는 작업) 횟수·누적 시간 증가가 없었다.
- DB 연결 풀(재사용할 DB 연결 모음)의 상한은 10개였고, 관측 시 연결 대기는 0개였다.
- 새 스왑 출력은 관측되지 않았다. 초반 스왑 읽기 약 1.46MiB/s는 이후 크게 감소했다.
- API·DB 컨테이너는 교체되지 않았고 재시작 횟수도 유지됐다. 메모리 부족 강제 종료 표시도 없었다.
- 컨테이너 자체의 RAM 상한은 설정돼 있지 않았다. 서버 전체 메모리 한계가 사라졌다는 뜻은 아니다.

**읽을 때 주의할 점:**

1. DB RAM이 12MiB라고 부담이 없다는 뜻은 아니다. 많은 부분이 스왑에 있다.
2. 스왑에 남아 있는 양과 지금 디스크를 오가는 속도는 다르다.
3. 힙 사용률이 낮다고 Java 전체가 가볍다는 뜻은 아니다.
4. 이번 표본만으로 모든 로그인 지연의 원인이나 메모리 누수를 확정할 수 없다.
5. 100 VU를 처리할 수 있다는 검증도 아니다.

## 10. Java를 줄일 구체적인 후보도 조사했다

### 10-1. 비힙 약 195MiB의 구성

17:56 KST 무렵 추가로 집계 지표를 세 번 조회했다. 비힙은 약 195~196MiB로 비슷한 규모였다. 이때 힙 사용률은 약 35%여서 앞선 1분과 같은 시점의 값으로 섞지 않는다.

| 구성 | 대략적인 사용량 | 하는 일 |
| --- | ---: | --- |
| Metaspace | 135MiB | 클래스 구조 정보 보관 |
| Compressed Class Space | 18MiB | 압축된 클래스 참조 관련 정보 보관 |
| Code Cache | 42MiB | 빠르게 실행하려고 변환한 코드 보관 |

추가 집계의 Java 스레드는 53개였다. 운영체제의 전체 Java 스레드 수와 같은 방식으로 센 값은 아니다.

### 10-2. 확인한 코드와 후보

| 후보 | 확인한 내용 | 판단 |
| --- | --- | --- |
| Netty 의존성 제외 | 로컬 실행 JAR에 비동기 통신 라이브러리 포함. 검색한 현재 소스에서는 AWS 비동기 클라이언트 사용을 찾지 못함 | 후보지만, 실제 클래스가 로딩되지 않았다면 RAM 절감은 작을 수 있음 |
| AWS HTTP 통신 경량화 | S3·SES·Rekognition 클라이언트 설정이 따로 있음 | 가벼운 HTTP 구현 또는 공유 연결을 비교할 수 있음. 통신·종료 처리 검증 필요 |
| Java 실행 최적화 단계 축소 | `-XX:TieredStopAtLevel=1`을 비교 후보로 설명 | 코드 메모리를 줄일 가능성이 있지만 처리 속도가 나빠질 수 있어 격리 비교부터 필요 |

로컬 JAR은 프로그램을 묶은 파일이다. **그 안의 라이브러리 목록을 본 것과 운영에서 해당 클래스의 메모리 점유를 증명한 것은 다르다.** 어느 후보도 절감량을 확정하지 않았다.

다음은 바로 적용할 해결책으로 채택하지 않았다.

- Metaspace 상한만 낮추기: 필요한 클래스가 줄지 않고 메모리 부족 오류가 날 수 있다.
- 전체 지연 초기화: 준비를 첫 요청까지 미뤄 첫 로그인 지연이나 설정 오류 발견을 늦출 수 있다.
- 이미 쓰는 보안·JPA·메일·이미지 기능 삭제: 정상 기능을 잃을 수 있다.
- 힙 무조건 확대, 스왑 끄기, 강제 메모리 정리: 여유·영향을 검증하지 않고 하지 않는다.

추가 조회 도중 출력 처리에서 `null` 값을 목록처럼 더하는 오류가 한 번 있었다. 그때 끝나지 못한 옵션·컨테이너 상태 확인은 조회 코드를 고쳐 다시 완료했다. 서비스 코드 오류나 운영 재시작으로 기록하지 않는다.

## 11. 배포 실행기는 무엇이고 왜 줄이려 하나?

**배포 실행기는 새 프로그램으로 교체하는 일을 기다리는 작업 담당자다.** 로그인·쪽지 요청을 처리하는 백엔드와는 다르다.

현재 흐름은 다음과 같다.

```text
GitHub에 코드 올리기
  → GitHub 제공 서버에서 테스트·이미지 빌드
  → 이미지 저장소에 새 이미지 게시
  → AWS의 배포 실행기가 작업 수신
  → 기존 배포 도구가 백엔드 교체·상태 검사
  → 실패하면 가능한 범위에서 이전 이미지로 복귀
```

배포 실행기는 작업이 없을 때도 기다리며 켜져 있다. 추가 측정에서는 **PSS(공유 메모리를 각 프로세스 몫으로 나눠 계산한 값)**로 RAM 약 35MiB, 스왑 몫 약 43MiB를 확인했다.

따라서 상주 RAM 수십 MiB를 줄일 후보라는 근거는 있다. 그러나 다음은 구분한다.

- RAM 35MiB와 스왑 43MiB를 더해 ‘RAM 78MiB 확보’라고 말하지 않는다.
- 제거 후 서버의 사용 가능 메모리가 정확히 35MiB 증가한다고 보장하지 않는다.
- 배포할 때 이미지 다운로드·교체 작업까지 AWS에서 사라지는 것은 아니다.
- 이것만으로 100 VU 문제가 해결된다고 말하지 않는다.

## 12. 대체 배포 경로는 어떻게 만들 계획인가?

**이 장은 설명한 계획이지 실행한 작업이 아니다.**

기존 배포 도구를 버리는 것이 아니라 작업을 지시하는 경로를 바꾸는 구상이다.

```text
GitHub 제공 실행기
  → OIDC로 제한된 AWS 임시 권한 받기
  → SSM으로 지정 서버에 배포 명령 전달
  → 기존 배포 도구 실행
  → 실제 성공·실패 결과를 GitHub에서 확인
```

SSM 관련 프로그램은 운영 서버에 이미 실행 중이었다. **AWS 관리 대상 등록·온라인 연결·권한까지 정상인지 확인한 것은 아니다.**

### 12-1. 설명한 다섯 단계

1. **연결 확인:** AWS에서 서버가 온라인 관리 대상으로 보이는지 확인한다. 처음에는 상태 조회 같은 변경 없는 명령만 시험한다.
2. **권한 설계:** 지정 저장소의 승인된 배포가 지정 서버·배포 명령만 실행할 수 있도록 한다. 장기 AWS 비밀번호를 GitHub에 복사하는 방식은 피한다.
3. **전달 경로 구현:** 검증한 이미지 정보와 해당 버전의 배포 코드를 전달한다. 명령 접수만으로 성공 처리하지 않고 실제 종료 결과를 확인한다.
4. **안전장치 검증:** 잘못된 버전 거절·동시 배포 차단·DB 유지·상태 검사·실패 후 복귀를 먼저 대역 테스트로 확인한다. 실제 배포는 별도 승인 후 검증한다.
5. **마지막에 실행기 중지:** 새 경로가 검증된 뒤에만 기존 실행기를 중지한다. 즉시 삭제하지 않고 기존 경로로 돌아갈 방법을 보존한다.

전환 중에는 두 경로가 동시에 자동 배포하지 않도록 제어해야 한다. SSM은 서버가 외부로 연결하는 방식이어서 GitHub 실행기의 IP 때문에 SSH를 인터넷 전체에 공개할 필요가 없다.

### 12-2. 예상 변경 범위와 비용

- 배포 워크플로, 원격 전달·검증 코드, 관련 테스트, 운영 안내.
- AWS의 임시 인증·권한·명령 실행 범위 설정.
- 기존 배포 도구의 이미지 검증·커밋 확인·잠금·DB 보호·상태 확인·복귀 동작 유지.
- API·DB 이전이나 새 서버 생성은 필요하지 않은 구상이다.

SSM Run Command 자체는 EC2에서 추가 서비스 요금 없이 제공되지만, GitHub 실행 시간·전달용 저장소·로그·통신은 별도로 확인해야 한다. **전체 비용이 무조건 0원이라고 확정하지 않았다.**
