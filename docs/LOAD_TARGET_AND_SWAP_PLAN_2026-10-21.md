# 임시 조회 목표 2초와 스왑 회복 진단 계획

작성일: 2026-10-21, 한국 시간 기준.

> 이 문서는 **2초 목표를 정했을 당시의 계획과 상태**를 보존한 기록이다. 이후 2초 재시험을 실행했고, 사용자 승인으로 임시 목표를 5초로 변경해 별도 시험도 시도했다. 아래의 '미실행'은 이 문서 작성 당시를 뜻한다. 최신 결과·5초 옵션·남은 작업은 [화요일 배포 이후 부하 시험 정리](LOAD_TEST_RECAP_2026-10-20_TO_21.md)를 확인한다. 과거 실패를 새 기준으로 재판정하지 않는다.

## 결정과 적용 범위

사용자 결정에 따라 앞으로 새로 측정하는 일반 조회의 임시 허용 목표는 **API별 p95 ≤ 2,000ms**로 한다. p95는 응답의 95%가 이 시간 안에 끝나는 값이다. **500ms는 개선 목표**로 유지하며 과거 결과는 변경하지 않는다.

이 결정은 성능 개선이나 기존 50 VU 시험 통과를 뜻하지 않는다. 기존 50 VU는 약 7.8초에서 종료되어 새 기준의 60초 결과로 재판정할 수 없다. 요청별 제한 5초, 오류율 1% 미만, 기존 자원 중단·회복 수치, 계정 분리, 외부 비용 경로 제외는 유지한다.

### 이번 도구 변경

- `tools/load/read-contract.mjs`: 기존 500ms 기본값을 재현 가능하게 유지하고 명시적 2000ms 선택을 지원한다. 500·2000 외의 값은 실행 전에 거절한다.
- `tools/load/read-ec2.js`, `tools/load/read-scale.js`: `READ_P95_TARGET_MS=2000`을 선택하면 임시 목표를 사용한다. 이 값으로 요청 제한이나 오류율을 변경하지 않는다.
- 위 계약·EC2·상위 VU 검사 파일: 기본값 보존, 잘못된 목표 거절, 2초 선택 시 요청 제한·계정·정리 유지, 실제 k6의 외부 요청 없는 옵션 해석을 검사한다.

새 시험의 k6 옵션에는 `--env READ_P95_TARGET_MS=2000`을 명시해야 한다. 환경변수 미지정은 과거 재현을 위해 500ms다. 선택했다고 과거 기록이나 원본을 다시 평가하지 않는다.

**실제 부하는 이번 작업에서 실행하지 않았다.** 다음 측정 전에 새로운 실행 기록에 `p95TargetMs: 2000`과 `improvementTargetMs: 500`을 남기고, k6뿐 아니라 실행기의 최종 판정도 같은 임시 목표를 사용하도록 검증해야 한다. `build/load-ec2/read-stages-20261020-01/run_stage.py` 등 과거 실행 보조 도구의 500ms 판정은 과거 조건으로 보존되어 있으므로, 환경변수만 넣어 그 실행기를 새 시험에 재사용하면 안 된다.

부하 상승 속도·중단 평가 시점·회복 기준은 이번 목표 옵션 추가에서 변경하지 않았다. 이전 50 VU 실패와 종료 후 회복 미통과는 그대로 남긴다.

## 스왑 문제에서 확인한 사실

스왑은 RAM에 있던 메모리 페이지를 디스크에 두는 기능이다. 스왑에 남아 있는 양과 지금 오가는 속도는 서로 다르다. 스왑 사용량을 0으로 만드는 것이 해결 목표는 아니다.

2026-10-20 23:50:18~23:51:08의 11개 표본을 원본에서 다시 계산했다.

| 항목 | 처음 → 마지막 또는 판정에 사용한 값 |
| --- | --- |
| Java RSS(RAM에 실제 올라와 있는 메모리) | 약 376.84 → 322.34MiB |
| Java 스왑 | 약 156.35 → 211.10MiB |
| MariaDB RSS | 약 17.02 → 17.27MiB |
| MariaDB 스왑 | 약 64.75 → 64.50MiB |
| 호스트 전체 스왑 사용량 | 약 524.27 → 570.79MiB |
| 마지막 6개 표본 평균 스왑 입력 | 약 0.083MiB/s |
| 마지막 6개 표본 평균 스왑 출력 | 약 1.641MiB/s — 기존 기준 미통과 |
| 마지막 6개 표본 평균 디스크 대기 | 약 1.73% |
| 관찰 가용 메모리 최솟값 | 약 129.96MiB |
| 관찰 Heap 최댓값 | 약 39.05% |

해당 구간에서 Java의 RAM 사용량 감소와 스왑 증가가 거의 맞물린다. MariaDB가 주로 밀려난 구간은 아니다. 그러나 Java의 Heap·클래스 정보·스레드 등 어느 영역인지, 왜 운영체제가 이동시켰는지는 아직 확정하지 못했다.

입력보다 출력이 컸으므로 자주 필요한 페이지가 왕복 이동하며 처리가 멈추는 현상인지, 덜 쓰는 페이지를 한동안 디스크로 옮긴 것인지를 구분해야 한다. 이 자료만으로 정상 회복이나 심각한 메모리 부족 중 어느 하나로 단정하지 않는다. 기존 1분 회복 미통과도 그대로 보존한다.

## 해결 순서

| 순서 | 작업 | 판단 및 다음 행동 |
| --- | --- | --- |
| 1 | 새 부하 없이 최대 10분 읽기 전용 관찰. 5초 간격 자원·프로세스별 RAM/스왑·GC·디스크 대기를 함께 비교 | 이동량이 일시적인지, 계속 이어지는지 확인. 원래 1분 실패를 소급해서 통과로 바꾸지 않음 |
| 2 | Java·DB·배포 도구·OS의 메모리 사용과 예산 비교. Heap 외 메모리·스레드·버퍼도 포함 | JVM 최대 Heap만 보고 남는 RAM을 계산하지 않음. 실행 인자·환경변수·토큰 등 비밀값은 수집하지 않음 |
| 3 | 계속 부족하면 원인별 변경안을 제시 | 실제 미사용 도구의 점유, 앱의 불필요한 할당·상주량, DB 캐시, 운영체제 메모리 정책을 구분. 이미 정리한 서비스를 다시 지우지 않음 |
| 4 | 필요한 조치만 별도 승인 후 하나씩 적용하고 같은 조건으로 검증 | 모든 설정을 한꺼번에 변경하지 않음. RAM 증설은 비용·승인 확인 후 별도 검토 |
| 5 | 자원 준비 조건을 충족한 뒤 새 기준을 기록한 50 VU 재시험 | 새 기준 p95 2초와 개선 목표 500ms를 함께 보고. 자원·회복 미통과 시 100 VU 보류 |

10분 관찰은 회복 원인을 찾기 위한 추가 자료다. 기존 1분 회복 기준을 자동으로 10분으로 완화한다는 뜻은 아니다. 이후 회복 시간 창을 변경하려면 그 근거와 새 조건을 시험 시작 전에 별도로 정하고 과거 결과와 구분해야 한다.

`swappiness`(스왑과 파일 캐시 회수의 상대 비용을 판단하는 설정)는 낮추면 무조건 좋아지는 숫자가 아니다. Linux 공식 문서도 적정값은 실제 작업에 따라 실험해야 한다고 설명한다. 현재값과 압박 상태를 확인하지 않고 변경하지 않는다.

근거: [Linux 커널의 swappiness 설명](https://docs.kernel.org/admin-guide/sysctl/vm.html#swappiness).

`swapoff`, 강제 GC, 캐시 강제 삭제, 임의 서비스 종료·컨테이너 재시작, Heap 무조건 확대는 하지 않는다. 특히 스왑을 끄는 행위는 메모리를 RAM으로 되돌려야 하므로 사용 가능한 여유를 확인하지 않고 해결책으로 사용하지 않는다.

## 검증과 현재 상태

조회 도구 관련 Node 검사 **34개 통과**. 실제 k6 `inspect`에서 10·50·100 VU의 선택한 2초 기준을 외부 요청 없이 확인했다. `git diff --check` 통과. Java·프론트엔드 서비스 코드는 바꾸지 않아 빌드를 재실행하지 않았다.

서버 설정 변경·실시간 자원 관찰·새 부하·배포·커밋·푸시는 이번 단계에서 실행하지 않았다. 스왑 해결을 완료했다고 판단하지 않는다. 다음 실행은 위 1번 읽기 전용 관찰부터다.
