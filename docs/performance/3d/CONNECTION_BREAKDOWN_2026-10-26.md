# 연결 463ms의 내부 원인 확인 · 2026-10-26

## 지금 확실한 것과 아직 모르는 것

직전 실제 첫 요청에서는 서버 전체 985.14ms 중 연결 수립이 463.49ms였다. 원본은 [직전 기록](backend-texture-transport-first-2026-10-25.json)이다. 이 연결 시간에는 이름 조회, 실제 연결, 보안 협상과 클라이언트 준비가 함께 들어 있었다. 따라서 **TLS가 463ms 걸렸다고 말할 수 없다.**

이번에는 원인을 나누어 볼 계측을 추가했다. 계측 준비 시점에는 실제 S3 결과가 없었으며, 이후 수집한 실제 결과는 아래 마지막 절에 구분했다. 예열, 캐시 확대, TLS 설정 변경, 배포는 하지 않았다. 기존 캐시와 권한 검사를 유지한다.

택배를 받는 과정에 비유하면 주소 찾기 → 통로 연결 → 신분 확인 → 주문 전송 → 답변 대기 → 포장 해석을 구분하는 것이다.

`s3Sdk.durations`는 경과 시간, 새 `s3Sdk.cpuDurations`는 같은 스레드가 실제 CPU를 쓴 시간이다. CPU 측정을 지원하지 않거나 이미 꺼져 있으면 필드를 생략하고 설정을 강제로 켜지 않는다. **경과 시간−CPU 시간을 순수 네트워크 시간으로 해석하면 안 된다.** 스레드가 실행 순서를 기다린 시간이나 다른 대기도 포함될 수 있다. 다른 스레드에서 한 작업도 이 CPU 값에는 포함되지 않는다.

부모·자식 시간은 중첩되므로 더하지 않는다. 재사용 연결에는 DNS/TCP/TLS 기록이 없을 수 있고, 캐시 HIT에는 S3 자체가 실행되지 않는 것이 정상이다. 누락은 0ms로 채우지 않는다. 여러 접속 시도는 count/total/max와 재시도 수를 함께 읽는다. SDK 콜백 중복·누락·실패는 `SDK_PHASE_INCOMPLETE`로 표시하고 완전한 단일 시도처럼 해석하지 않는다.

## 보안과 동작을 유지한 방법

- 로컬 프로필과 기존 명시적 계측 스위치가 모두 맞을 때만 설치한다. prod가 활성화되면 설치하지 않는다.
- 기존 SDK의 DNS 조회기, SSL 소켓 공장, 인증서 신뢰, 서버 이름 검증기에 그대로 위임한다. 새 SSLContext나 신뢰 예외를 만들지 않는다. 프록시·암호군·프로토콜·시간 제한·재시도 정책도 바꾸지 않는다.
- 공개 관찰 지점이 없는 연결 내부에는 현재 AWS Apache 2.31.67 / Apache HttpClient 4.5.13의 한정된 내부 필드만 사용한다. 시작 때 구조가 다르면 로컬 계측 시작을 거절한다. 이 경우 계측 인수를 제거하면 원래 경로로 실행할 수 있다. 버전 업그레이드 때 관련 테스트와 구조 검증을 다시 해야 한다.
- 숫자와 고정된 지표 이름만 저장한다. 사진, 객체 키, 주소, 인증서 내용, 헤더, 쿠키, 인증정보, 패킷, 원문 예외는 수집하지 않는다. 외부 진단 서비스로 전송하지 않는다.
- 매 요청의 인증/멤버십/현재 디자인 조회, PNG 응답, no-store, 캐시 만료·크기·동시 요청 정책을 유지한다. `JarDesignTextureCache.java`의 SHA-256은 이전과 같은 `8146AA2D0850F024E5395A88647F53F3A1A791ABD1DFB62FFB2412E1C0CD3F41`이다.

주요 변경 파일은 `monitoring/TextureSocketDiagnostics.java`, `TextureS3ExecutionDiagnostics.java`, `TextureDiagnosticsClock.java`, 기존 `TextureHttpTransportDiagnostics.java`, `LoginDiagnostics.java`, `config/S3Config.java`, `service/jar/JarDesignTextureService.java`다. 모두 `src/main/java/shop/esjh/memoryjar/` 아래에 있다. SDK 준비와 소켓 하위 구간을 추가 관찰하기 위한 변경이며, 다운로드나 캐시의 새 성능 최적화가 아니다.

## 실제 2D→3D를 함께 확인하는 방법

1. 백엔드를 기존 인수 `--spring.profiles.active=local --app.monitoring.texture-diagnostics-enabled=true`와 기존 환경변수 그대로 재시작한다.
2. 로컬 개발 프론트에서 이전과 같은 사진의 저금통 상세 주소에 `?diagnose3d=1`을 붙인다. 기존 쿼리가 있으면 `&diagnose3d=1`이다. 창 크기와 확대율을 유지한다.
3. 2D 상태에서 3D로 **첫 1회** 전환하고 사진이 완전히 보일 때까지 기다린다. 새 계측을 확인하기 전에는 반복 횟수를 늘리지 않는다.
4. 오른쪽 아래 `로컬 3D 시간`의 숫자 기록과 서버의 같은 시점 IMAGE 진단을 함께 확인한다. 서버 기록에 새 관찰자 카운터와 DNS/TCP/TLS 세부 지표가 있는지 확인해 이전 코드로 측정한 결과를 섞지 않는다.
5. 큰 구간과 그 CPU 시간을 본 뒤 필요한 개선만 선택한다. 개선한 경우에만 같은 사진·화면·배율·측정 방식으로 첫 요청, 바로 반복, 만료 후 요청을 나누어 비교한다. 권한·만료·실패 테스트도 다시 확인한다.

프론트의 진단 URL은 DEV 빌드와 localhost/127.0.0.1/IPv6 루프백의 상세·만들기 경로에서만 켜진다. 새 `LocalBody3DTimingPanel.jsx`는 화면 배치를 바꾸지 않는 별도 패널이며 숫자 결과만 표시한다. 브라우저 저장소나 서버로 전송하지 않는다. 2D 복귀 때 직전 완료 결과를 유지하고 횟수를 표시한다. 운영 빌드에는 이 패널과 결과 출력이 남지 않는 것을 확인했다.

클릭→모든 텍스처를 사용한 `renderer.render` 반환이 전체 완료 기준이다. 사진 소스 확보, 사진 onload까지, 모양 계산, 렌더러 준비를 함께 볼 수 있다. **GPU 실행 완료나 실제 모니터 표시 시점은 아니다.** `renderSubmitCpu`는 기존 이름으로, 동기 render 호출의 경과 시간 합계이며 JVM 스레드 CPU 지표와는 다르다.

## 실제 앱에서 완료 0회로 남은 계측 오류 수정

사용자가 실제 로컬 상세 화면에서 3D 전환 후에도 패널이 0회로 남는 현상을 보고했다. 앞의 합성 검증은 실제 앱의 `React.StrictMode`를 포함하지 않아 이 오류를 발견하지 못했다.

StrictMode는 개발 중 효과를 설정→정리→재설정해 정리 누락을 찾는다. 기존 `CustomJarBody3D.jsx`는 정리할 때 클릭 계측도 취소했다. 재설정된 렌더러는 같은 계측 객체를 사용했지만 객체가 이미 취소돼 결과를 내지 못했다. `?live-panel=1&strict-mode=1` 합성 진단에서 사진이 표시돼도 완료 0회인 현상을 수정 전에 재현했다.

클릭 계측의 취소는 소유자인 `CustomJarBodyViewer`의 실제 2D 전환에 맡기고, 렌더러 정리에서는 자원과 비동기 작업만 폐기하도록 수정했다. 폐기된 렌더러의 draw/이미지 콜백은 기존 disposed/version 검사로 차단한다. 폐기된 사진·테두리 소스의 늦은 응답이 현재 시간 기록에 섞이지 않도록 시간 종료도 이 검사 뒤로 옮겼다. 3D 모양·권한·캐시·백엔드 코드는 이 수정에서 바꾸지 않았다.

같은 StrictMode 화면에서 수정 후 완료 0→1→2회, 2D 복귀 시 직전 완료 기록 유지, 브라우저 오류·경고 로그 0건을 확인했다. [수정 확인 화면](strict-mode-panel-fix-2026-10-26.png). 프론트 Node 244개 테스트와 운영 빌드도 다시 통과했다. 기존 번들 크기 경고는 남아 있다. 테스트 fixture는 `strict-mode=1`일 때만 StrictMode를 켜므로 이전 기준점의 실행 모드를 임의로 바꾸지 않는다.

StrictMode 실측은 개발 검사 때문에 실행된 반복 준비·정리 비용도 클릭 전체 시간에 포함한다. 이번 동작 검증의 1262.2ms/1970.9ms를 이전 비-StrictMode 값과 전후 최적화 비교에 사용하지 않는다. 운영 전체 속도는 별도 같은 빌드 조건으로 확인해야 한다. 실제 앱의 개인 사진 확인은 사용자가 현재 화면을 새로고침하고 한 번 전환해 확인할 단계이며, 이번 프론트 수정만 반영하는 데 백엔드 재시작은 필요하지 않다.

## 개발 검사와 출력 계산 분리 · 실제 저금통 확인

이전 패널은 클릭 중 실행된 모든 모양 계산을 합쳤다. `body3DTiming.mjs`에 효과 실행 번호와 수명을 추가하고 `CustomJarBody3D.jsx`에서 각 준비·정리·모양 계산을 해당 실행에 연결했다. 최종 텍스처 render를 완료한 실행은 rendered, 그 전에 정리한 실행은 discarded로 구분한다. 정리된 실행의 늦은 콜백은 현재 결과에 기록하지 않는다. 효과별 준비 완료 표식도 분리해 폐기된 실행의 texturesReady가 최종 실행을 대신하지 않게 했다.

`LocalBody3DTimingPanel.jsx`에는 출력에 사용한 모양 계산과 폐기된 모양 계산을 나란히 표시한다. 기존 timingsMs 합계 필드는 유지하고, 숫자 허용 목록의 effectBreakdown을 추가했다. 최종 실행과 폐기 실행 각각에 테두리/사진 분할·높이·정점·바닥 계산도 표시한다. 구버전 결과는 분리값을 미측정으로 취급한다. 개인정보·네트워크 전송·의존성은 추가하지 않는다. 모양 계산 소스 `body3DMesh.mjs`는 변경하지 않았고 SHA-256도 이전과 같다. 백엔드·캐시·인증·DB·실제 앱의 StrictMode 설정은 이 단계에서 변경하지 않았다.

폐기된 실행에는 StrictMode 외에 다른 원인으로 재준비한 경우도 들어갈 수 있다. 따라서 실제 앱에서 discarded 숫자만 보고 전부 StrictMode라고 자동 판정하지 않는다. 같은 합성 사진·그리기 영역·배율·삼각형 조건의 진단 fixture에서만 strict-mode=1/0을 통제해 켠 경우 2회/폐기 1회, 끈 경우 1회/폐기 0회를 확인했다. [동작 확인 숫자](effect-split-check-2026-10-26.json), [합성 화면](effect-split-check-2026-10-26.png). 별도 탭의 순차 실행이라 로딩·JIT·기기 부하가 완전히 같지 않아 켜고 끈 두 값의 차이를 개선율로 사용하지 않는다. 두 화면의 오류·경고 로그는 0건이었다.

프론트 전체 Node 248개 테스트가 통과했고, 최종 완료 표식 분리 수정 후 관련 15개 테스트를 다시 통과했다. 폐기/출력 계산 분리, 늦은 콜백 거절, 클릭 취소, 중복/모호한 실행 번호 거절, 허용 목록 및 기존 모양 보존을 검증했다. 최종 운영 빌드가 성공했고 진단 표식이 JS 산출물에 없는 것을 확인했다. 기존 500kB 초과 번들 경고는 남아 있다. 백엔드를 수정하지 않아 이 단계에서 백엔드 테스트를 다시 실행하지 않았다.
