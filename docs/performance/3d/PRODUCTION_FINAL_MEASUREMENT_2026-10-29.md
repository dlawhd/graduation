### 보완 요청 당시의 절차

최종 버전은 그대로 유지한다. 같은 페이지·사진·창 크기·확대율에서 CPU·네트워크 제한을 없음으로 유지하고 스크린샷을 켠다. 새로고침 없이 먼저 녹화 밖에서 3D 사진 표시 → 2D 복귀를 한 번 진행해 반복 요청 준비를 맞춘다. 바로 새 녹화를 시작하고 `3D → 사진 표시 완료 → 2D`를 **3회만** 실행한 뒤 즉시 중지해 별도 `.json.gz`로 저장한다. 기존 `sisi.json.gz`는 덮어쓰지 않는다.

추가 기록을 합칠 경우 원래 6회의 누락값을 복원했다고 쓰지 않는다. **첫 파일의 반복 2회와 추가 파일의 반복 3회를 묶은 표본**이며, 파일·준비 실행·사이의 시간 차이를 함께 남긴다. 추가 기록에 실제 화면 표시가 남았는지 확인한 다음 과거 프론트 측정도 짧은 파일로 나누어 같은 준비 절차를 적용한다.

선택한 숫자·버전·한계는 [최종 운영 기록 숫자 요약](production-final-trace-summary-2026-10-29.json)에 보관했다. 사진과 원본 trace는 저장소에 복사하지 않았다. 앱 코드 변경 없이 기록 분석과 문서만 추가했으므로 앱 테스트·빌드는 이번 분석에서 다시 실행하지 않았다.

## 과거 원본 운영 시도와 최종 복구

최종 기록을 분석한 뒤, GitHub의 해당 커밋 Vercel 상태 링크와 실제 Vercel 소스를 대조했다. 과거 배포는 [6msHX2DfoxHLd4FZdju2EdzVsFRk](https://vercel.com/limjonghyeons-projects/graduation/6msHX2DfoxHLd4FZdju2EdzVsFRk), 소스는 `dd6e50b31ee9405f41a255152510367aa9d27cca`다. 해당 Production 배포를 Promote하고 `www.esjh.shop`의 Current 연결 및 실제 실행 파일 **`/assets/index-Cge89zpq.js`**를 확인했다. 백엔드·캐시 설정·DB·보안 정책은 이번 작업에서 변경하지 않았다.

로그인된 같은 `/jars/112`에서 3D로 전환하자 **“3D 사진을 불러오지 못했어요. 기존 2D로 보여드려요.”**가 표시되고 2D로 돌아왔다. 과거 소스의 이 문구는 사진 `Image.onerror`(브라우저의 사진 읽기 실패 처리)에서 나온다. 따라서 모양 계산이 끝났다는 이유만으로 정상 3D 전환이 완료됐다고 보지 않았으며, 실패한 전환 시간이나 운영 개선율을 만들지 않았다.

코드에서 확인한 차이는 과거 `CustomJarBody3D.jsx`가 `crossOrigin="anonymous"`로 기존 사진 URL을 직접 읽는 반면, 최종 버전은 `openTextureSource`를 통해 현재의 인증된 디자인 이미지 API를 사용한다는 점이다. **사진 읽기 실패 지점과 두 경로의 차이는 확인한 사실**이다. CORS(다른 사이트의 사진을 화면 계산에 사용해도 되는지 정하는 규칙), 서명 만료 또는 다른 네트워크 이유 중 무엇이 실제 요청을 거절했는지는 응답 증거가 없어 확정하지 않았다. 비교를 통과시키려고 S3 공개 범위나 CORS 정책을 완화하지 않았다.

실패 확인 후 최종 배포 **`7nxVGo78jVUA28rr3uDiyLBvTeTi` / `491ffa4`**를 다시 Promote했다. Vercel Current·운영 도메인과 새로고침 후 **`/assets/index-DQf0JCme.js`**를 확인했다. 복구된 운영 화면에서 실제 사진·테두리·입구 표시를 확인했고, 왼쪽 회전의 yaw 변화, 정면 복귀의 yaw·pitch 모두 0, 2D 복귀 시 canvas 0개, 재전환 후 사진 준비 상태가 끝나고 회전 버튼이 활성화되는 것까지 확인했다. 과거 원본의 운영 비교는 이 오류 때문에 중단된 상태이며, 최종 버전의 위 관측값은 그대로 유효한 별도 기록으로 유지한다.
