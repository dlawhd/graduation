# 테두리 계산 최적화 · 2026-10-26

## 확인한 문제

실제 여우 저금통의 출력에 사용한 모양 계산은 729.8ms였으며, 테두리 정점 생성 247.0ms와 표면 분할 225.7ms가 큰 구간이었다. 이 수치는 StrictMode의 폐기된 준비와 분리한 개발 실행 1건이다. [수정 전 실제 숫자](actual-effect-split-2026-10-26.json).

코드에서 다음 낭비를 확인했다.

- 여러 삼각형이 같은 테두리 점을 공유하지만, `face`가 경계 거리·높이를 다시 구하고 앞뒤 정점 문자열 키도 다시 만들었다.
- 분할 개선에서 변마다 인접 배열과 삼각형 객체를 만들었다. 삼각형이 바뀌지 않은 마지막 개선 패스의 연결 정보도 다음 분할이나 최종 경계를 찾을 때 다시 생성했다.

## 변경과 유지한 계약

`frontend/src/features/jarDesign/body3DMesh.mjs`를 수정했다.

1. 테두리 점 객체별 높이와 앞뒤 정점 번호를 한 번 계산하고 같은 모양 생성 안에서 재사용한다. `WeakMap`은 점 객체를 키로 삼는 임시 저장소다. 가까운 두 점을 반올림해 합치지 않으며 다른 저금통이나 다음 생성에 공유하지 않는다.
2. 삼각형 앞면 세 점 → 뒷면 세 점의 원래 등록 순서를 유지한다. 좁은 모서리에 보조 중심점을 넣는 조건과 순서도 유지한다. 임시 삼각형 배열은 줄였다.
3. 연결 정보를 변별 단일 기록으로 만들고 두 번째 인접 삼각형의 정점/번호만 추가한다. 변 방문 순서, 인접 개수 판정, 교체 순서, 기하 판정식은 같다. 한 패스 중에는 원래 연결 스냅샷을 사용하고, 삼각형이 바뀌면 다음 패스 전에 폐기한다.
4. 삼각형이 바뀌지 않았을 때만 연결 정보를 재사용한다. 분할/교체 후에는 반드시 무효화한다. 패스 내 사용 여부는 삼각형 번호별 `Uint8Array`로 기록한다.

분할 길이 기준, 최대 횟수, 삼각형 상한, 높이 계산식, 사진 배치/UV, 입구 높이, 바닥 절단, 빈 구멍과 앞뒤 재질은 바꾸지 않았다. 새 의존성, 영구 메모리 캐시, Worker, 해상도 축소는 추가하지 않았다. StrictMode도 그대로다. 백엔드·권한·S3·캐시·API/DTO/DB는 이번 단계에서 수정하지 않았다.

- 전체 프론트 Node 테스트 **252개**, 실패·취소·건너뜀 0. 운영 빌드 성공. 기존 500kB 초과 번들 경고는 남아 있다. 백엔드를 수정하지 않아 이 단계에서 백엔드 테스트를 재실행하지 않았다.

## 실제 저금통의 최적화 후 첫 전환·반복 전환

[최적화 후 사용자 전달 원본](actual-rim-after-2026-10-26.json)을 수정 전 [분리 측정 1건](actual-effect-split-2026-10-26.json)과 대조했다. 3건 모두 그리기 영역 380×380, 배율 1.25, 삼각형 18,308개, 준비 2회·폐기 1회·미결정 0회이며 render 반환 완료 기록이다. 사용자 실행 순서에 따라 첫 전환과 반복 전환을 구분했다. 완료 시각과 서버 요청 대응 정보는 없어 개별 API 캐시 HIT/MISS는 판정하지 않았다. 새로고침도 모든 다운로드/OS/S3 캐시를 비웠다는 뜻은 아니다.

출력용 모양 계산은 두 새 실행에서 264.7/266.6ms로 가까웠고, 목표로 수정한 테두리 분할과 정점 생성도 짧게 관찰됐다. 반복 검사에서 버리는 모양 계산까지 같은 최적화의 적용을 받는다. 두 실행의 분리값 합계가 기존 합계 필드와 일치하는 것도 검사했다.

다만 이 표를 평균·중앙값이나 보장된 개선율로 발표하지 않는다. 수정 전 분리 표본은 1건, 수정 후는 첫/반복 각 1건이다. 수정하지 않은 높이·바닥 계산과 사진 로딩도 달라 기기 부하·JIT·캐시 등의 영향이 섞였을 수 있다. 실제 전환 차이 전체나 계산 감소 약 64%를 이번 코드 변경만의 순수 효과로 귀속하지 않는다. 앞서 분리 계측 전 실제 1194.9ms도 관찰했고 별도 합성 화면에도 편차가 있으므로 가장 느린 2434.2ms만 기준 삼아 '전체 전환이 항상 50% 빨라졌다'고 주장하지 않는다.

현 단계의 결론은 **동일 입력을 번갈아 실행한 CPU 비교에서 계산 개선과 모양 보존을 확인했고, 실제 저금통의 새 첫/반복 전환에서도 약 265ms의 출력용 계산과 1.209/0.895초의 전체 전환을 확인했다**는 것이다. 이로써 이번 로컬 계산 최적화와 실제 상세 화면 재확인을 마쳤다. 운영 배포 후 성능·GPU 완료·모든 기기/사진의 성능 보장은 이번 검증에 포함하지 않았다.

이번 결과 수집에서는 소스 코드를 추가 변경하지 않았다. 직전 252개 테스트·빌드 결과와 비교 원본의 현재 모양 소스 해시가 계속 일치하는 것을 확인했으며, 테스트를 새로 실행한 것처럼 보고하지 않는다. 문서·숫자 기록만 추가했고 커밋·푸시·배포는 하지 않았다.
