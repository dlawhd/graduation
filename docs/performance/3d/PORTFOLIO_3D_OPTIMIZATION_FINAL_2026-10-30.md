# Memory Jar — 사진형 저금통의 2D→3D 전환 성능 개선

작성 기준: 2026-10-30. 포트폴리오에 사용할 최종 정리다. **로컬 반복 실험의 개선율**과 **운영 화면에서 관측한 감소율**을 구분한다. 자세한 실험 기록과 숫자 원본은 문서 끝의 근거 링크에서 확인할 수 있다.

## 1. 한눈에 보는 프로젝트와 성과

Memory Jar는 사용자가 사진과 직접 만든 외곽선으로 저금통을 꾸미고 추억을 공유하는 개인 프로젝트다. 이번 작업에서는 사진이 입혀진 저금통을 2D에서 3D로 전환할 때 발생하는 지연을 분석하고 개선했다.

- **담당:** 프론트·백엔드의 구간별 시간 계측, 3D 계산 최적화, 서버 이미지 캐시 구현, 기능·모양 보존 검증, 운영 프론트 비교.
- **관련 기술:** React, Three.js, Java, Spring Boot, MariaDB, AWS S3, Chrome DevTools Performance.
- **핵심 접근:** 사진 읽기·모양 계산·화면 그리기 준비를 나누어 측정하고, 확인한 반복 계산과 외부 이미지 읽기를 줄였다.

| 검증 환경과 항목 | 개선 전 | 최종 버전 | 시간 감소율 | 표본·완료 기준 |
| --- | ---: | ---: | ---: | --- |
| **로컬 고정 합성 입력의 반복 전환** | 3,242.95ms | 1,002.00ms | **69.10%** | 버전별 반복 10회 중앙값. 사진·테두리 준비 후 그리기 함수 반환 |
| **운영 프론트의 첫 기록 전환** | 1,188.020ms | 756.266ms | **36.34%** | 버전별 1회. 사진이 보인 최초 기록 캡처 |

로컬과 운영은 입력·환경·완료 기준·비교 범위가 다르므로 서로 빼거나 합산하지 않는다. 운영의 두 수치는 각 1회 관측의 감소율이다. 평균·중앙값 개선율이나 모든 사용자에게 보장되는 성능으로 표현하지 않는다.

## 2. 포트폴리오에 바로 넣을 짧은 소개

> **사진형 저금통의 3D 전환 지연을 구간별로 분석하고 개선했습니다.** 사진 읽기, 모양 계산, 화면 그리기 준비를 분리해 측정한 뒤, 공유 정점의 반복 계산과 삼각형 분할 과정의 임시 객체 생성을 줄였습니다. 백엔드에는 매 요청의 권한 검사를 유지하는 용량 제한 이미지 캐시를 구현했습니다. 같은 합성 입력의 로컬 버전 비교에서 반복 10회 중앙값이 3.243초에서 1.002초로 **69.10% 감소**했습니다. 운영 프론트 비교에서는 사진이 보인 최초 캡처 기준 첫 전환 **36.34%**, 반복 전환 **51.41% 감소**를 각각 1회 관측했습니다. 고정 입력의 모양 데이터 일치와 사진·입구 표시, 회전, 2D 복귀를 함께 검증했습니다.

위 소개와 함께 다음 측정 주석을 붙인다.

> 측정 범위: 로컬은 같은 합성 입력의 과거·최종 프론트와 백엔드를 분리된 시험 환경에서 비교했습니다. 운영은 과거 3D 계산에 현재 인증 이미지 읽기를 적용한 프론트와 최종 프론트를 비교했으며, 백엔드·서버 캐시·DB를 유지했습니다. 운영 수치는 각 버전의 첫 전환·반복 전환 각 1건이며 GPU 완료 시간이 아닙니다.

## 3. 문제 — 버튼을 눌러도 사진이 늦게 나타났다

저금통 상세 화면에서 ‘3D로 보기’를 누르면 사진이 입혀진 입체 저금통이 나타날 때까지 기다려야 했다. 이 기능은 사진 다운로드뿐 아니라 외곽선을 작은 삼각형으로 나누고, 각 점의 높이를 계산하고, 사진을 표면에 붙이는 준비를 거친다.

전체 시간만 확인해서는 어디를 먼저 고쳐야 할지 판단하기 어려웠다. 다음과 같이 실제 처리 흐름을 나누어 확인했다.

```text
3D 버튼 클릭
  → React 화면 준비와 3D 코드 로딩
  → 외곽선 분석·모양 계산·WebGL 준비
  → 인증 이미지 API 요청
      → 멤버 권한·현재 디자인 확인
      → 서버 캐시 확인 또는 S3 이미지 읽기
  → 사진 해석·표면에 붙일 텍스처 준비
  → 사진이 포함된 3D 화면 그리기
```

이 흐름은 이해를 위한 설명이다. 실제 처리에는 겹치는 구간이 있으므로 개별 시간을 모두 더해 전체 시간을 만들지 않았다.

## 4. 원인 — 같은 계산과 이미지 읽기를 반복했다

### 3D 모양을 만드는 계산

3D 표면은 여러 삼각형이 같은 정점, 즉 꼭짓점을 공유한다. 기존 코드에서는 같은 점을 다시 방문할 때 높이·좌표 변환·앞뒤 출력 번호를 반복해서 구하고 있었다. 표면을 나누는 과정에서도 삼각형의 연결 정보를 다시 만들고, 변을 표현하는 문자열과 잠깐 쓰는 배열·객체를 많이 생성했다.

바닥 처리에서는 바닥과 만나지 않는 면도 절단 검사와 임시 배열 생성을 거쳤다. 계측과 코드 대조를 통해 이러한 반복 작업을 개선 대상으로 정했다.

개발 모드에서는 React StrictMode가 화면 준비·정리를 다시 실행할 수도 있었다. 실행 번호를 붙여 **최종 출력에 사용한 계산**과 **정리되어 폐기된 준비 계산**을 구분했다. 폐기된 모든 작업을 자동으로 StrictMode 때문이라고 단정하지 않고, 실행 횟수와 비교 조건을 따로 확인했다.

### 서버 이미지 읽기

같은 저장 사진을 요청해도 S3 읽기가 다시 발생했다. DB 조회와 외부 이미지 읽기 시간을 나누어 확인하고, 저장된 PNG 바이트를 짧게 재사용하도록 서버 캐시를 추가했다. 캐시가 없는 첫 요청의 연결·SDK 준비 비용은 별도 구간으로 확인했다.

처음 연결이 느렸다는 관측만으로 TLS 설정을 변경하거나 별도의 예열 기능을 추가하지 않았다. 이번 성과에 ‘첫 연결 지연을 완전히 해결했다’는 주장은 포함하지 않는다.

## 5. 해결 — 계산 결과를 필요한 범위 안에서 재사용했다

| 개선 영역 | 실제 변경 | 적용 이유 |
| --- | --- | --- |
| 정점의 높이·출력 번호 | 같은 점의 결과를 한 번의 모양 생성 안에서 재사용 | 여러 삼각형이 공유하는 점의 중복 계산 감소 |
| 삼각형 연결 정보 | 연결이 유지될 때 재사용하고, 분할·변경 후 다시 생성 | 반복 조사를 줄이면서 오래된 연결 사용 방지 |
| 변을 나타내는 키 | 정점 번호 쌍을 충돌 없는 숫자로 표현 | 반복 문자열 생성 감소 |
| 분할 검사 | 세 변을 직접 확인하고 임시 배열·콜백 생성 감소 | 자주 실행되는 반복문의 준비 비용 감소 |
| 바닥 정점 | 좌표 변환과 출력 번호를 재사용하되 몸통·바닥의 표면 방향을 구분 | 같은 좌표 처리의 반복 감소와 기존 명암 유지 |
| 바닥 면 처리 | 절단이 필요한 면에 절단 절차 적용 | 바닥과 만나지 않는 면의 불필요한 처리 감소 |

계산 결과의 저장 범위는 **한 번의 모양 생성**으로 제한했다. 다른 저금통이나 변경된 윤곽에 이전 결과가 섞이지 않게 했다. 사진 배치·입구 위치·분할 품질을 유지하면서 계산량을 줄이는 방향으로 검증했다.

최종 추가 계산 개선의 주요 파일은 다음과 같다.

- [body3DMesh.mjs](../../../frontend/src/features/jarDesign/body3DMesh.mjs): 높이·정점 번호·연결 정보 재사용, 숫자 키와 분할 검사.
- [body3DBase.mjs](../../../frontend/src/features/jarDesign/body3DBase.mjs): 바닥 정점 처리 재사용과 필요한 면의 절단.
- [body-3d-benchmark.mjs](../../../frontend/tests/body-3d-benchmark.mjs): 과거·현재 계산 구현을 같은 입력으로 비교하는 시험.

최종 운영 프론트 소스는 [`491ffa4`](https://github.com/dlawhd/graduation/commit/491ffa41b1f68266fcc26fce8f8bc180f7ff1628)다. 이 커밋은 앞선 개선이 포함된 `8a5f7cc` 위에 계산 파일 두 개의 추가 최적화를 적용한 버전이다. 전체 개선을 이 마지막 커밋 하나에서 모두 구현했다고 설명하지 않는다.

## 6. 서버 이미지 캐시는 어떻게 구현했나?

캐시는 **같은 사진을 잠시 기억해 두는 서버 메모리 저장소**다. 브라우저 저장이나 Redis·CDN 캐시를 새로 도입한 방식은 아니다.

```text
요청마다 로그인·활성 멤버 권한·현재 디자인 키 확인
  → 짧은 DB 트랜잭션 종료
  → 서버 메모리 캐시 조회
      → 유효한 항목 있음: 저장된 PNG의 복사본 반환
      → 없음: S3 읽기·PNG/크기 검증·스트림 닫기 후 저장
```

| 항목 | 구현 내용 |
| --- | --- |
| 키 | 서버가 DB에서 확인한 `(bucket, objectKey)` |
| 만료 | 저장 후 60초. 읽어도 만료 시각을 연장하지 않음 |
| 저장 상한 | 이미지 1개 최대 4MiB, 저장 바이트 합계 최대 16MiB, 최대 64개 |
| 상한 초과 | 최근에 쓰지 않은 항목부터 제거. 4MiB 초과~기존 허용 16MiB 이미지는 정상 반환하되 저장하지 않음 |
| 같은 사진의 동시 요청 | 진행 중 읽기를 `CompletableFuture`로 공유. 공유 대상은 동시에 최대 8개 객체 |
| 잠금 범위 | 짧은 맵 접근에만 사용. S3 읽기와 응답 대기는 잠금 밖에서 수행 |
| 실패 | 잘못된 PNG·실패 응답은 저장하지 않음. 한 대기자의 중단이 다른 요청의 원본 읽기를 취소하지 않음 |
| 응답 보호 | 캐시 원본과 분리한 배열 복사본 반환 |
| 정리 | 요청 시 만료 확인, 15초 주기 만료 정리, 종료 시 저장 항목 해제 |

캐시에 사진이 있어도 매 요청의 권한·현재 디자인 조회를 수행한다. API 응답의 `Cache-Control: no-store`도 유지한다. 새 디자인은 새 객체 키로 구분하지만, 같은 S3 키를 외부에서 덮어쓰거나 삭제하면 최대 유효 기간 동안 이전 바이트가 반환될 수 있다. 서버 인스턴스별 메모리이므로 재시작 후에는 비어 있고 여러 서버가 공유하지 않는다.

16MiB는 **저장한 이미지 바이트 합계의 상한**이다. 진행 중 다운로드·응답 복사본·메타데이터까지 포함한 서버 전체 메모리 상한을 뜻하지 않는다.

## 7. 검증 — 속도와 정상 동작을 함께 확인했다

### 로컬: 같은 입력의 반복 비교

과거 `dd6e50b`와 최종 수정본을 분리된 로컬 환경에서 실행했다. 각 버전은 별도 시험 DB를 사용하고, 같은 480×480 합성 PNG·53점 윤곽·사진 배치·입구를 적용했다. 실제 AWS 대신 고정 합성 이미지를 제공하는 로컬 시험 서버를 사용했다.

과거→최종→최종→과거 순서로 각 묶음 6회, **총 24회** 전환했다. 버전별 12회 중 묶음마다 첫 전환을 제외한 **반복 10회의 중앙값**을 비교했다. 두 순서 묶음 모두 최종 버전의 시간이 짧았다.

| 로컬 반복 관측 | 과거 | 최종 | 시간 감소율 |
| --- | ---: | ---: | ---: |
| 묶음 1의 5회 중앙값 | 3,128.50ms | 992.90ms | 68.26% |
| 역순 묶음 2의 5회 중앙값 | 3,429.10ms | 1,002.30ms | 70.77% |
| **반복 10회 전체 중앙값** | **3,242.95ms** | **1,002.00ms** | **69.10%** |

이 실험에서는 과거·최종 백엔드와 서버 캐시 상태도 각 버전에 맞춰 달랐다. 따라서 69.10%는 해당 로컬 버전 비교 결과로 사용한다. 운영 프론트만의 개선율이나 순수 모양 계산만의 개선율로 바꾸지 않는다.

### 모양 보존과 기능

- 같은 합성 입력의 두 버전 모두 정점 14,196개·삼각형 28,160개였다.
- 좌표·법선(빛을 받을 방향)·UV(사진을 붙일 좌표)·삼각형 연결·재질 그룹이 바이트 단위로 일치했다.
- 최종 계산 수정 단계의 전체 프론트 시험 252개와 빌드가 통과했다. 관련 고정 모양·바닥 보존 검사도 포함한다.
- 로컬 직접 비교에서는 앱 시작·로그인·같은 저금통 조회와 실제 HTTP·권한·캐시 30항목을 검증했다.
- 실제 화면의 사진·테두리·입구, 좌우 회전, 정면 복귀, 2D 복귀와 재진입을 확인했다.
- 운영 비교용 과거 프론트의 사진 읽기 호환 수정은 별도로 시험 172개와 빌드를 통과했다. 두 단계의 시험 수를 더해 하나의 전체 시험 수로 발표하지 않는다.

위 결과는 해당 수정·실험 단계의 검증 이력이다. 이 포트폴리오 문서를 작성하면서 모든 앱 시험을 새로 실행한 결과는 아니다.

## 8. 운영: 실제 사진 표시까지의 시간 비교

옛 백엔드는 현재 운영 데이터 일부와 호환되지 않았다. 운영에서는 현재 백엔드·캐시·DB를 유지하고, **옛 3D 계산에 현재 인증 이미지 읽기를 적용한 프론트**와 최종 프론트를 비교했다. 원본 과거 백엔드 전체를 운영에 되돌린 시험은 아니다.

사용자가 제공한 Chrome 성능 기록 `qqq`와 `www`에서 같은 저금통 112와 그림을 대조했다. 클릭 처리 시작부터 **사진이 보인 최초 기록 캡처**까지를 관측했다. 사진이 없는 흰 입체 표면과 전환 직후 남아 있는 2D 그림은 완료로 세지 않았다.

| 운영 관측 | 과거 호환 프론트 | 최종 프론트 | 줄어든 시간 | 감소율 |
| --- | ---: | ---: | ---: | ---: |
| 첫 기록 전환 | 1,188.020ms | 756.266ms | 431.754ms | **36.34%** |
| 반복 전환 | 750.075ms | 364.465ms | 385.610ms | **51.41%** |

같은 Chrome 프로세스·주 실행 스레드, metadata의 hostDPR 1.125, 저장 캡처 크기 350×498을 확인했다. 두 기록의 저금통은 전체가 화면 안에 보였고 표시 크기도 비슷했다. 캡처의 세로 위치에는 15~17px 차이가 있었다. 실제 viewport·canvas 크기·CPU/네트워크 제한과 사진 원본 바이트의 동일성은 기록만으로 독립 검증하지 않았다.

**표본은 각 버전의 첫 전환·반복 전환 각각 1건**이다. 이 범위에서 시간 감소를 관측했다고 설명한다. GPU 완료 시간이나 엄격히 통제한 여러 번의 평균 성능으로 표현하지 않는다. 같은 날짜의 두 파일로 계산한 결과이며 다른 날의 운영 기록이나 로컬 숫자를 섞지 않았다.

과거 측정 후 최종 배포 `7nxVGo78jVUA28rr3uDiyLBvTeTi`로 복구하고 소스·운영 실행 파일·사진 표시·회전·2D 복귀를 확인한 뒤 최종 기록을 받았다. 상세 캡처 경계와 버전 대조는 [운영 프론트 비교 결과](PRODUCTION_FRONTEND_COMPARISON_2026-10-30.md)에 있다.

## 9. 감소율을 계산하고 설명하는 기준

```text
시간 감소율(%) = (개선 전 시간 − 개선 후 시간) ÷ 개선 전 시간 × 100

로컬 반복 중앙값: (3242.95 − 1002.00) ÷ 3242.95 × 100 = 69.10%
운영 첫 전환:     (1188.020 − 756.266) ÷ 1188.020 × 100 = 36.34%
운영 반복 전환:   (750.075 − 364.465) ÷ 750.075 × 100 = 51.41%
```

계산은 반올림 전 ms 값으로 하고, 결과를 소수점 둘째 자리까지 표시했다. 이 값은 **걸린 시간의 감소율**이다. 처리량 증가율과 구분한다. 각 실험의 감소율을 더하거나, 서로 다른 환경의 절대 시간을 빼서 새 성과를 만들지 않는다.

## 10. 면접에서 설명할 핵심

**왜 바로 최적화하지 않고 시간을 나누었나요?**

사진 응답이 느린지, 3D 계산이 느린지에 따라 해결 방법이 달라지기 때문입니다. 개발 모드의 폐기된 준비 작업도 구분해 실제 출력에 쓰인 비용을 확인했습니다.

**캐시를 넣으면 첫 요청도 빨라지나요?**

캐시에 없는 첫 요청은 S3 읽기와 필요한 준비를 수행합니다. 캐시는 같은 객체의 반복 읽기를 줄이는 방법이고, 첫 연결 준비 비용은 별도로 봤습니다. 적중 여부를 확인하지 않은 운영 trace만으로 서버 캐시 효과를 수치화하지 않았습니다.

**69.10%와 51.41% 중 어느 수치를 말해야 하나요?**

환경과 표본을 같이 설명합니다. 69.10%는 같은 합성 입력의 로컬 반복 10회 중앙값입니다. 51.41%는 현재 백엔드를 유지한 운영 프론트 비교에서 각 버전의 반복 전환을 1회씩 관측한 감소율입니다.

**과거 코드를 그대로 운영에 올리지 않은 이유는 무엇인가요?**

옛 백엔드가 현재 저장 형식 일부와 호환되지 않았고, 과거 프론트의 사진 읽기도 현재 서버와 맞지 않았습니다. 운영 데이터와 권한 정책을 유지하면서 비교하기 위해 이미지 읽기만 현재 인증 방식에 맞췄습니다. 이 비교 범위를 결과에 명시했습니다.

**빨라지는 대신 모양이 달라지지 않았나요?**

고정 입력에서 좌표·법선·사진 좌표·삼각형 연결·재질 그룹의 일치를 확인했습니다. 사진·입구 위치, 회전과 2D 복귀도 실제 화면에서 검증했습니다. 확인한 고정 입력과 기능 범위로 설명합니다.
