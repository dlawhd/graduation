# 저금통 3D 전환, 왜 느렸고 지금 어디까지 고쳤을까?

작성 기준: 2026년 10월 25일, 로컬 개발 환경에서 진행한 측정과 변경.

이 문서는 처음 속도 측정을 요청한 때부터 현재까지의 과정을 쉽게 설명한다.
세부 측정값 전체를 다시 복사하지 않고, 필요한 곳에서 [상세 측정 기록](README.md)과 원시 자료를 연결했다.
새로 읽는 사람은 이 문서부터, 같은 실험을 다시 할 개발자는 상세 측정 기록부터 읽으면 된다.

## 1. 시작은 “3D로 바뀔 때 왜 기다려야 하지?”였다

처음 요청은 다음과 같았다.

> 저금통을 만들고 자세히 보기에서 3D 보기를 누르면 2D에서 3D로 바뀔 때 느리다. 개선하기 전에 지금 속도부터 측정하자.

그때는 어디에서 시간이 걸리는지 몰랐다. 사진을 가져오는 것이 느릴 수도 있고, 입체 모양을 계산하는 것이 느릴 수도 있었다.

그래서 한꺼번에 “3D가 느리다”라고 판단하지 않고, 기다리는 시간을 나누기로 했다.
음식 배달이 늦을 때 주문 접수, 요리, 배달 중 어느 단계가 늦는지 따로 확인하는 것과 같다.

## 2. 3D 버튼을 누르면 어떤 일이 생길까?

우리 서비스에는 크게 두 쪽의 일이 있다.

- 프론트엔드(브라우저에서 화면을 만드는 부분): 저금통의 입체 모양을 계산하고 사진을 입힌 뒤 그릴 준비를 한다.
- 백엔드(서버에서 데이터를 확인하고 전달하는 부분): 요청한 사람이 사진을 볼 수 있는지 검사하고 필요한 이미지를 가져온다.

서버는 DB(회원·저금통 정보를 보관하는 곳)에서 권한과 디자인을 확인한다.
사진이 필요하면 S3(AWS의 파일 보관 서비스)에서 이미지 파일을 읽는다.

즉, 화면을 만드는 일과 사진을 준비하는 일이 함께 필요하다. 일부 작업은 겹쳐 진행될 수 있다.
그러므로 각 단계의 숫자를 무조건 모두 더하면 안 된다.

또한 “서버가 사진을 보내는 데 걸린 시간”과 “사용자가 완성된 3D 화면을 보기까지 걸린 시간”은 다르다.
서버가 빨라져도 브라우저 계산이 오래 걸리면 사용자는 계속 기다릴 수 있다.

## 3. 먼저 측정기를 만들고, 변경 전 상태를 남겼다

계측(작업의 시작과 끝 시간을 재는 것) 코드를 추가해 사진 로딩, 모양 계산, 화면 그리기 준비를 나눠 봤다.
또한 개선 전 결과와 화면을 보관했다. 나중에 느낌이 아니라 숫자로 비교하기 위해서다.

초기 시험에는 실제 개인 사진 대신 시험용 합성 이미지를 사용했다.
사용자가 제공한 사진형 저금통의 표시 윤곽도 시험 입력에 반영했지만, 얼굴 사진 자체를 저장소에 넣지는 않았다.
만들기 쪽 조건과 상세 보기 쪽 조건을 구분하는 로컬 진단 화면도 마련했다.
이것이 실제 운영에서 모든 만들기/상세 화면을 측정했다는 뜻은 아니다.

기록의 완료 기준은 브라우저의 그리기 함수가 반환한 시점이다.
GPU(화면 그림 계산을 맡는 장치)가 모든 처리를 끝냈거나 모니터에 표시를 마친 시각까지 측정한 것은 아니다.

자료: [변경 전 측정 환경](README.md), [변경 전 화면](before-optimization-2026-10-25.jpg).

## 4. 브라우저의 같은 계산을 반복하는 부분을 줄였다

3D 저금통은 작은 점과 삼각형을 많이 연결해서 만든다.
그런데 여러 삼각형이 같은 점을 사용해도, 그 점의 높이를 반복해서 계산하는 부분이 있었다.

이를 “한 번 계산한 점의 높이는 같은 사진 면을 만드는 동안 다시 사용하기”로 바꿨다.
같은 수학 문제의 답을 이미 구했는데 옆 문제에서 또 계산하던 일을 줄인 것이다.

사진의 해상도를 낮추거나 삼각형을 줄여서 빨리 보이게 만든 것은 아니다.
기존 모양 15개에 대해 좌표, 사진 배치에 쓰는 값, 삼각형 연결 정보가 이전과 같은지도 검사했다.

다만 결과는 모양마다 달랐다.
불규칙한 모양과 깊게 굴곡진 모양은 전체 계산이 짧아졌지만, 둥근 기본 모양은 한 비교에서 오히려 느려졌다.
따라서 “모든 3D 계산 최적화 완료”라고 결론 내리지 않았다. 이 편차는 아직 재검증 대상이다.

자료: [프론트 계산 변경과 조건별 결과](README.md), [CPU 계산 비교 원시 자료](cpu-comparison-2026-10-25.json), [변경 후 합성 화면](after-optimization-2026-10-25.jpg).
두 화면 사진은 표시 상태도 다르므로, 사진 두 장만으로 모양 보존이나 최종 개선율을 판단하지 않는다.

## 5. 실제 사진 요청을 보니, 서버 쪽도 따로 확인해야 했다

합성 사진은 인터넷의 실제 이미지 요청을 그대로 재현하지 않는다.
그래서 운영 화면과 로컬 화면에서 브라우저 개발자 도구의 Timing(요청에 걸린 시간표)을 확인했다.

운영은 실제 사용 중인 사이트이고, 로컬은 개발자 컴퓨터에서 실행하는 환경이다.
서로 다른 환경·사진·저금통에서 잰 숫자는 그대로 개선 전후 비교로 쓰면 안 된다.

처음에는 응답을 기다리는 시간이 크다는 것만 알 수 있었다.
이 기다림 안에 DB 조회, S3 읽기, 네트워크 중 무엇이 들어 있는지는 브라우저 시간표만으로 알 수 없었다.

그래서 로컬 서버 안에 DB 확인, S3 응답 시작, 이미지 전체 읽기를 나누는 측정기를 추가했다.
사진 계측은 로컬에서 명시적으로 켤 때만 동작하고, 운영 프로필에서는 켜지지 않도록 했다.

쿠키·토큰은 로그인 열쇠에 해당한다. 실제 값이 보이는 캡처는 측정 자료로 저장하거나 커밋하지 않았다.
진단 기록에도 개인 사진, 사용자 번호, 사진 보관 주소와 로그인 열쇠를 남기지 않도록 했다.

## 6. 반복 다운로드를 줄이는 캐시를 만들었다

측정 결과, 반복 요청에서도 S3에서 같은 사진을 다시 읽는 비용이 눈에 띄었다.
그래서 캐시(한 번 가져온 결과를 잠시 보관해 다시 쓰는 장치)를 추가했다.

사진 창고에 갈 때마다 같은 상자를 가져오는 대신, 최근에 가져온 상자를 작업대에 잠시 올려 두는 것과 같다.

현재 캐시는 다음처럼 동작한다.

1. 요청할 때마다 로그인 상태와 저금통 멤버 권한, 현재 디자인을 먼저 확인한다.
2. 보관 중인 같은 이미지가 있으면 복사본을 반환한다.
3. 없거나 만료됐으면 S3에서 읽고 이미지 검증을 마친 뒤 잠시 보관한다.
4. 같은 이미지 요청이 동시에 들어오면 진행 중인 다운로드를 함께 기다릴 수 있게 한다.

보관 시간은 저장 후 60초이며, 중간에 사용해도 시간이 연장되지 않는다.
이미지 한 개는 약 4MB, 저장된 이미지 합계는 약 16MB, 최대 64개로 제한한다.
이 합계는 캐시에 보관된 이미지 크기이지 서버 전체 메모리 사용량의 상한은 아니다.
더 큰 허용 이미지는 정상 전달하되 캐시에 넣지 않으며, 실패한 다운로드도 보관하지 않는다.

사진을 볼 권한이 없는 사람에게 캐시를 먼저 주는 구조가 아니다.
또한 이것은 서버 메모리의 보관함이다. 브라우저 저장 정책을 풀거나 사진을 공개 파일로 바꾼 것이 아니다.

실제 반복 요청 비교에서 서버 이미지 API(사진을 요청하는 창구)의 중앙값은 약 **270ms에서 41ms**로 줄었다.
ms(밀리초)는 1,000개가 모이면 1초다. 중앙값은 숫자를 정렬했을 때 가운데 값이다.
이 결과는 **반복 이미지 API가 약 85% 짧아졌다는 뜻이지, 3D 화면 전체가 85% 빨라졌다는 뜻은 아니다.**
전후 표본 수도 달라 그 차이와 보조 비교를 상세 자료에 함께 남겼다.

## 7. “처음만 느린 건 당연하지?”를 확인했다

맞다. 캐시에 아직 사진이 없는 첫 요청은 창고에서 가져와야 한다.
캐시가 잘 동작한다고 해서 첫 방문의 기다림까지 해결된 것은 아니다.

그래서 재시작 직후 첫 요청, 바로 이어진 요청, 60초 넘게 기다려 캐시가 만료된 요청을 구분했다.
같은 서버 실행 안에서도 “처음 가져오기”와 “한 번 사용한 뒤 다시 가져오기”는 조건이 다를 수 있었다.

사용자가 말한 전환 횟수와 서버가 받은 요청 수가 다른 경우도 있었다.
그때는 유리한 숫자만 골라내지 않고 실제 기록 전체와 차이를 남겼다.
진단에 저금통 번호를 저장하지 않으므로 추가 요청의 원인을 마음대로 추측하지도 않았다.

S3용 SDK(AWS와 통신하는 프로그램 도구)의 숫자도 추가로 확인했다.
AWS 통신에 필요한 인증정보 준비는 이번 측정들에서 매우 짧았고, 이때 관찰한 실제 S3 요청에 재시도도 없었다.

여기서 중요한 해석도 정정했다.
기존 ‘연결 획득’이라는 이름의 지표는 현재 라이브러리에서 연결 풀(다시 쓸 연결을 관리하는 보관함)의 객체를 빌리는 시간이었다.
실제 연결을 새로 맺는 과정 전체가 아니었다. 따라서 그 숫자만 보고 “TLS는 빨랐다”고 말할 수 없었다.

## 8. 실제 연결 준비와 응답 대기를 나눠 봤다

다음에는 원래 통신 방식을 유지하면서 실제 연결 수립, 요청 송신, 송신 후 응답 헤더 수신을 따로 관찰했다.
헤더는 본문 사진 앞에 오는 응답 상태·형식 같은 안내 정보다.

새 관찰자는 SDK 내부 구조 일부에 의존하는 로컬 진단 전용 코드다.
지원 구조가 달라지면 일부만 측정하고 넘어가지 않고 로컬 시작 때 알린다.
운영에서는 설치하지 않으며, 캐시 기능과 달리 진단이 끝난 뒤 꺼둘 수 있다.

2026년 10월 25일 17:41 KST에 사용자가 수행한 새 계측의 첫 이미지 요청 결과는 다음과 같다.

| 구간 | 쉬운 설명 | 관찰 시간 |
| --- | --- | ---: |
| 서버 처리 전체 | 서버가 요청을 받아 응답 처리를 마칠 때까지 | 약 985ms |
| 실제 연결 준비 | S3와 통신할 길을 준비하는 과정 | 약 463ms |
| 요청 송신 | 사진을 달라는 요청을 보내는 과정 | 약 2.9ms |
| 송신 후 응답 헤더 수신 | 보낸 뒤 응답 안내를 기다리고 해석하는 과정 | 약 102ms |
| 이미지 전체 읽기 | 응답의 사진 데이터를 모두 읽는 과정 | 약 62ms |
| DB 처리 | 권한과 현재 디자인을 확인하는 과정 | 약 17ms |
| AWS 인증정보 준비 | AWS 통신에 사용할 인증정보를 얻는 과정 | 약 0.10ms |

서버 전체 행 안에 다른 행들이 포함된다. 표에 없는 추가 준비·처리 시간도 있다.
이 숫자를 무조건 모두 더하거나, 서로 다른 실험의 시간을 더해 실제 화면 전환 시간을 만들면 안 된다.

이번 요청에서 가장 큰 관찰 구간은 연결 준비였다. 전체 서버 시간의 약 47%였다.
요청은 정상 응답했고 재시도는 없었다.

하지만 연결 준비에는 아래 작업이 함께 들어 있다.

- DNS(서버 이름을 실제 접속 주소로 찾는 작업)
- TCP(데이터를 주고받을 연결을 맺는 작업)
- TLS(HTTPS의 보안 연결을 준비하고 인증서를 확인하는 작업)
- 이 작업 도중 필요한 프로그램의 초기 실행 준비

따라서 **연결 준비가 컸다는 것은 확인했지만, TLS 하나가 원인이라고 확정한 것은 아니다.**
송신 후 대기도 네트워크와 헤더 해석을 포함하므로 순수 S3 서버 처리 시간이라고 부르지 않는다.
기존 TLS 인증서·호스트 이름 검증을 끄고 얻은 결과도 아니다.

## 9. “아까 1.6초보다 빨라진 것 아닌가?”의 정확한 답

이번 서버 관찰값이 앞선 약 1.6초보다 짧았다는 것은 맞다.
약 0.6초 차이이고, 비율로는 약 38%다.

다만 이 단계에서 추가한 것은 속도를 높이는 코드가 아니라 측정 코드였다.
각각 한 번 잰 값이므로 연결 상태와 초기 실행의 차이로 달라졌을 수도 있다.

그래서 두 가지를 구분한다.

- 확인된 개선: 캐시를 사용한 반복 요청에서는 S3 다운로드를 생략해 API 시간이 줄었다.
- 아직 보장하지 못한 개선: 첫 요청이 언제나 38% 빨라졌다는 주장.

또한 이 985ms는 서버 이미지 API 시간이다. 사용자의 실제 3D 전환 전체 시간은 아니다.

## 10. 무엇을 검사했고, 지금 무엇이 남았을까?

변경한 코드가 기존 기능을 망가뜨리지 않는지도 확인했다.

- 프론트엔드 Node 테스트 242개 통과. 이 안에 기존 15개 모양의 보존 검사도 포함된다.
- 관련 백엔드 테스트 83개 통과. 전체 백엔드 테스트를 모두 실행한 수치가 아니라 이번 기능과 연결된 검사 수다.
- 프론트엔드 운영용 빌드와 백엔드 bootJar(실행 파일을 묶는 빌드) 성공.
- 잘못된 입력·권한 없는 접근·실패 이미지·캐시 만료·동시 요청·기존 응답 형식을 검사했다.
- 시험 서버와 임시 인증서로 인증서 신뢰 거절, 올바른 시험 신뢰 통과, 호스트 이름 불일치 거절을 확인했다. 실제 AWS 계정/사진을 이용한 보안 시험과는 구분한다.

기존 프론트엔드의 큰 번들(브라우저가 받는 프로그램 묶음) 경고는 남아 있다.
모양이 같다는 테스트 통과와 모든 조건에서 더 빠르다는 보장은 서로 다르다.
전체 검사 명령과 한계는 [상세 측정 기록](README.md)에 남겼다.

현재 상태를 한 문장으로 정리하면 다음과 같다.

> 같은 사진을 반복해서 가져오는 비용은 캐시로 줄였고, 첫 요청에서는 실제 연결 준비가 큰 구간임을 확인했다. 그러나 첫 연결의 세부 원인과 실제 3D 전환 전체의 개선까지 완료한 것은 아니다.

앞으로 남은 일은 순서대로 다음과 같다.

1. 연결 준비 안의 DNS·TCP·TLS·초기 실행 비용을 안전하게 더 구분할 수 있는지 확인한다. 연결 밖에 남은 준비/해석 비용도 살펴본다.
2. 확인된 원인에 맞는 최소 변경을 적용한다. 이유를 모른 채 인증서 검증을 끄거나 캐시 크기를 늘리지 않는다.
3. 같은 사진·저금통·화면 조건으로 첫 요청과 반복 요청을 따로 검증한다.
4. 브라우저의 계산 편차와 실제 2D→3D 전체 전환을 함께 재확인한다. 필요할 때 GPU 완료 시간도 추가로 확인한다.

## 11. 자료 보관과 배포는 어떻게 구분할까?

이 폴더에는 쉬운 설명, 세부 측정 방법, 숫자 원본, 합성 화면만 나누어 보관한다.
개인 사진과 인증 쿠키 캡처, 설치 폴더와 빌드 산출물은 이번 커밋 대상이 아니다.

사용자는 이 정리와 관련 변경의 main 커밋·푸시를 요청했고, 기존 자동배포가 시작될 수 있다는 안내 후 main 푸시를 선택했다.
현재 저장소에서는 main 푸시 뒤 백엔드 전체 테스트와 이미지 게시가 성공하면 운영 배포 작업으로 이어질 수 있다.

**커밋·푸시 완료, 자동배포 시작, 운영 배포 성공, 운영에서의 성능 확인은 각각 별개의 상태다.**
이 문서의 로컬 측정값을 운영 배포 후 성능이라고 바꿔 부르지 않는다.
