# 과거 3D 버전의 사진 읽기 호환 수정

2026-10-30 기준 **로컬 기능 검증과 빌드 완료, 운영 확인 전**이다. 이 문서는 속도 개선 결과가 아니라, 비교에 사용할 과거 화면이 현재 서버에서 사진을 읽을 수 있도록 준비한 기록이다.

## 문제: 과거 화면이 현재 사진을 읽지 못했다

과거 프론트 `dd6e50b31ee9405f41a255152510367aa9d27cca`를 운영에 잠시 적용했을 때, 저금통 112에서 “3D 사진을 불러오지 못했어요. 기존 2D로 보여드려요.”가 나타났다. 사진이 표시되지 않은 실행은 정상 전환 시간으로 집계하지 않았다. 이후 최종 배포 `7nxVGo78jVUA28rr3uDiyLBvTeTi`로 복구했다.

과거 코드는 사진 주소를 `Image.src`에 직접 넣었다. 현재 코드는 로그인과 저금통 멤버 권한을 검사하는 이미지 API에서 PNG를 받은 뒤, 브라우저 안에서만 쓰는 임시 주소로 읽는다. **두 버전의 읽기 방식이 다르다는 것은 코드로 확인했지만, 당시 직접 읽기 실패가 CORS·주소 만료 중 무엇 때문인지는 확정하지 않았다.**

## 해결: 사진을 가져오는 부분만 현재 방식에 맞췄다

비교용 버전의 기준 코드는 `dd6e50b`다. 현재 최종 프론트 `491ffa41b1f68266fcc26fce8f8bc180f7ff1628`의 이미지 읽기 함수를 재사용했다.

1. 상세 디자인 응답의 `imageTextureUrl`·`bodyArtworkTextureUrl`을 기존 컴포넌트 순서로 전달한다.
2. 기존 `apiClient`로 사진과 테두리를 읽는다. 기존 로그인 쿠키·세션 갱신·서버 권한 검사를 사용한다.
3. 허용된 `/api/v1/jars/{양의 정수}/design/texture?part=IMAGE|BODY` 경로만 읽는다. 임의 외부 주소에 인증 요청을 보내지 않는다.
4. 비어 있거나 PNG가 아니거나 16MiB를 넘는 응답은 거절한다. 요청 제한 시간은 현재 프론트와 같은 15초다.
5. 2D 복귀·사진 변경·실패 때 진행 중 요청을 취소하고 임시 주소를 해제한다. 늦은 응답이 이전 화면을 덮지 못하게 기존 버전 검사와 정리 상태를 확인한다.

권한 오류가 나면 S3 주소로 다시 시도하지 않고 기존 오류 안내와 2D 복귀를 사용한다. API 경로 필드가 없는 기존 서버 응답이나 작성 중 사진은 원래 주소를 읽는 기존 동작을 유지한다.

## 그대로 둔 부분과 비교의 의미

옛 3D 모양 계산·표면 분할·정점 생성·사진 배치·입구 표시·그리기 품질을 유지했다. 다음 파일은 `dd6e50b`와 줄바꿈을 정규화한 SHA-256 및 내용이 같다.

- `body3DBase.mjs`, `body3DMesh.mjs`, `body3DGeometry.mjs`, `body3DPhoto.mjs`
- `bodyArtworkPixels.mjs`, `customJarBody.mjs`, `components/JarSlotOverlay.jsx`
- 기존 `apiClient.js`, `package.json`, `package-lock.json`

`CustomJarBody3D.jsx` 내부의 `draw()` 함수도 과거와 같다. 원래 추적 중인 파일의 변경은 아래 컴포넌트 4개뿐이다. 백엔드·서버 캐시·DB·권한·S3 정책은 이번 수정으로 바꾸지 않았다. 새 의존성도 추가하지 않았다.

따라서 이후 비교의 이름은 **“과거 3D 계산 + 현재 인증 이미지 읽기”와 “최종 프론트”의 비교**다. 과거 프론트·백엔드·캐시 전체를 그대로 재현한 운영 비교라고 설명하지 않는다. 양쪽 이미지 읽기 경로를 맞추므로 이미지 접근 방식 자체의 개선율을 이 비교로 주장하지 않는다.

## 검증 결과

**Node 시험 172개 전부 통과**했다. 기존 166개와 새 호환 시험 6개이며 실패·취소·건너뜀은 0개다. 전체 시험 명령은 저장소 루트에서 다음과 같다.

```powershell
$legacyTests = @(rg --files frontend/src frontend/tests -g '*.test.mjs')
node --test @legacyTests
```

`frontend`에서 운영 API 주소를 지정한 `npm run build`도 통과했다. 655개 모듈을 처리했으며 기존 대용량 청크 경고는 남아 있다. 로컬 빌드의 진입 파일은 `index-BSmtQ3XR.js`, 3D 청크는 `CustomJarBody3D-BubbEUIo.js`다. 이 파일명을 아직 만들지 않은 Vercel 산출물의 파일명으로 사용하지 않는다. 개발 검증 화면의 문구·합성 사진은 실행용 JS 청크에 포함되지 않았다.

브라우저에서는 고정된 합성 사진과 네 가지 응답 상황을 사용했다. 실제 상세 컴포넌트·prop 전달·WebGL은 실행하고, API 응답만 로컬 시험 어댑터로 대체했다. 회원·사진·S3에 접근하지 않았으며 이 화면의 실행 시간을 성능값으로 사용하지 않는다.

| 확인 항목 | 관측 결과 |
| --- | --- |
| 정상 사진·다색 테두리 | IMAGE/BODY 각각 200, 실제 3D 사진과 테두리 표시 |
| 왼쪽 회전 | yaw 0.35 → 약 0.05, 이미지 재요청 없음 |
| 정면 복귀 | yaw·pitch 모두 0 |
| 2D 복귀 | 3D canvas 0개, 활성 임시 주소 0개 |

| 잘못된 이미지 타입 | 오류 안내 후 2D, 활성 임시 주소 0개 |
| 응답 대기 중 2D 복귀 | IMAGE/BODY 모두 취소됨 |
| 취소 후 늦은 응답 완료 시도 | 2D 유지, canvas·임시 주소 모두 0개 |
| 오류·취소 뒤 정상 재진입 | 다시 사진·테두리 표시, 마지막 2D 복귀 때 자원 해제 |

단위 시험에서는 401·403·404·500, 외부 주소·경로 탈출·잘못된 번호·추가 쿼리, 빈 이미지·타입 오류·용량 상한, 중복 해제와 늦은 응답도 확인했다. 서버 권한 검사 자체를 새로 구현한 것이 아니므로 실제 운영 권한 검증을 로컬 대역 시험으로 대체했다고 쓰지 않는다.

파일별 해시와 브라우저 관측 원문은 [검증 숫자·소스 근거](legacy-texture-compat-verification-2026-10-30.json)에 남겼다. 원본 사용자 사진·쿠키·토큰은 포함하지 않는다.

## 운영에서 남은 확인

1. 별도 비교용 브랜치로 배포하고 소스 커밋·실제 실행 파일을 확인한다.
2. 같은 저금통 112에서 사진·테두리·입구 표시 → 회전 → 정면 → 2D 복귀 → 3D 재진입을 먼저 확인한다. 실패한 전환은 성능값으로 사용하지 않는다.
3. 정상 동작하면 최종 버전과 같은 사진·창 크기·확대율·CPU/네트워크 설정으로 짧은 Chrome 성능 기록을 받는다. 첫 전환과 반복 전환을 구분한다.
4. 완료 기준은 클릭 처리 시작부터 사진이 보인 최초 기록 캡처다. GPU 완료·실제 모니터 표시 시각과 구분하고 중첩된 이미지 요청 시간을 더하지 않는다.
5. 확인 후 최종 Production 배포 **`7nxVGo78jVUA28rr3uDiyLBvTeTi` / `491ffa4`**로 복구하고 실제 화면도 확인한다.

이번 로컬 검증만으로 새 운영 시간이나 개선율을 만들지 않는다. 기존 로컬 개선율과 기존 운영 관측값도 각각 원래 조건을 유지한다.
