# 저금통 3D 전환 성능 개선 — 쉽게 읽는 정리와 포트폴리오용 성과

작성 기준: 2026년 10월 26일. Memory Jar의 **로컬 개발 환경에서 확인한 결과**다.

**대표 성과: 여우·레서판다의 사진형과 빈 틀 4개 조건에서, 모양 계산 시간이 반복 비교 중앙값 기준 40.16~46.07% 줄었다. 고정 모양 19개의 데이터는 그대로 유지했다.**

이 글은 이번 테두리 계산 개선을 쉽게 설명한다. 이전 서버 이미지 캐시와 연결 시간 분석은 [앞선 작업 정리](JOURNEY_2026-10-25.md)와 [연결 세부 측정](CONNECTION_BREAKDOWN_2026-10-26.md)에 남아 있다. 개발자가 구현과 실험을 재확인할 때는 [기술 기록](RIM_OPTIMIZATION_2026-10-26.md)을 함께 본다.

## 1. 어떤 문제가 있었나?

저금통 상세 화면에서 ‘3D로 보기’를 누르면 사진이 입혀진 입체 모양이 나올 때까지 기다려야 했다.

처음에는 사진을 가져오는 일이 느린지, 입체 모양을 만드는 계산이 느린지 알 수 없었다. 그래서 사진 준비, 모양 계산, 화면 그리기 시간을 따로 쟀다.

배달이 늦을 때 주문 접수·요리·배달 시간을 따로 확인하는 것과 같다. 전체 시간만 보면 어디부터 고쳐야 할지 알기 어렵다.

## 2. 왜 계산 시간이 두 번 잡혔을까?

실제 개발 앱에는 StrictMode(개발 중 화면 준비와 정리를 다시 실행해 문제를 찾는 기능)가 켜져 있었다. 이 검사 과정에서 입체 모양을 준비했다가 정리하고 다시 준비할 수 있었다.

그래서 계측(작업 시간을 재는 코드)에 실행 번호를 붙여 다음 두 비용을 구분했다.

| 구분 | 뜻 | 수정 전 실제 표본 |
| --- | --- | ---: |
| 폐기된 준비의 계산 | 모양을 준비했지만 최종 화면에는 쓰이지 않은 계산 | 995.7ms |
| 출력에 사용한 계산 | 최종 3D 화면을 만드는 데 사용한 계산 | 729.8ms |
| 두 계산의 합계 | 기존 계측에 함께 잡히던 값 | 1,725.5ms |

1,000ms는 1초다. 위 합계 전체를 ‘모양을 한 번 만드는 비용’이라고 해석하면 잘못된 결론을 낼 수 있다.

분리 계측은 ‘출력에 쓴 실행’과 ‘그 전에 정리된 실행’을 구별한다. 다른 이유로 화면 준비가 다시 실행될 수도 있으므로 폐기된 작업을 무조건 개발 검사 때문이라고 자동 판정하지는 않는다. 합성 시험에서는 같은 화면의 StrictMode를 켜고 끄며 실행 횟수가 달라지는 것을 확인했다.

개발 검사는 유지한 채, 실제로 어디에 계산 시간이 쓰이는지 확인하는 데 이 구분을 사용했다.

## 3. 실제로 어디가 느렸나?

3D 모양은 작은 점과 삼각형을 많이 연결해 만든다. 정점(삼각형의 꼭짓점), 표면 분할(표면을 작은 삼각형으로 나누는 작업)이 중요한 재료다.

출력에 사용한 729.8ms 중 큰 두 구간은 다음과 같았다.

| 작업 | 수정 전 실제 표본 |
| --- | ---: |
| 테두리의 점을 입체 좌표로 만들기 | 247.0ms |
| 테두리 표면을 작은 삼각형으로 나누기 | 225.7ms |

코드를 읽어 보니 여러 삼각형이 같은 점을 공유하는데도, 그 점의 높이와 앞뒤 정점 번호를 다시 구하고 있었다. 이미 푼 수학 문제를 옆 문제에서 또 푸는 상황이었다.

어떤 삼각형이 같은 변을 공유하는지 나타내는 연결 정보도 반복해서 만들고 있었다. 이 과정에서 잠깐 쓰고 버리는 배열과 객체도 많이 생겼다.

## 4. 어떻게 바꿨나?

### 같은 점의 답은 한 번만 구하기

같은 점의 높이와 앞뒤 정점 번호는 한 번 계산한 뒤, 그 모양을 만드는 동안 재사용하도록 했다. 저장소에는 점 객체 자체를 기준으로 삼는 WeakMap(객체별 계산 결과를 기억하는 임시 저장소)을 사용했다.

가까이 있는 서로 다른 두 점을 임의로 합치지 않았다. 다른 저금통이나 다음 생성에 이전 결과가 섞이지 않도록 재사용 범위도 한 번의 모양 생성 안으로 한정했다.

### 연결이 그대로면 다시 조사하지 않기

삼각형 구성이 그대로일 때는 이미 만든 연결 정보를 재사용했다. 삼각형을 바꾸거나 나눈 뒤에는 그 정보를 폐기하고 새로 만들도록 했다. 오래된 연결을 잘못 쓰지 않기 위한 조건이다.

변마다 만들던 인접 배열과 추가 객체도 줄였다. 한 번의 검사 안에서 이미 처리한 삼각형인지 표시하는 데에는 Uint8Array(번호별로 작은 숫자 표시를 보관하는 배열)를 사용했다.

수정 대상은 [body3DMesh.mjs](../../../frontend/src/features/jarDesign/body3DMesh.mjs)다. 테두리 높이·정점 번호 재사용과 분할 연결 정보 재사용이 핵심이다.

사진 위치, 입구 위치, 표면을 나누는 기준, 삼각형 상한과 높이 계산식은 유지했다. 사진 해상도나 모양 품질을 낮추지 않았고, 새 라이브러리도 추가하지 않았다. 서버의 권한 검사와 이미지 캐시 설정은 이번 계산 개선 단계에서 바꾸지 않았다.

## 5. 몇 % 줄었나? — 대표 성과로 사용할 반복 비교

이 표는 **CPU(프로그램의 계산을 처리하는 장치)에서 모양을 만드는 시간**을 비교한 결과다. 사진 다운로드와 화면 그리기는 포함하지 않는다.

옛 코드와 새 코드에 같은 입력을 넣었다. 두 구현을 각각 3회 먼저 실행한 뒤, 순서를 번갈아 각각 7회 실행했다. 비교한 값은 중앙값(크기순으로 정렬했을 때 가운데에 오는 값)이다. 먼저 3회 실행한 값은 통계에서 제외했으며, 서비스에 별도의 예열 기능을 추가한 것은 아니다.

### 전체 모양 계산 시간

| 입력 | 수정 전 중앙값 | 수정 후 중앙값 | 시간 감소율 |
| --- | ---: | ---: | ---: |
| 여우 사진형 | 882.34ms | 527.95ms | **40.16%** |
| 여우 빈 틀 | 1,038.91ms | 579.00ms | **44.27%** |
| 레서판다 사진형 | 1,308.55ms | 759.01ms | **42.00%** |
| 레서판다 빈 틀 | 1,092.94ms | 589.45ms | **46.07%** |

사진형은 사진 면이 있는 모양, 빈 틀은 사진 자리가 뚫린 모양이다. 이 4개 조건에서의 결과를 ‘모든 모양이 40% 이상 빨라졌다’로 넓혀 말하지 않는다. 별도의 일반 윤곽 3개 조건에서는 전체 계산 시간이 10.80~21.77% 감소했다.

### 직접 고친 테두리 작업의 감소율

| 입력 | 표면 분할 시간 감소율 | 정점 생성 시간 감소율 |
| --- | ---: | ---: |
| 여우 사진형 | **40.38%** | **75.73%** |
| 여우 빈 틀 | **35.99%** | **78.18%** |
| 레서판다 사진형 | **32.36%** | **80.47%** |
| 레서판다 빈 틀 | **40.60%** | **79.03%** |

정점 생성이 최대 80.47% 줄었다고 해서 전체 계산이나 전체 화면 전환도 80.47% 줄었다는 뜻은 아니다. 각 표의 작업 범위가 다르다. 표면 분할과 정점 생성 감소율을 더하거나, 조건별 감소율을 단순 평균해 대표 성과로 쓰지 않는다.

원본: [카탈로그 4개 조건](rim-cpu-comparison-catalog-2026-10-26.json), [일반 윤곽 3개 조건](rim-cpu-comparison-2026-10-26.json). 두 비교는 모양 계산 소스의 같은 수정 전·후 버전을 사용했다.

### 감소율 계산 방법

```text
시간 감소율(%) = (수정 전 시간 − 수정 후 시간) ÷ 수정 전 시간 × 100

예: 여우 사진형
(882.3386 − 527.9547) ÷ 882.3386 × 100 = 약 40.16%
```

100초 걸리던 작업이 60초가 되면 시간이 40% 줄어든 것이다. 이 문서의 %는 모두 **걸린 시간의 감소율**이다. 표시 시간은 반올림했지만 감소율은 원본 숫자로 계산한 뒤 소수점 둘째 자리까지 표시했다.

## 6. 실제 저금통 화면에서도 확인했나?

같은 저금통과 사진에서 그리기 영역 380×380, 배율 1.25, 삼각형 18,308개를 유지하고 확인했다. 수정 후에는 새로고침 뒤 첫 전환과 바로 반복한 전환을 따로 받았다.

| 항목 | 수정 전 분리 표본 1건 | 수정 후 첫 전환 | 수정 후 반복 전환 |
| --- | ---: | ---: | ---: |
| 출력에 사용한 모양 계산 | 729.8ms | **264.7ms** | **266.6ms** |
| 전체 클릭→3D 그리기 함수 반환 | 2,434.2ms | **1,208.7ms** | **894.7ms** |

수정 전 표본과 수정 후 첫 전환을 산술적으로 비교하면 다음과 같다.

- 출력용 모양 계산: **63.73% 감소**로 관찰됐다.
- 전체 전환: **50.35% 감소**로 관찰됐다.

**이 두 %는 실제 화면의 제한된 표본을 비교한 보조 관찰값이다. 포트폴리오의 대표 성과는 5절의 반복 비교 결과를 사용한다.**

수정 전 분리 표본은 1건이며, 반복 전환에 대응하는 수정 전 반복 표본은 없다. 그래서 894.7ms를 이용해 ‘반복 전환이 몇 % 개선됐다’고 확정하지 않는다. 새로고침도 모든 캐시를 비웠다는 뜻은 아니다. 기기 부하와 실행 준비 상태, 사진 요청 시간 등도 달라질 수 있다.

앞선 다른 실제 측정에는 전체 전환이 1,194.9ms인 기록도 있었다. 따라서 가장 느린 2,434.2ms만 기준으로 잡아 ‘전체 전환이 항상 절반으로 줄었다’고 발표하지 않는다. 제한된 실제 화면 관찰과, 동일 입력을 번갈아 비교한 계산 시험을 함께 근거로 남겼다.

완료 기준은 renderer.render 반환(브라우저의 그리기 함수가 끝난 시점)이다. GPU(화면 그림을 처리하는 장치)의 작업 완료나 실제 모니터 표시 완료까지 잰 결과는 아니다. 현재 결과는 개발 모드의 값이며 운영 배포 후 성능은 별도로 확인해야 한다.

원본: [수정 전 분리 표본](actual-effect-split-2026-10-26.json), [수정 후 첫·반복 표본](actual-rim-after-2026-10-26.json), [앞선 1,194.9ms 기록](actual-socket-and-frontend-2026-10-26.json).

## 7. 빨라지면서 모양이 바뀌지는 않았나?

눈으로만 비슷한지 보지 않고, 고정 모양 **19개**의 데이터를 대조했다. 기존 15개 기준에 여우·레서판다의 사진형·빈 틀 4개를 더했다.

확인한 값은 점의 좌표, 법선(빛을 받을 방향), UV(사진을 붙일 위치), 삼각형 연결 순서, 재질 구분이다. 이 값들을 해시(데이터를 비교하기 위한 요약값)로 확인했을 때 수정 전후가 일치했다. 비교 기준을 새 결과로 덮어쓰지 않았다.

개선 작업에서는 다음 검증도 마쳤다.

- 전체 프론트 테스트 **252개 통과**.
- 운영용 프로그램 묶음을 만드는 빌드 통과. 기존 큰 묶음 크기 경고는 남아 있다.
- 합성 화면에서 3D 표시, 오류 발생 시 2D 복구, 다시 3D 전환 확인.
- 실제 저금통에서 최적화 후 첫 전환과 반복 전환의 완료 기록 확인.

19개 기준에서 데이터가 같다는 것은 확인한 사실이다. 모든 가능한 그림과 기기에서 결과를 검증했다는 뜻으로 확대하지 않는다. 개인 사진과 인증정보는 성과 자료에 저장하지 않았다.

## 8. 포트폴리오에는 이렇게 적을 수 있다

### 제목에 쓰기 좋은 문장

> 저금통 3D 모양 생성 시간을 로컬 반복 비교 중앙값 기준 40.16% 단축 — 여우 사진형 기준

### 본문에 쓰기 좋은 문장

> 저금통의 2D→3D 전환을 구간별로 계측하고, 개발 모드에서 폐기되는 준비 작업과 실제 출력에 사용한 계산을 분리했습니다. 테두리의 중복 높이 계산·정점 등록과 삼각형 연결 정보 재생성을 줄여, 같은 입력을 번갈아 7쌍 측정한 로컬 CPU 비교에서 여우 사진형의 모양 생성 시간을 중앙값 882.34ms에서 527.95ms로 40.16% 단축했습니다. 여우·레서판다의 사진형과 빈 틀 4개 조건에서는 40.16~46.07% 감소를 확인했으며, 고정 모양 19개의 좌표·법선·UV·인덱스·재질 데이터를 보존하고 프론트 테스트 252개와 빌드를 통과했습니다.

### 실제 화면 확인을 덧붙일 문장

> 같은 저금통의 로컬 상세 화면에서 개선 후 출력용 모양 계산 264.7ms·266.6ms, 전체 전환 1.209초·0.895초를 첫 전환과 반복 전환으로 나누어 확인했습니다. 실제 화면의 표본 수가 적고 개발 모드의 비용이 포함되므로 운영 성능 개선율로 일반화하지 않았습니다.

‘전체 서비스 속도 80% 개선’, ‘모든 3D 화면이 항상 50% 단축’, ‘운영에서 검증 완료’는 현재 근거로 쓸 수 없다. **측정한 작업 범위와 조건을 붙인 시간 단축 수치**로 표현한다.
