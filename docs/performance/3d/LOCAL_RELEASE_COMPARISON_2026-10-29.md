# 초기 3D와 현재 3D를 분리된 로컬에서 비교했다

## 먼저 결론

이번 시험에서는 **초기 구현이 더 빨랐다.** 초기 구현과 현재 구현은 그리는 모양과 사진 표현 방식이 다르다. 같은 일을 빠르게 바꾼 시험과 구분해야 한다.

초기 구현은 평면 사진을 입체 틀 위에 겹친다. 현재 구현은 둥근 곡면을 계산하고 그 위에 사진을 입힌다. 삼각형은 입체 모양을 만드는 작은 조각이다. 이번 본체의 삼각형 수는 **632개 → 28,160개, 약 44.56배**다. 그리는 방식과 기능이 달라 이 전체 버전 비교를 순수 최적화 개선율로 발표하지 않는다. 삼각형 수의 배수가 계산 시간의 배수라는 뜻도 아니다.

## 왜 이렇게 시험했나?

운영에는 옛 백엔드(서버 프로그램)가 읽지 못하는 새 디자인 형식이 실제로 있다. 운영 DB(서비스 데이터를 저장하는 곳)는 유지하고, **과거 프론트(화면)·백엔드 한 쌍과 현재 프론트·백엔드 한 쌍**을 PC의 별도 시험 공간에 실행했다. 실제 회원·사진·S3 키·AWS 자격 증명을 가져오지 않았다.

| 조건 | 초기 구현 | 현재 구현 |
| --- | --- | --- |
| 고정 커밋 | c5f58c4, 2026-10-11 | 8a5f7cc, 2026-10-26 |
| 백엔드·프론트 | 모두 해당 커밋 | 모두 해당 커밋 |
| DB | 빈 MariaDB의 V53과 합성 표시 데이터 | 같은 구조와 합성 표시 데이터 |
| 사진 | 같은 480×480 합성 PNG, 7,143바이트 | 같은 바이트 |
| 본체 입력·사진 배치·입구 | 같은 시험 설정 | 같은 시험 설정 |
| 그리기 영역·배율 | 380×380, 1.25 | 380×380, 1.25 |
| 브라우저·출력 버퍼 | 1265×720, 475×475 | 동일 |
| 네트워크 | 로컬 사진 서버, 추가 지연 없음 | 동일, 현재 서버 이미지 캐시 유지 |

V53은 DB 구조 변경 기록을 53번째까지 적용한 상태다. 캐시는 한 번 읽은 사진을 잠시 보관했다가 다시 쓰는 기능이다.

두 앱과 DB는 인터넷으로 나가는 길이 없는 시험용 네트워크에 둔다. PC에서 접속하는 별도 프록시(요청을 중계하는 프로그램)만 정해진 앱 두 개와 사진 서버로 전달한다. DB 포트를 공개하거나 운영 서버의 네트워크 설정을 바꾸지 않았다.

사진 요청을 만드는 S3 SDK(파일 저장소에 요청을 보내는 개발 도구)는 실제로 실행했다. 접속 주소와 인증정보는 로컬 시험용으로 바꿨다. **실제 AWS 인증·S3·TLS(암호화 연결)와 운영 이미지 응답 시간을 재현한 시험은 아니다.**

## 어떻게 쟀나?

안내 팝업을 닫고 기능 확인·준비 실행을 한 뒤 페이지를 다시 열었다. 측정 버튼이 저금통을 화면 중앙에 맞춘 다음, 각 버전에서 **첫 전환 1회 + 반복 5회**를 수행했다. 정식 기록은 현재 구현, 초기 구현 순서다. 첫 전환은 새 문서의 첫 3D 전환이다. 앞서 준비 실행을 했기 때문에 브라우저와 서버에 이미 준비된 값이 남아 있을 수 있다. 반복 5회는 값을 크기순으로 놓았을 때 가운데 값인 중앙값으로 비교했다.

완료 기준은 ① 사진이 준비되고 그리기 함수가 반환된 때, ② 그 뒤 rAF가 두 번 호출된 때다. rAF(requestAnimationFrame)는 브라우저가 다음 화면 갱신을 준비할 때 호출하는 함수다. **GPU(화면을 그리는 칩)의 계산 완료나 실제 모니터에 표시된 정확한 순간은 아니다.**

처음 안내가 겹친 실행과 두 화면의 스크롤 위치가 달랐던 실행은 제외했다. 최종 12건은 모두 그리기 영역 전체가 화면 안에 있었고 크기·배율·출력 버퍼가 같았다. 기존 화면의 둥실거리는 애니메이션은 유지해 위치가 몇 픽셀 변한 값도 원본에 남겼다. 같은 PC에서 순서대로 관측한 한 묶음이며 무작위 순서의 반복 실험이나 CPU 부하 격리는 하지 않았다.

## 결과

| 관측 항목 | 초기 구현 | 현재 구현 |
| --- | ---: | ---: |
| 첫 전환: 사진·그리기 준비 | **385.5ms** | **951.3ms** |
| 반복 5회 중앙값: 사진·그리기 준비 | **68.4ms** | **520.1ms** |
| 첫 전환: 준비 후 두 번의 rAF 관측까지 | 402.5ms | 968.1ms |
| 반복 5회 중앙값: 두 번의 rAF 관측까지 | 82.9ms | 531.6ms |
| 6회 동안 사진 서버에서 실제 읽은 횟수 | 0회 | 1회 |

초기 구현은 2D에서 미리 로드한 사진을 재사용해 3D 전환 중 추가 사진 요청이 관찰되지 않았다. 현재 구현은 인증 이미지 API를 6번 요청했고 사진 서버 읽기는 1번이었다. 이것이 AWS 왕복이 1번이었다는 뜻은 아니다. 실제 제공자는 로컬 시험 서버다.

이 자료로 말할 수 있는 것은 **초기 구현의 가벼운 평면 사진 방식과 현재 곡면 방식의 로컬 처리 차이**다. 새 기능·데이터 경로·배포 환경의 차이를 모두 제거한 최적화 실험은 아니다. 각 구간은 겹칠 수 있으므로 사진 요청 시간을 전체 전환 시간에 다시 더하지 않는다.

## 기능과 권한도 확인했다

- 두 버전에서 실제 로그인, 같은 윤곽·사진 배치와 같은 PNG 바이트를 확인했다.
- 사진 표시 → 좌우 회전 → 정면 복귀 → 2D 복귀 → 재전환을 확인했다. 2D 복귀 때 3D canvas가 제거됐다.
- 현재 캐시가 준비된 뒤에도 비회원은 403, 비로그인은 401로 거절됐다. 잘못된 이미지 종류는 400이고 거절된 요청은 사진 서버를 읽지 않았다.
- 로컬 게이트웨이 테스트 6개, 사진 서버 10항목, 진입 프록시 3항목과 두 앱의 시작 전 권한/조회 시나리오가 통과했다. 별도 실제 HTTP 검사도 **30항목, 실패 0**이었다.
- 과거·현재 백엔드와 운영용 프론트 빌드를 각각 통과했다. 큰 청크에 대한 기존 번들 경고는 남아 있다. 앱 원본과 운영 환경은 수정하지 않았다.

## 포트폴리오에는 어떻게 쓰나?

동일한 모양을 보존하며 검증한 기존 **모양 계산 중앙값 40.16~46.07% 감소**는 [기존 성과 정리](PORTFOLIO_3D_OPTIMIZATION_2026-10-26.md)의 범위로 사용한다. 이번 초기 버전 비교를 그 개선율의 기준점으로 바꾸지 않는다.

이번 작업은 이렇게 설명할 수 있다.

> 과거 버전을 운영 DB에 바로 연결하기 전에 실제 데이터 호환성 문제를 확인했습니다. 이후 과거·현재 프론트와 백엔드를 격리된 로컬 환경에서 같은 합성 데이터로 비교했습니다. 초기 평면 방식과 현재 곡면 방식의 기능 차이를 구분하고, 이미지 캐시 재사용 시에도 권한 검사가 유지되는지 실제 HTTP로 검증했습니다.

숫자 원본과 해시(파일 내용이 같은지 확인하는 값)는 [공개 측정 JSON](local-release-comparison-2026-10-29.json), 재현·종료 방법은 [도구 설명](../../../tools/compat/README.md)을 본다. 이 시험의 수치를 운영 개선 전후 결과나 GPU 완료 시간으로 사용하지 않는다.

## 실행기 재현과 종료까지 확인했다

최종 실행기를 별도 새 폴더에서 VerifyOnly 모드로 처음부터 실행했다. 과거·현재의 빌드, 빈 DB 구성, 앱 시작, 진입 프록시, 실제 HTTP/캐시 30항목과 종료가 모두 통과했고 종료 코드는 0이었다. 두 실행의 빌드 명세·관찰 코드·합성 이미지 해시도 같았다. 이 재현 실행에서는 성능 수치를 다시 만들지 않았다.

측정 실행과 재현 실행 모두 임시 컨테이너(서로 분리된 프로그램 실행 공간)·네트워크가 0개 남았고, 시험용 PC 포트도 모두 닫혔다. 합성 시험 계정 원문·전체 실행 로그·제외한 준비 기록은 Git 제외 폴더에만 두었다. 앱 원본과 운영 환경은 그대로이며 이번 작업의 커밋·푸시는 하지 않았다.
