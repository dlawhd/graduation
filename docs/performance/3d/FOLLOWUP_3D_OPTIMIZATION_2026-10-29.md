# 3D 전환 추가 최적화 — 같은 계산을 덜 하고 같은 모양을 만든다

이 문서의 32.88%는 **중간 버전에서 추가로 줄인 비율**이다. 원래 과거 기준 `dd6e50b`와 최종 수정본을 직접 재측정한 결과는 [최종 직접 비교 — 69.10% 감소](FINAL_DIRECT_3D_COMPARISON_2026-10-29.md)를 본다. 서로 다른 실험 기록으로 구분한다.

검증일: 2026-10-29. **직전 코드 `8a5f7cc` 대비 반복 전환 중앙값 32.88% 추가 감소**를 로컬에서 확인했다. 이번 수정본은 아직 커밋·푸시·배포하지 않았다.

## 1. 문제와 확인한 원인

서버 이미지 캐시가 켜져 있어도 2D에서 3D로 바뀔 때마다 몸통 모양을 계산한다. CPU 프로파일(어떤 함수가 계산 시간을 쓰는지 기록하는 도구)에서 바닥의 정점 처리와 삼각형 연결 정보 생성이 큰 구간으로 확인됐다.

- 정점(삼각형의 꼭짓점)을 여러 삼각형이 공유하지만, 매 방문마다 좌표 객체·Float32 변환(그래픽에 쓰는 32비트 숫자로 바꾸기)·문자열 키를 다시 만들었다.
- 바닥과 만나지 않는 면도 모두 절단용 배열과 반복문을 거쳤다.
- 표면을 나눌 때 변의 번호 쌍을 매번 문자열로 만들고, 세 변을 검사하는 데 임시 배열·콜백을 반복 생성했다.

## 2. 어떻게 고쳤나?

| 파일 | 변경 |
| --- | --- |
| `frontend/src/features/jarDesign/body3DBase.mjs` | 한 번의 바닥 계산 안에서 같은 정점의 좌표·출력 번호를 재사용한다. 바닥과 만나지 않는 면은 원래 면을 유지하고, 완전히 아래에 있는 면은 바로 제외한다. 절단이 필요한 면만 기존 절단·닫기 절차를 수행한다. |
| `frontend/src/features/jarDesign/body3DMesh.mjs` | 변의 번호 쌍을 충돌 없는 숫자로 표현하고, 세 변의 중간점을 직접 검사해 임시 배열·콜백을 줄인다. |
| `frontend/tests/body-3d-benchmark.mjs` | 수정 전 mesh가 현재 바닥 함수를 잘못 사용하지 않도록, 기준 바닥 함수도 Git 원본에서 함께 읽는다. |
| `tools/compat/` | `8a5f7cc`와 작업 수정본을 구분하고, 허용한 계산 파일 두 개만 시험 복사본에 적용한다. 파일 해시를 보관한다. |

바닥과 몸통은 좌표가 같아도 명암 방향이 달라야 하므로 출력 번호를 따로 관리한다. 기존 좌표 중복 제거도 유지한다. 분할 수·허용 오차·사진 크기·입구·법선 계산·예외·2D 복구 코드는 유지했다. 사진이나 완성 geometry를 장기 보관하는 새 캐시는 추가하지 않았다. 새 정점 재사용 정보는 **계산 한 번이 끝나면 버린다.** 서버 이미지 캐시·권한·API·DTO·DB·CSS·애니메이션·의존성은 변경하지 않았다.

## 3. 모양을 줄여서 빨라진 것은 아닌가?

고정된 수정 전 모양 기준을 덮어쓰지 않고 테스트했다. 기본·불규칙·깊은 굴곡·가는 부분·역방향·빈 틀·준비된 도안의 회귀 검사와 전체 프론트 테스트가 통과했다. 같은 합성 저금통은 두 버전 모두 정점 14,196개·삼각형 28,160개이고, 좌표·법선(표면 방향)·UV(사진 좌표)·삼각형 연결·재질 그룹이 바이트 단위로 같았다.

## 4. 실제 전환은 얼마나 줄었나?

두 앱 모두 **동일한 `8a5f7cc` 백엔드·서버 캐시 활성화·같은 V53 시험 DB 구조**를 사용했다. 차이는 위 프론트 계산 파일 두 개다. 같은 480×480 합성 사진·53점 윤곽·색·사진/입구 배치, 380×380 영역, 1.25 배율을 유지했다. 기록된 브라우저 영역은 1265×720, 캔버스는 475×475였다.

수정 전→수정 후→수정 후→수정 전 순서로 새 문서에서 각 6회, 총 24회 측정했다. 매 묶음의 첫 1회는 반복 통계에서 제외했다. 클릭 처리 시작부터 사진·테두리가 준비된 상태의 그리기 함수 반환까지이며 **GPU 완료·실제 모니터 표시·운영 성능 측정은 아니다.**

| 반복 전환 | 직전 코드 | 이번 수정본 | 감소율 |
| --- | ---: | ---: | ---: |
| 묶음 1의 5회 중앙값 | 1279.7ms | 952.7ms | 25.55% |
| 역순 묶음 2의 5회 중앙값 | 1478.0ms | 963.1ms | 34.84% |
| **반복 10회 전체 중앙값** | **1427.25ms** | **957.90ms** | **32.88%** |

감소율은 `(수정 전 - 수정 후) ÷ 수정 전 × 100`을 반올림 전 값으로 계산했다. 두 묶음 모두 감소했다. 24회 모두 정상 완료됐고 활성 탭·전체 모양 표시·같은 화면 조건을 확인했다. 수동 기능 확인 전환은 통계에 넣지 않았다.

첫 전환 원시 값은 수정 전 2084.0/2137.5ms, 수정 후 2027.6/1559.6ms다. 수정 후 두 번째 묶음은 서버 이미지 캐시가 남아 사진 제공자를 0회 읽었고 다른 묶음은 1회 읽었다. **첫 요청의 초기 준비·캐시 상태를 완전히 통제한 실험은 아니므로 첫 전환 개선율은 성과로 확정하지 않는다.** 반복 요청은 기존 서버 캐시를 사용하는 상태에서 비교했다.

앞서 얻은 **45.24%**는 `dd6e50b`→`8a5f7cc` 전체 버전 비교이고, 이번 **32.88%**는 `8a5f7cc`→작업 수정본의 별도 비교다. 서로 다른 실험이므로 더하거나 곱해 누적 개선율을 만들지 않는다. 컴퓨터 부하·예열에 따라 같은 코드의 절대 시간도 달라질 수 있어 이전 실험의 916ms와 이번 수정본 값을 직접 빼지 않는다.

## 5. 계산 자체도 빨라졌나?

같은 Node 프로세스에서 각 구현을 3회 예열하고 순서를 번갈아 7쌍 실행했다. 모든 쌍에서 모양 데이터가 같았다. 이미지·네트워크·GPU를 제외한 **CPU 모양 계산만의 감소율은 35.95~51.50%**였다.

| 입력 | 직전 계산 중앙값 | 수정본 계산 중앙값 | 감소율 |
| --- | ---: | ---: | ---: |
| ROUND:filled | 1029.02ms | 548.80ms | 46.67% |
| IRREGULAR:filled | 791.92ms | 411.09ms | 48.09% |
| DEEP:filled | 911.87ms | 442.26ms | 51.50% |
| FOX:filled | 628.90ms | 402.79ms | 35.95% |
| FOX:hollow | 523.93ms | 324.94ms | 37.98% |
| RED_PANDA:filled | 852.84ms | 546.11ms | 35.97% |
| RED_PANDA:hollow | 785.10ms | 438.17ms | 44.19% |

이 값은 브라우저 전체 전환 감소율과 구분한다. 재현 명령은 `node frontend/tests/body-3d-benchmark.mjs 8a5f7cc` 및 마지막에 `catalog`를 붙인 명령이다.

## 6. 검증·안전·남은 확인

- 전체 프론트 Node 테스트 **252개 통과**, 실패·건너뜀 0. 기존 바닥·모양 바이트 보존 24개 검사는 이 수에 포함된다.
- 비교 도구 테스트 **12개**, 사진 서버 **10항목**, 진입 프록시 **3항목**, 실제 HTTP·권한·캐시 **30항목** 통과.
- 두 버전의 프론트 production 빌드와 백엔드 스냅샷 빌드가 성공했다. 기존 큰 청크 경고는 남아 있다.
- 실제 앱 시작·로그인·같은 디자인 조회·CSRF·비멤버/비로그인 거절을 확인했다. 캐시 적중 뒤 권한 거절과 잘못된 이미지 종류 거절도 통과했다.
- 수정본의 사진·테두리·입구·좌우 회전·정면 복귀·2D 복귀·재진입을 확인했다. 2D 복귀 뒤 캔버스는 0개, 사진은 480px 로딩 완료였다.
- 백엔드 앱 소스와 캐시 코드는 변경하지 않았고, 이번에는 백엔드 전체 단위 테스트를 재실행하지 않았다. 실제 모바일 기기·실제 AWS·운영 배포 후 속도·GPU 완료는 별도 확인 대상이다.
- 운영·Git 브랜치·실제 DB·실제 인증정보를 바꾸지 않았다. 임시 앱과 DB는 외부 통신 경로가 없는 로컬 네트워크에서 실행했고 정상 종료했다. 시험 컨테이너·네트워크·loopback 포트를 정리했다.

빌드 입력 해시·전체 원시 수치·CPU 비교·검증 결과는 [followup-3d-optimization-2026-10-29.json](followup-3d-optimization-2026-10-29.json)에 보관했다. 쿠키·시험 비밀번호·사진 URL·운영 로그는 포함하지 않는다. 비교 도구 실행 방법은 [도구 설명](../../../tools/compat/README.md)을 본다.
