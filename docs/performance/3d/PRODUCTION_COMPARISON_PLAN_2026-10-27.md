# 운영에서 수정 전 계산을 재현하는 비교 준비

이 문서는 2026-10-27의 **재현 비교 방법과 진행 상태**다. 테두리 계산만 비교하려고 수정 전 프론트를 잠시 적용했으나, 사용자의 원래 목표인 전체 2D→3D 전환 비교로 범위를 바로잡았다. 운영 프론트는 최적화 후 `8a5f7cc`로 복구했고 운영 도메인 연결까지 확인했다. 전체 최적화 전 상태의 적용·새 운영 측정은 아직 하지 않았다. 이전 운영 성능 기록을 수정 전 결과로 바꾸지 않는다.

## 로컬에서 운영용 파일 준비

`frontend/scripts/build-3d-comparison.mjs`는 기존 Vite 설정과 production 모드로 두 버전을 만든다. Git `show`로 읽은 계산 코드만 메모리에서 교체하며, 소스 파일·일반 `frontend/dist`·Git 이력은 바꾸지 않는다. 새 라이브러리는 필요 없다.

기존 운영 빌드와 같은 공개 `VITE_` 환경변수를 사용한다. 예를 들어 API와 WebSocket 접속 주소는 다음과 같이 지정한다. 기존 개인 환경변수를 덮어쓰지 않도록 별도 터미널에서 실행한다. 키·비밀번호는 넣거나 공유하지 않는다.

```powershell
cd C:\Users\whdgu\Desktop\graduation\frontend
$env:VITE_API_BASE_URL = 'https://api.esjh.shop'
$env:VITE_WS_BASE_URL = 'wss://api.esjh.shop/ws'
node scripts/build-3d-comparison.mjs
```

결과는 Git에서 제외된 `frontend/build/3d-comparison/<실행별 폴더>/before`와 `after`다. 각 폴더의 `comparison-build.json`으로 어느 버전인지 확인한다. 기존 Vercel SPA 경로 설정도 함께 복사한다. 계산 파일이 기록된 버전과 다르거나 추적 중인 프론트 파일에 미커밋 변경이 있으면 빌드를 거절한다. 로컬 API 주소도 거절한다. 빌드 성공을 배포 성공으로 기록하지 않는다. 실제 Vercel 운영 빌드의 나머지 공개 환경변수도 같은지 확인한 뒤 배포해야 한다.

## 실제 운영 측정 순서

1. Vercel의 현재 운영 배포 식별자와 복구 대상을 먼저 확인한다. 로그인 후 `8a5f7cc` 배포의 Production·Current Domains·`www.esjh.shop` 연결을 확인했고, `d56d067` 배포도 Ready 상태로 남아 있음을 확인했다. 운영 환경변수의 원문을 열거나 수집하지 않았다.
2. 동일한 운영 도메인·브라우저에서 수정 전·후를 번갈아 확인한다. 이번에는 준비 빌드를 업로드하지 않고 보관된 Vercel Production 배포의 Promote(운영 도메인의 연결 대상을 해당 배포로 변경)를 사용한다. 서로 다른 미리보기 도메인의 결과를 동일 운영 조건의 비교로 합치지 않는다. 다른 도메인에서는 로그인 쿠키·CORS(브라우저가 다른 사이트의 API 접근을 허용하는 규칙)도 달라질 수 있다.
3. 같은 저금통·사진·화면 크기·확대율·CPU 및 네트워크 설정을 유지한다. 전환 중 다른 화면을 조작하지 않는다. 사진까지 보인 상태와 회전·2D 복귀 동작을 확인한다.
4. 각 버전의 첫 전환과 반복 전환을 나누어 기록한다. 첫 전환은 모든 캐시를 지웠다는 뜻이 아니며, 이미지 요청과 코드 재사용 상태를 함께 남긴다. 가능하면 실행 순서를 바꾼 반복 비교를 하고, 새 운영 기록 두 버전끼리 중앙값을 비교한다.
5. 완료 기준은 두 버전 모두 클릭부터 사진이 나타난 캡처까지로 통일한다. 로컬 render 반환 시간이나 INP를 섞지 않는다. Chrome 녹화 부하와 캡처 간격의 한계도 함께 적는다.
6. 비교를 마치면 현재 최적화된 버전으로 복구하고 버전 식별값과 화면 동작을 다시 확인한다. 오류가 나면 측정을 중단하고 확인된 복구 대상으로 되돌린다.

이전 운영 기록의 첫 약 1.09초·반복 약 0.57초는 이미 확보한 배포 후 관찰로 유지한다. 새 비교를 완료하기 전에는 운영 개선율을 추가하지 않는다.

## 범위 정정과 현재 상태: 전체 전환 개선 비교로 변경

사용자는 최초 목표가 ‘클릭 후 사진이 입혀진 3D가 나타날 때까지 기다리는 전체 시간 단축’이므로 테두리 계산만이 아니라 **프론트 계산과 백엔드 이미지 캐시를 포함한 전체 최적화 전후**를 확인해야 한다고 명확히 했다. 이 목표에 테두리만 되돌린 비교는 부족하다.

- 현재 상태 기록: 2026-10-27 19:44:03 KST. 이는 확인 후 기록 시각이며 정밀한 배포 완료 시각이 아니다.
- 임시 적용한 `d56d067` 프론트에서 원래 `8a5f7cc` 배포로 Promote를 실행했다. 프로젝트 Overview의 Production Deployment에서 배포 `FiTbdDBuHB5EZ39SqnBZNsk686XJ`, `www.esjh.shop`, 소스 `8a5f7cc`가 함께 표시되는 것을 확인했다.
- **현재 운영 프론트는 최적화 후 버전으로 복구 완료다.** 백엔드 배포·DB·서버 이미지 캐시 설정·로컬 앱 소스는 변경하지 않았다. 범위가 달라진 테두리 전용 녹화는 중단하도록 안내했다.

운영 서버 전체를 무작정 과거 버전으로 되돌리는 대신, 위 성능 개선 대상의 수정 전 동작을 재현하고 인증·인가·입력 검증·오류 처리는 유지할 수 있는지 검증한다. 기존 테두리 전용 빌드 도구는 이 전체 비교에 사용하지 않는다. 실제 적용 전 테스트·빌드·복구 경로 확인이 필요하다.

#### 진행을 막고 있는 사항과 정확한 다음 단계

2026-10-29에 API DNS가 기존 서버 `52.78.116.71`을 가리키는 것을 확인했지만, SSH 연결은 반복해서 시간 초과됐다. 따라서 준비한 읽기 전용 집계도 실행 성공으로 확정하지 않았고, 원격 자원 상태와 옛 AWS SDK 실행도 새로 확인하지 못했다. 로컬에는 AWS 인증 환경변수나 표준 자격 증명 파일이 없으며 운영 비밀값을 복사하지 않았다.

1. SSH가 복구되면 DB를 변경하지 않는 읽기 전용 트랜잭션으로 새 JSON 필드·AI 스타일·테두리 이미지의 **집계 건수만** 확인한다. 원문 데이터·사진·S3 키는 가져오지 않는다.
2. 운영 데이터에 맞지 않는 형식이 있으면 옛 백엔드 전체를 공유 운영 DB에 연결하지 않는다. 비용이 없는 격리된 비교 환경 또는 범위를 한정한 비교 중 가능한 방법을 결정한다.
3. 실제 옛 AWS SDK 확인은 DB 쓰기·S3 삭제·스케줄러가 없는 읽기 검증으로 먼저 준비한다. 현재 서버 자원 여유와 복구 수단도 확인한 뒤 실행 여부를 결정한다. 현재 실행한 것처럼 기록하지 않는다.
4. 그 뒤 같은 저금통·사진·화면 조건에서 첫 전환과 반복 전환을 따로 수집한다. 두 시대의 사진 합성·곡면 기능 차이도 함께 적어 순수 최적화 효과와 구분한다.

이번 단계에서는 앱 코드·운영 백엔드·캐시 설정·DB·보안 설정을 변경하지 않았다. 추가 유료 자원도 만들지 않았다. 문서만 보완했으므로 앱 테스트·빌드는 다시 실행하지 않았다. **전체 과거 백엔드의 운영 검증과 새 성능 비교는 미완료**다.

#### 같은 날 후속 확인: SSH 복구 후 읽기 전용 집계 완료

사용자가 AWS의 SSH 접근을 추가했다고 알려줘 재시도했고 접속이 성공했다. **위 SSH 차단은 해소됐다.** 원격 DB에는 `SET SESSION TRANSACTION READ ONLY`와 `START TRANSACTION READ ONLY`를 적용해 집계한 뒤 `ROLLBACK`으로 종료했다. 원문 행·사진·객체 키·회원 정보·인증정보는 가져오지 않았다. 공개 가능한 결과는 [읽기 전용 집계 근거](legacy-production-readonly-audit-2026-10-29.json)에 보관한다.

| 실제 운영 DB 확인 항목 | 집계 |
| --- | ---: |
| 현재 구조 | V53 |
| 완성 디자인 / 임시 디자인(Draft) 전체 | 15 / 60 |

`points`·`color` 외 필드 여부는 `JSON_REMOVE(custom_body_json,'$.points','$.color')`에 남은 필드 수로 확인했고, `photoContours` 존재도 별도로 집계했다. 새 스타일은 옛 enum의 6개 허용 값 밖의 값으로 집계했다. **같은 데이터가 여러 행에 포함될 수 있으므로 표의 숫자를 더해 비호환 저금통 수로 발표하지 않는다.** 정리 완료 기록이 실제 S3 객체 삭제 여부까지 새로 확인한 것을 뜻하지는 않는다. 현재 정리 대기 0건이라는 결과와 옛 정리 코드의 지원 범위 차이도 구분한다.

앞선 로컬 시험에서 `photoContours`와 새 enum을 옛 코드가 거절하는 것을 검증했고, 이번에는 그 형식의 데이터가 운영에 실제로 있음을 확인했다. 따라서 **대상 112 한 건이 호환되더라도 수정하지 않은 옛 백엔드 전체를 공유 운영 DB에 연결하는 방식은 사용하지 않는다.** 다른 디자인의 조회나 관련 기능에서 오류가 발생할 수 있다. 비교를 위해 운영 데이터를 삭제·변환하거나 옛 DB 구조로 되돌리지 않았다.

현재 API는 revision `8a5f7cc`, 실행 이미지 `sha256:a8e4f1212932f983da361306f84c2e61075c96cd3c0df7f96b8a86c84ee201e5`로 실행 중이고 비공개 관리 포트의 health가 `UP`이었다. 캐시 환경변수는 미설정으로 기본 활성 상태이며 활성 캐시 비교 기록은 없었다. API 시작 시각은 2026-10-28 18:46:27 KST, DB 시작 시각은 2026-10-18 17:41:18 KST로 앞선 기록과 같았다. 이번 작업에서 재시작하지 않았다.

서버 메모리는 전체 약 914MiB, 가용 약 **201MiB**였고 스왑은 약 **511MiB 사용 중**이었다. 디스크 여유는 약 3,682MiB였다. 순간 관측값이며 전체 시간의 최대 사용량은 아니다. 이 여유에서 또 하나의 전체 백엔드를 띄우지 않았다. 운영 JVM에 검증 코드를 주입하거나 AWS 비밀값을 로컬로 복사하는 방식도 사용하지 않았다.

**현재 결정:** 추가 비용 없이 진행한다는 사용자 조건을 유지하고, 전체 과거 버전 비교는 운영과 분리된 로컬 환경에서 호환되는 고정 시험 데이터로 수행하는 범위로 한정한다. 앞선 로컬 14개 시험은 그중 시작·로그인·조회만 완료한 결과다. 실제 사진을 포함한 옛 AWS 경로와 전체 2D→3D 속도 비교는 아직 실행하지 않았으며, 새 개선율도 없다. 이번 후속 작업은 읽기 전용 집계와 문서 보완이므로 앱 테스트·빌드는 재실행하지 않았다.

#### 이후 진행: 합성 사진을 사용한 로컬 전체 버전 비교 완료

사용자가 로컬 비교를 계속 요청했고 같은 원본 사진이 아니어도 된다고 답했다. 운영 데이터 재복사 없이 공개 시험 윤곽과 고정 480×480 합성 PNG를 사용했다. 프론트·백엔드 모두 c5f58c4인 환경과 모두 8a5f7cc인 환경을 각각 빈 V53 MariaDB에 연결했다. 로그인·쿠키·CSRF·JWT·권한·Service·Repository·DB와 실제 S3 SDK의 로컬 HTTP는 사용하되, 사진 제공자는 외부 AWS 대신 내부 시험 서버이고 메일·AI와 자동 정리 작업은 대역이다.

Docker 내부 전용 네트워크에서는 직접 지정한 호스트 포트가 실제로 생기지 않아 첫 브라우저 연결이 실패했다. 앱·DB에 외부 경로를 추가하는 대신, 고정된 두 앱·사진 서버로만 전달하는 별도 Java 프록시를 사용했다. 앱의 외부 기본 경로 0개를 다시 확인했고 프록시에는 시험 클래스와 숫자 결과 폴더만 마운트했다. PC에는 loopback 포트만 공개했다. [Docker 유지관리자의 내부 네트워크 설명](https://github.com/moby/moby/discussions/53256)을 참고했다.

온보딩 안내와 겹친 실행, 화면 위치가 달랐던 실행은 최종 비교에서 제외했다. 같은 관찰 코드를 양쪽에 고정하고 측정 전에 본체를 중앙 정렬했으며, 화면 전체 노출·크기·배율·출력 버퍼를 각 결과에 기록했다. 최종 순서는 현재 구현 6회 → 초기 구현 6회이며, 이후 추가한 동작 확인 전환은 통계에 넣지 않았다.

최종 관측은 사진·그리기 준비까지 초기 구현 첫 385.5ms / 반복 5회 중앙값 68.4ms, 현재 구현 첫 951.3ms / 반복 중앙값 520.1ms다. GPU 완료·정확한 모니터 표시 시각이 아니다. 초기 구현은 632개의 삼각형과 평면 사진 합성이며 현재는 28,160개의 곡면 텍스처 방식이다. **같은 일을 최적화한 비교로 해석하지 않으며 전체 개선율을 계산하지 않는다.**

기능 확인·준비 실행 뒤 새 문서에서 측정했으므로 완전한 콜드 스타트도 아니다. 초기 구현은 이미 읽은 사진을 재사용해 전환 중 사진 서버 읽기가 0회였고 현재는 이미지 API 6회에 사진 서버 읽기 1회였다. 최종 실제 HTTP 검사 30항목에서는 두 버전의 같은 PNG 바이트·표시 필드와 현재 캐시 재사용 뒤 비회원 403·비로그인 401·잘못된 종류 400 및 거절된 요청의 사진 서버 미접근이 확인됐다.
