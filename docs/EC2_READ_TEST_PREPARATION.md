## 백업과 투입 전 검증

- 운영 appdb를 `--single-transaction --quick --routines --events --triggers --hex-blob`로 논리 백업했다.
- 서버에서 압축·완료 표시를 검사하고, PC의 프로젝트 밖 Downloads 전용 폴더로 복사해 SHA-256을 대조했다.
- 백업 경로·체크섬은 무시되는 `build/load-ec2/prep-20261018/backup.json`에 보관한다. DB 내용은 문서·로그에 출력하지 않는다.
- 외부 네트워크 없는 로컬 임시 MariaDB에 복원했다. 25개 InnoDB 테이블, V52, 실패 migration 0개를 확인했다.
- 운영에 투입할 동일 SQL을 복원 사본에서 실행해 중간 실패의 실제 SQLSTATE 45000 / 오류 1644 롤백,
  중복 생성 거절, 시험 행 정리 후 원래 25개 테이블의 checksum 일치를 확인했다.
- 준비 계획·SQL·원본 백업 checksum을 검증 기록과 연결한다. 다른 계획/SQL/백업을 투입하지 못하게 검사한다.
- 세션 정리 SQL도 복원 사본의 시험 세션으로 실행하고 기존 행 보존을 확인했다.

복원 검사는 논리 DB 범위다. EC2 전체 복원·S3 파일·DB 계정/권한·정기 백업 구축은 포함하지 않는다.

## 실제 API의 순차 기능 확인

- https://api.esjh.shop의 허용한 인증·조회 경로만 호출했다. 프록시·리다이렉트 추적 없이 TLS 검증을 유지했다.
- 한 번에 한 요청, 요청 사이 최소 0.5초로 계정 10개를 순서대로 로그인·내 정보·내 저금통 목록·로그아웃 확인했다.
- 한 계정으로 저금통 상세 3개·쪽지 목록 6개 페이지를 추가 확인했다.
- 인증 준비·로그아웃을 포함해 성공한 재확인에서 총 69개 요청, 그중 공유 응답 계약으로 검사한 조회 응답은 19개다.
- 계정 ID·역할·저금통 ID·멤버 수·쪽지 ID/순서·페이지 개수·첨부 없음 등이 예상값과 일치했다.
- 메일 인증·AI·Rekognition·S3 전송·사진·초대·실제 저금통 삭제 API는 호출하지 않았다.

**주의: 첫 기능 확인에서는 5초 제한의 시간 초과가 발생했다.**
최초 시도의 정확한 실패 지점과 원인은 확정하지 못했다. 무인증 HTTPS 조회 정상 여부를 확인하고,
단계별 비밀값 없는 진행 기록을 추가한 뒤 한 차례 순차 재확인했다. 재확인은 모두 성공했다.
실패를 숨기거나 응답 제한 시간을 늘려 통과시키지 않았다. 이 결과로 응답 지연 문제가 없다고 단정하지 않는다.

첫 실패에서 남은 전용 계정의 활성 Refresh Token 1개만 폐기했다.
실제 사용자 세션·sessionVersion은 바꾸지 않았다. 최종 활성 시험 Refresh Token은 0개다.
로그아웃/Refresh Token 폐기가 기존 Access JWT를 즉시 무효화한다는 뜻은 아니다.
시험 중 받은 JWT는 메모리에서만 사용하고 영구 결과 파일에는 저장하지 않았다.

## 자원 관측과 한계

준비 전 60초·순차 기능 재확인 중 90초를 별도 관찰했다.
후자에서 Heap이 한 표본에 약 75.4%로 기록됐다가 다음 표본에서 75% 아래로 내려왔다.
마지막 관측은 약 74.5%였다. 지속 30초 초과로 판정되지는 않았으며 재시작/OOM 변화 경고는 없었다.
강제 GC·서버 재시작·Heap/풀 크기 변경은 하지 않았다.
이것은 준비 작업 중 관측이지 안정적인 최대 처리량·메모리 회복·장기 누수 검증이 아니다.
첫 HTTPS 시간 초과와 Heap 여유는 실제 부하 전 다시 확인할 사항이다.
