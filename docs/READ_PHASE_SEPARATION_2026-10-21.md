# 계정 준비·조회 판정 분리와 재시험

작성일: **2026년 10월 21일**, 한국 시간. 실제 시험은 오후 15:09경에 실행했다.

## 결론

**준비·조회·정리 기록을 분리했다. 50 VU(동시에 반복 요청하는 가상 사용자 50명) 재시험을 시도했지만 첫 계정 로그인에서 시간 초과가 나 동시 조회는 시작하지 않았다.** 100·150·200·300 VU는 미실행이다.

이번 변경은 시험 절차와 기록 방식의 보완이다. 운영 서비스의 성능을 개선한 변경이 아니다. 과거 500ms·2초·5초 시도의 실패 기록은 그대로 보존했다.

## 무엇을 어떻게 바꿨나?

준비·조회·정리는 **같은 k6(부하 발생 도구) 실행 안의 순차 단계**다. 별도 프로세스에서 토큰을 미리 만들어 전달하는 방식으로 바꾸지 않았다. 준비 요청을 정상 검증한 뒤에만 조회 함수가 실행된다. 준비 단계도 기존 자원 감시 아래 있다.

결과 파일은 각각 `preparation-result.json`, `read-phase.json`, `cleanup-phase.json`, `session-cleanup.json`, `recovery-result.json`으로 분리했다. 조회 0건은 성공이나 조회 성능 실패가 아니라 **미시작**으로 기록한다. 준비 실패 시 후속 조회를 강행하거나 요청 제한을 늘리지 않는다.

새 라이브러리·인증 우회·API/DTO/DB 변경은 없다. 단계별 시간과 상태만 보고하고 사용자 ID·로그인명·비밀번호·쿠키·토큰·SQL 원문은 요약에 넣지 않는다. `account_index`는 실제 사용자 ID가 아닌 시험 내 순번이다.

## 연결·배포·준비 확인

처음에는 SSH(서버 접속 통로)가 시간 초과했다. 사용자가 보안 그룹 접속 규칙을 수정한 뒤 **기존 주소로 접속 성공**했다. 서버 주소가 바뀐 것으로 처리하지 않았다. 에이전트가 접속 허용 범위를 넓히거나 보안 그룹을 수정하지 않았다.

- 운영 커밋 `84d530153d79de0c4056220542290531b30f5dfb` 일치 확인.
- API 이미지 `sha256:7c067e9c42c31e43e2909bf7f57f6dc8b154b15b93198218de9c9f31bd2521a4`.
- API 기동 2026-10-21 01:17:11 KST, DB 기존 기동 상태 유지.
- 재시작 0회·OOM(메모리 부족 강제 종료) 표시 없음.
- 일반 포트의 관리 API 접근은 403으로 차단.
- JVM 메모리 옵션·DB 캐시·DB 풀 상한 10개 유지. 상세 조회 계측 OFF.
- 약 61초·11개 표본의 시작 전 자원 검사 통과.
- 최신 DB 백업 생성·PC 복사·해시(파일 일치 확인값) 검증 완료.
- 전용 시험 묶음의 데이터·세션 경계 확인.

## 실제 실행 결과

조건은 API별 p95(응답의 95%가 끝나는 시간) 목표 5초, 개별 요청 제한 5초, 조회 오류율 1% 미만, 예정 조회 60초였다. 기존 자원 중단·회복 조건은 완화하지 않았다.

| **첫 계정 로그인** | **약 5010.78ms 뒤 클라이언트 시간 초과, 상태 0** |

이 결과를 “50명 동시 조회를 서버가 못 버텼다”거나 “오류율 0%로 통과했다”고 표현하면 안 된다. 이번에는 준비 요청 2개 중 로그인 요청이 실패했고, 측정할 동시 조회 표본 자체가 없다.

### 서버에서는 로그인이 뒤늦게 끝났다

관리 지표의 해당 로그인 기록에서는 서버 내부 경과 약 **5359.41ms**, 서버 기록 상태 200이 확인됐다. 클라이언트는 그보다 먼저 5초 제한으로 요청을 포기했다. 따라서 서버 기록 200을 클라이언트 성공으로 바꾸지 않는다.

같은 기록의 비밀번호 검사 약 798.24ms, 자격 정보 조회 약 827.49ms, 인증 서비스 전체 약 1641.55ms, Refresh Token(로그인을 갱신하는 인증 정보) 저장 트랜잭션(함께 성공하거나 취소되도록 묶은 DB 처리) 약 1052.07ms였다. 서로 포함 관계가 있는 시간은 더하지 않는다. 일부 계측하지 않은 구간도 있으므로 하나의 단계만으로 전체 지연을 설명하지 않는다. 해당 요청의 JVM 전체 GC(불필요한 자바 객체 메모리 정리) 카운터·시간 증가는 0이었다. 모든 지연이 GC 때문이라는 주장도 하지 않는다.

이번 자원 표본에서 스왑(디스크에 보관한 메모리) 읽기와 디스크 대기도 관측됐다. 표본 간격상 요청 전체의 최고 압박을 포착했다고 보장할 수 없고, 원인이 완전히 해결됐다는 근거도 아니다.

### 늦게 만들어진 시험 세션 정리

실패 후 기존 절차대로 최소 30초 기다렸다. 서버가 뒤늦게 만든 활성 시험 세션 **1개를 전용 계정 범위에서만 무효화**했다. 5개 시험 묶음·50계정의 남은 활성 Refresh Token 세션은 모두 0개였다. 이미 발급된 Access Token(요청할 때 로그인 상태를 증명하는 인증 정보)의 즉시 무효화까지 의미하지 않으며 실제 두 사용자의 세션은 수정하지 않았다.

정리 뒤 약 **60.7초·11개 표본**의 자원 관찰은 기존 회복 조건을 모두 통과했다. 이것으로 준비 실패를 통과로 바꾸거나 장기 안정성 전체를 입증하지 않는다. 재시작·OOM 표시도 없었다.

## 단계 상승을 막는 방식

로컬 실행 제어기는 `50 → 100 → 150 → 200 → 300`의 직전 단계 결과와 회복 결과를 함께 읽는다. 둘 중 하나라도 실패하거나 준비 관찰이 오래됐으면 시작을 거절한다. 각 실행은 별도 백업·배포 식별값·소스 해시를 확인한다.

이번에는 50 VU 준비가 실패했으므로 상위 실행을 하지 않았다. 추가 로그인 재시도·서버 설정 변경·증설·재배포·커밋·푸시도 하지 않았다. 실제 Cloudflare AI·Rekognition·SES·S3 전송은 호출하지 않았다. 기존 EC2·통신·백업 비용까지 0원이라는 뜻은 아니다.

## 검증

- 관련 Node 검사 **39개 최종 통과**. 실제 k6 옵션 해석은 외부 HTTP 없이 검사했다.
- 로컬 단계 제어 검사 **3개 통과**: 선행 단계·회복 실패 거절, 잘못된 단계 거절, 빈 표본 실패.
- 첫 Node 검사에서는 새 150 VU를 비교하는 테스트가 과거 3초 모드로 호출해 1개 실패했다. 비교 대상을 기존 50 VU 기본 기준으로 고친 뒤 전체 39개를 다시 통과했다. 운영 장애나 과거 기록 변경은 아니다.
- `git diff --check` 통과.
- 운영 Java·프론트 코드 변경이 없어 해당 빌드는 실행하지 않았다.

## 다음 할 일

개선 전 조회 한계를 측정하려는 목표는 유지한다. 다만 이번 장애는 동시 조회 전의 **로그인 준비 지연**이다. 다시 같은 시험을 반복하거나 제한을 더 늘리기 전에, 해당 로그인의 남은 시간 구간·메모리 재접근·인증/세션 저장 대기를 읽기 전용으로 좁혀 확인해야 한다.

로그인 없이 조회를 강행하거나 인증 정책을 바꾸지 않는다. 사전 인증을 별도 실행으로 옮기는 설계를 선택한다면 토큰 만료·보관·정리·실패 판정과 측정 조건 차이를 먼저 검증해야 한다. 이번에는 그 방식으로 변경하지 않았다.
