# 문의 기능 확장 작업 기록

기존의 AI 실패 문의를 유지하면서 일반 문의·유형·추가 대화·해결/재개·선택 첨부·문제 화면 연결·비로그인 로그인 도움·FAQ를 구현했다. 최종 검증 집계는 아래 검증 결과 절에서 구분한다.

## 구현 기준

- V55까지 기존 마이그레이션을 유지하고 V56에서 확장한다. 기존 AI 접수/상세/답변 API와 응답 필드는 호환한다.
- 일반 문의는 사진·Draft·AI 후보 없이 접수한다. 유형과 제목, 내용, 요청 UUID를 사용한다.
- 메시지는 별도 테이블과 커서 페이지로 조회한다. 같은 요청 UUID는 한 번만 저장·알림 처리한다. 계정별 생성/메시지 제한과 문의별 잠금으로 중복·상태 경쟁을 보호한다.
- 기존 답변과 해결을 구분하고 추가 정보 대기·해결·재개를 제공한다. 기존 reply 필드는 유지한다.
- 첨부는 문의당 최대 3개·파일당 2MB. PNG/JPEG/WebP 단일 프레임을 실제 디코딩 후 메타데이터 없는 이미지로 저장한다. 이미지 처리는 동시 2건으로 제한한다. S3 호출 중 DB 잠금을 유지하지 않는다.
- 원본/첨부 30일, 본문/대화 90일 보관 기한을 적용하고 만료 즉시 조회를 제한한다. 파일 삭제는 기존 정리 작업에서 제한된 묶음으로 수행한다.
- 로그인 도움은 계정 로그인과 별개의 HttpOnly 쿠키로 본인 문의만 조회한다. 임의 요청으로 다른 계정·저금통·Draft를 연결하지 않는다. 원시 IP·쿠키·토큰을 로그나 응답 본문에 남기지 않는다.
- 비로그인 세션은 이 브라우저의 쿠키로 유지한다. 쿠키 삭제 시 자동 복구를 제공하지 않으며 화면에서 안내한다. 실제 이메일 발송은 추가하지 않는다.
- 기존 알림·권한·CSRF·CORS·요청 보호 패턴을 재사용한다. 설치 의존성은 추가하지 않는다.

## 검증 계획

권한/다른 사용자 차단, 기존 V49 데이터 호환, 대화·해결 경쟁, 중복 요청, 첨부 크기/내용/개수/외부 실패, 익명 세션·접수 제한, PC/모바일 화면을 검사한다. 실제 S3/메일/AI/운영 DB 대신 격리된 대역과 임시 MariaDB를 사용한다.

300명은 300개의 계정으로 실제 API를 동시에 이용하는 로컬 시험으로 기록한다. 오류율·응답 분포·서버 자원·시험 조건과 요청 구성을 함께 남긴다. 로컬 결과를 운영 환경의 보장으로 표현하지 않는다.

## 2. 기존 동작

AI 생성이 실패한 후보에서만 원본 공유 동의와 함께 문의할 수 있었다. 운영자는 최초 답변을 한 번 남겼고, 문의자가 같은 문의 안에서 추가 설명하거나 해결 여부를 표시할 수 없었다. 일반 문제와 로그인 실패에는 별도 접수 경로가 없었다.

## 3. 바뀐 사용자 흐름

|---|---|

| 유형 선택 | 사진 업로드 / AI 생성·결과 품질 / 3D 표시 / 쪽지·댓글·채팅 / 초대·권한 / 사용 방법 / 기능 제안 / 기타 / 로그인·계정 |
| 추가 대화 | 문의 상세에 설명을 이어 쓰고 운영자가 답변. 운영자는 추가 정보가 필요하다는 상태 표시 가능 |
| 해결·재문의 | `해결됐어요`로 닫고, 계속 문제가 있으면 `아직 문제가 있어요 · 다시 문의`로 같은 대화 재개 |

| 문제 화면 연결 | 공통 `도움말·문의`에서 저금통/Draft/허용 경로·오류 코드·발생 시각 연결. 전송 전 제외 가능 |

첨부 실패 시 “문의 본문은 접수됐고 일부 첨부만 실패했다”고 표시한다. 재시도는 같은 문의에 파일만 추가하며 본문을 새로 접수하지 않는다. 이미 저장된 첨부가 있는 경우에도 대화만 재전송할 수 있다.

## 4. 이렇게 나눈 이유

문의 접수, 운영자 답변, 실제 문제 해결은 서로 다른 시점이다. 답변이 왔다는 이유만으로 해결된 것으로 처리하지 않았다. 기존 AI 실패 기록과 원본 공유 흐름은 그대로 두고, 일반 문의만 새 진입점으로 연결했다. 대화와 파일을 문의 본문과 별도 테이블에 두어 한 번에 모든 내용을 읽거나 큰 파일을 DB에 저장하지 않는다.

로그인 실패 문의는 계정 인증을 대신하지 않는다. 문의 쿠키를 가진 브라우저가 자기 문의만 읽으며, 비밀번호 변경·계정 복구·다른 회원의 자료 조회 권한은 주지 않는다. 쿠키 분실 시 다른 브라우저로 복구하는 기능은 이번 범위에 없다.

## 5. 성능·보안·유지보수 보호

- **중복 방지:** 접수·대화의 UUID와 DB 유일 제약을 함께 사용한다. 같은 요청의 답이 유실되어 다시 보내도 본문·알림은 한 번만 저장한다. 같은 UUID의 다른 본문은 충돌로 알린다.
- **동시 요청:** 생성 제한 키 → 기존 사용자/Draft 또는 문의 → 첨부 순서로 잠근다. 일반/AI 문의가 동시에 와도 합산 접수 한도를 지킨다. 해결과 대화 저장도 같은 문의 행을 잠근다.
- **고정 조회:** 최초 상세는 문의·대화·첨부를 한 HTTP 응답으로 반환한다. 일반 사용자 서비스 조회는 대화 개수와 관계없이 SQL 3개다. 인증 필터의 세션 확인 쿼리는 이 숫자에 포함하지 않는다.
- **유한한 페이지:** 목록 12개, 대화 20개, 문의별 대화 최대 100개, 유효 첨부 최대 3개다. 운영 목록도 전체 일괄 로딩을 하지 않는다.
- **외부 저장 분리:** 파일을 예약한 뒤 DB 트랜잭션 밖에서 검사·S3 저장하고 다시 짧게 확정한다. 확정 결과를 잃어도 READY 상태면 보존한다. 실패 키도 추적해 이후 삭제를 재시도한다.
- **이미지 제한:** 파일 2MB, 실제 해상도 12MP·한 변 8,000px 이하, 정지 PNG/JPEG/WebP만 허용한다. 최대 1,600px PNG로 다시 저장해 메타데이터를 없애고 JPEG 방향은 유지한다. 처리 중 이미지가 2개면 추가 요청은 429로 재시도를 안내한다. 무제한 대기열을 만들지 않는다.
- **기간 제한:** 본문·대화 90일, 사진 최대 30일. 조회 때 기한을 먼저 검사한다. 정리 작업은 제한된 묶음으로 삭제하며 외부 삭제 실패 시 완료로 표시하지 않는다.
- **접근 제한:** 문의당 본인/서버 지정 운영자/해당 문의 쿠키만 허용한다. 타인 문의는 404다. 첨부는 클릭한 뒤에만 최대 60초 URL을 요청한다. 운영자의 사진 열람은 감사 기록에 남긴다.
- **비로그인 보호:** 새 문의 쿠키 원문 대신 SHA-256 해시만 DB에 저장한다. IP·요청 주체 제한 키는 목적별 HMAC을 사용한다. 쿠키는 HttpOnly·호스트 전용·SameSite=Lax이고 Secure는 기존 설정을 따른다. 비로그인 변경도 CSRF를 검사한다.
- **화면 전환 보호:** 떠난 화면과 이전 계정의 늦은 응답은 이동·내용·오류 상태를 바꾸지 않는다. 첨부 읽기/전송 중 중복 제출을 막고 이전 대화와 빈 상태를 구분한다.
- **의존성:** 새로운 라이브러리를 추가하지 않았다. 기존 API 계층, 요청 보호, MariaDB/Flyway, AWS SDK, 이미지 디코더와 알림 흐름을 재사용했다.

| 제한 | 값 |
|---|---|
| 로그인 사용자 생성 | 일반/기존 AI 합산 10건/시간 |
| 로그인 도움 생성 | 세션당 5건/시간 |
| 추가 대화 | 문의자당 50건/시간, 운영자당 1,000건/시간 |
| 첨부 시도 | 주체당 20건/시간 |
| 비로그인 세션 신규 발급 | 서버 관측 IP당 60건/시간, 전체 1,000건/시간 |

운영자는 300명의 문의에 답할 수 있도록 개인 문의자보다 대화 한도를 높였지만 무제한으로 열지는 않았다. 프록시 주소를 클라이언트가 임의 지정한 헤더로 바꾸지 않는다. 운영의 실제 클라이언트 주소 전달 정책은 배포 환경에서 별도로 확인해야 한다.

## 6. 실행한 검증

```powershell
# 전체 백엔드 회귀 및 빌드
./gradlew.bat test bootJar jar --console=plain

# 문의 최종 변경 관련 재검증
./gradlew.bat test --tests '*Support*Test' --console=plain

# 외부 연결 없는 임시 DB/HTTP 시험. 마지막에 해당 실행의 컨테이너와 네트워크 정리
./tools/isolated/run-e2e.ps1 -Support300

# frontend 폴더에서 단위 테스트/운영용 빌드
node --test src/**/*.test.mjs
node node_modules/vite/bin/vite.js build

# 로컬 Vite 서버가 준비된 뒤 Chrome 검사
node tests/support-expansion.browser.cjs
node tests/account-safety.browser.cjs
node tests/round4-races.browser.cjs
node tests/ui-readability.browser.cjs
```

브라우저 검사는 `PLAYWRIGHT_MODULE`(기존 설치 경로)과 `TEST_BASE_URL`(로컬 Vite 주소)을 사용한다. 실제 S3·메일·AI·운영 DB는 호출하지 않는다. V55 기존 문의/답변을 넣은 뒤 V56으로 올리는 검사, 권한/중복/동시 제한/해결 경쟁/유효 기한/외부 저장 실패와 원본 방향 보존을 포함한다.

| 백엔드 `bootJar`·`jar`, 프론트 Vite 빌드 | 통과. Vite의 500kB 초과 청크 안내 경고는 남음 |
| 기존 V55 → V56 이관 | 기존 문의·최초 답변·알림 유지, 답변을 대화로 이관, 일반 문의 NULL 허용·소유자 제약 통과 |
| 상세 조회 수 | 대화 0개/45개 모두 일반 사용자 서비스 SQL 3개 확인 |

전체 회귀의 조건부 제외 6개는 별도 환경에서 켜는 HTTP·WebSocket 4개, 조회 부하용 1개, 이번 300명 시나리오 1개다. HTTP·WebSocket 4개와 300명 1개는 위와 같이 별도 격리 환경에서 실행했다. 이전 조회 부하 시나리오 1개는 이번 범위에 포함하지 않았다. 조건부 제외를 통과 수에 더하지 않았다.

권한·잘못된 입력·중복 접수/대화·기존/일반 접수 합산 한도·해결 경쟁·게스트 격리·CSRF·보안 쿠키·첨부 크기/내용/개수/기한·애니메이션 거부·외부 저장/삭제 실패·미확정 결과 복구·실제 정적 WebP 디코딩과 기존 JPEG 방향 보존을 확인했다. 브라우저에서는 선택 취소, 일부 첨부 실패 후 같은 문의로 재시도, 떠난 화면/다음 계정에 늦은 응답 미반영도 검사했다.

### 최종 300명 동시 이용 시험

실행 ID는 `memoryjar-e2e-9c0d4c917c22`다. 임시 MariaDB 10.11과 애플리케이션을 Docker internal 네트워크에 연결했다. 운영 DB나 호스트 DB를 사용하지 않고, 완료 후 이 실행에서 만든 컨테이너·네트워크가 각각 0개임을 확인했다.

앱/HTTP 발생기는 같은 컨테이너(2 CPU·메모리 상한 1,536MiB·JVM Xmx768MiB), DB는 별도 컨테이너(메모리 상한 512MiB·tmpfs)다. DB 풀 크기는 기존 10개를 유지했다. HTTP 발생기와 앱이 CPU·메모리를 공유하므로 독립 부하 발생기로 측정한 운영 기준값은 아니다.

가짜 사용자 300명과 운영자 1명을 생성하고 실제 JWT 서명·DB 세션 버전 검사·CSRF 필터·Controller·Service·DB를 통과시켰다. 토큰은 시험 데이터에서 발급했으므로 300명의 비밀번호 로그인 비용을 포함하지 않는다. 실제 메일·S3·AI 클라이언트는 대역이며 호출하지 않았다. 첨부는 별도의 동시성·실패 테스트에서 검사했다.

각 단계에서 300건을 함께 시작하고, 그 단계가 끝난 뒤 다음 단계로 진행했다. 최고 미완료 요청 수는 300이었다. 접수 → 같은 UUID 재전송 → 목록 → 상세 → 대화 → 같은 대화 재전송 → 운영자 답변 → 해결 → 재개 → 최종 상세와 CSRF 준비를 검사했다.

| 결과 | 관측값 |
|---|---:|
| 기록한 HTTP 요청 | **3,301건** |
| 정상 200 응답 | **3,301건** |
| 예상하지 않은 오류·5xx·타임아웃 | **0건** |
| 소요 시간 | 약 43.83초 |
| 로그인 사용자 문의 | 300건, 중복 접수 없음 |
| 사용자 추가 대화 | 300건, 중복 재전송 저장 없음 |
| 운영자 답변 | 300건 |
| 새 문의 알림·운영자 답변 알림 | 각각 300건 |
| 샘플링한 JVM Heap 최고값 | 약 198.3MiB |
| 샘플링한 DB 연결 대기 최고값 | 190건 |

비로그인 쿠키·CSRF·잘못된 입력·FAQ의 추가 HTTP 검사는 위 3,301건 분포와 별도로 통과했다. Heap·연결 대기는 200ms 간격의 관측값이라 순간 최고값을 보장하지 않는다.

p50은 가운데 응답, p95는 95%의 요청이 그 시간 안에 끝났다는 뜻이다. 이 시험은 **300명이 동시에 같은 종류의 작업을 누르는 순간적인 집중 요청**이다. 오류가 없었다는 결과와 빠르다는 평가는 다르다. 접수·대화 저장의 수 초 대기를 확인했으므로 “300명에게 즉시 응답한다”거나 “운영에서도 같은 속도를 보장한다”고 쓰지 않는다. 이 시험만으로 연결 대기의 내부 CPU/SQL 비용을 단정하거나 DB 풀을 무작정 키우지 않았다.

원본 숫자·자원 샘플·외부 연결 차단·정리 결과는 `build/isolated-e2e-results/memoryjar-e2e-9c0d4c917c22/`에 있다. 컨테이너 샘플링 메모리는 앱/발생기 최고 약 701.9MiB, DB 최고 약 351MiB였다. 이는 JVM Heap과 다른 지표다.

공개할 수 있는 숫자와 해시만 [검증 요약 JSON](support-expansion-verification-2026-11-02.json)에 보관했다. 소스 666개 파일의 검증 중 변경 여부를 확인했고, 백엔드 빌드의 모든 main 클래스가 실행용 격리 번들·일반/실행 JAR과 일치함을 검사했다. 로컬 비밀 설정 파일은 JAR에 없으며, `application-prod.yml`은 저장소의 환경변수 참조 템플릿과 일치한다. Git HEAD는 작업 전 기준일 뿐 현재 미커밋 변경까지 포함한 산출물의 커밋 번호로 표현하지 않는다.

실행 로그·XML·소스 해시 목록·합성 화면 캡처는 `build/support-expansion-2026-11-02/`에 남겼다. 운영 이미지·쿠키·개인 문의를 이 문서나 요약 JSON에 복사하지 않았다.

## 8. 아직 확인이 필요한 범위

로컬 임시 DB와 가짜 외부 서비스로 검증한다. 운영 Flyway 적용·실제 비공개 S3 첨부 저장/열기/만료 삭제·실제 프록시와 HTTPS 쿠키 동작은 배포 후 확인 대상이다. 새 저장 접두사는 `support-attachments/`이므로 운영 S3 권한과 수명주기 정책이 이 경로를 포함하는지도 확인해야 한다. 이번 작업에서 운영 설정을 바꾸거나 배포하지 않았다.

300명 시험은 **동시 인증 사용자 API 이용**이다. 300건의 이미지 업로드를 모두 즉시 처리하거나 300개의 3D 화면을 서버에서 그리는 시험이 아니다. 파일 처리 포화 시 429로 제한하는 것은 의도한 보호 동작이다. 로컬 시험은 운영의 인원·응답 시간 보장이 아니다.

관리자 메일 알림은 이번 수정에 추가하지 않았다. 현재 코드는 사이트 알림을 저장한다. 기존 SES 발송 기반을 확장하면 서버가 지정한 운영자의 가입 이메일로 접수 알림을 보내는 기능을 만들 수 있다. 이를 추가할 때는 문의 저장 후 발송·재시도·중복 방지를 따로 설계해야 한다.

검증 완료 시점에는 커밋·푸시·배포를 수행하지 않았다. 이후 사용자의 별도 요청으로 검증한 소스·테스트·문서를 커밋하고 푸시하며, 운영 배포 성공 여부는 이 로컬 검증 결과에 포함하지 않는다.
