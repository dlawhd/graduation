# 내 정보·조회 요청 단계별 시간 계측

작성일: 2026년 10월 20일, 한국 시간 기준.

## 목적과 현재 상태

50 VU(동시에 요청하는 가상 사용자 50명) 시험 준비 중 내 정보 조회가 약 4.61초 걸렸다. Nginx(요청을 자바 서버로 전달하는 프로그램)에서도 응답 대기 약 4.526초가 확인됐다. 그 뒤 약 1분 46초 떨어진 조회 구간에서는 DB 연결 10개 사용·대기 2개 표본이 있었다.

기존 상세 기록은 로그인·CSRF(다른 사이트의 몰래 요청을 막는 보안표) 요청만 포함했다. 따라서 위 두 현상을 특정 SQL이나 메모리 정리 하나로 확정할 수 없었다. 이번 변경은 원인을 구분하기 위한 **측정 기능**이며 지연을 해결하는 성능 수정이 아니다.

코드·시험·문서만 준비한다. 커밋·푸시·운영 배포·진단 활성화·추가 로그인·지속 부하는 별도 단계다. 기본 조회 계측은 꺼져 있다.

## 무엇을 나눠서 재나?

| 구간 | 기록 | 포함 범위와 주의점 |
| --- | --- | --- |
| 요청 전체 | 고정 요청 종류·시작/종료 시각·경과 시간·상태·예외 종료 여부 | 진단 필터 진입부터 반환까지. 진입 전 서버 큐와 PC 네트워크는 포함하지 않음 |
| 인증 | JWT_VALIDATE, JWT_CLAIMS_PARSE, SESSION_VERSION_QUERY | 원래 토큰 검증·파싱·세션 버전 확인 호출을 유지 |
| 서비스 | ME_SERVICE, JAR_LIST_SERVICE, JAR_DETAIL_SERVICE, NOTE_LIST_SERVICE | 컨트롤러가 호출하는 서비스 프록시 전체. 트랜잭션 시작·종료도 포함 |
| 연결 획득 | CONNECTION_ACQUIRE의 횟수·합계·최댓값 | Hibernate(자바 객체와 DB를 연결하는 도구)의 연결 획득 콜백. 풀 대기와 연결 제공 처리 등을 포함하며 순수 대기 시간만은 아님 |
| SQL 준비 | STATEMENT_PREPARE | JDBC(자바의 DB 통신 기능) 문장 준비 호출 시간 |
| SQL 실행 | STATEMENT_EXECUTE, BATCH_EXECUTE | 문장/묶음 실행 호출 횟수·합계·최댓값. SQL 원문·파라미터·결과는 기록하지 않음 |
| 단계별 DB | databaseByStage | 인증 세션 확인과 조회 서비스의 DB 시간을 구분. 가장 안쪽의 측정 단계에만 귀속 |
| GC | 기존 JVM 전체 누적 시간·횟수 차이 | GC(쓰지 않는 자바 객체 메모리 정리)는 다른 요청과 겹칠 수 있어 요청 전용 정지 시간으로 보지 않음 |

시간은 나노초이며 1,000,000으로 나누면 밀리초다. 중첩된 서비스·인증·DB 시간은 서로 겹치므로 단순 합산하지 않는다. 단계가 없는 DB 콜백은 요청 전체 database에만 기록한다.

Hibernate 콜백이 끝난 구간만 집계한다. 빈 database 맵은 콜백 기록이 없다는 뜻이지 DB 처리가 0ns였다는 뜻이 아니다. JDBC 실행 시간은 DB 내부 계산·네트워크·OS 대기 등을 포함할 수 있고, 결과 목록 전체 변환이나 모든 커밋 시간을 따로 재는 값은 아니다. 직접 JdbcTemplate/JDBC 호출과 비동기 스레드는 이 Hibernate 계측의 범위 밖이다. 서비스 전체와 요청 전체 시간으로 남은 구간을 비교한다.

## 대상과 보안

추가 대상은 다음 GET 요청만이다.

- `/api/v1/me`
- `/api/v1/jars`
- `/api/v1/jars/{숫자 ID}`
- `/api/v1/jars/{숫자 ID}/notes`

Servlet 컨텍스트 경로도 고려한다. 세부 ID·검색어·원문 URI·헤더·본문·이메일·사용자 정보·토큰·SQL·예외 메시지는 저장하지 않는다. 요청은 ME/JAR_LIST/JAR_DETAIL/NOTE_LIST라는 고정 분류로만 남긴다. 쓰기·댓글·다른 상세 경로는 추가하지 않는다.

기존 인증 검사·예외·트랜잭션·일반 API 응답 DTO·DB 구조·관리 포트 보호는 변경하지 않는다. 새 의존성이나 DB 연결 래퍼도 없다. ThreadLocal(현재 요청의 실행 스레드에 붙이는 임시 기록)은 finally에서 제거하고, 이전 요청에서 시작한 DB 측정이 다른 요청에 귀속되지 않도록 검사한다.

## 메모리·보관 상한과 누락 표시

고빈도 조회가 로그인 기록을 밀어내지 않도록 저장 공간을 분리했다.

| 위치 | 상한 | 내용 |
| --- | ---: | --- |
| `loginDiagnostics.recent` | 기존 64개 | 로그인·CSRF. 기존 의미 유지 |
| `loginDiagnostics.reads.recent` | 64개 | 최근 조회 요청 |
| `loginDiagnostics.reads.slow` | 32개 | 500ms 이상이거나 오류 상태·예외 종료인 조회 |

slow는 별도 보관함이므로 이후 빠른 요청이 많아도 느린 요청이 바로 사라지지 않는다. 하지만 32개를 넘는 느린/오류 기록까지 무제한 보존하지 않는다. 완료 기록 수·recent 퇴출 수·slow 퇴출 수도 공개해 누락을 숨기지 않는다. completedCount는 성공 건수가 아니라 **종료 처리한 기록 수**이며 JVM 기동 이후 누적이다.

5초 수집 간격 사이에 recent에서 밀려난 빠른 요청은 상세 기록이 없을 수 있다. 모든 HTTP 응답의 오류율·p95는 기존 k6 원본으로 계산해야 한다. 이 메모리 버퍼만으로 전체 요청 수나 성능 합격 여부를 판정하면 안 된다.

분석기는 recent·slow의 중복을 JVM 식별값+진단 ID로 제거한다. 서버가 교체되면 ID가 같아도 구분한다. 구버전 자료에 조회 필드가 없으면 미측정(null)이며 false/0으로 바꾸지 않는다. 기존 로그인·CSRF 집계와 실패 판정은 유지한다.

요청별 시간 측정·GC 카운터 조회·관리 응답 직렬화의 비용이 추가된다. 메모리 상한이 있어도 비용이 0인 것은 아니다. 진단을 켠 결과와 이전 계측 조건이 다른 결과를 섞어 개선율을 계산하지 않는다.

## 활성화와 배포 순서

1. 이번 코드를 조회 계측 기본 꺼짐 상태로 먼저 검증·배포한다. 커밋·푸시·배포는 별도 승인 후 수행한다.
2. 새 이미지·기동 상태·Heap·DB 캐시·관리 포트 보호를 확인한다.
3. 필요할 때 별도 승인으로 `APP_MONITORING_READ_DIAGNOSTICS_ENABLED=true`를 진단 설정에 추가하고 API만 재생성한다. DB나 풀 크기·포트는 바꾸지 않는다.
4. 내부 `/actuator/resources`의 `loginDiagnostics.reads.enabled=true`와 새 요청의 실제 DB 기록을 확인한다. 로그인 계측의 기존 플래그와는 별개다.
5. 전용 계정의 소량 요청으로 시작해 인증·서비스·연결 획득·SQL 실행·GC·스왑을 비교한다. 지연 구간을 좁힌 뒤 지속 부하 여부를 정한다.
6. 진단을 마치면 조회 플래그를 제거/해제하고 API만 재생성한 뒤 비활성 상태를 확인한다.

예제: `tools/monitoring/read-diagnostics.override.example.yml`. 예제 파일을 운영에 자동으로 복사하지 않는다.

자동 배포 도구는 실행 중 환경과 Compose가 이미 일치한다는 전제다. 새 플래그를 파일에만 먼저 추가하면 `RUNNING_ENV_DIFFERS_FROM_COMPOSE`로 중단될 수 있다. 활성화는 정상 자동 배포와 구분한 설정 변경 단계다. 조회 계측을 모르는 구버전 상태에서는 활성 진단 배포의 기준본 검사를 거절해, 지원하지 않는 이전 이미지로 원복해야 하는 위험을 줄인다.

배포 도구는 진단 override에서 기존 로그인 true 외에 조회 true만 추가 허용한다. 이미지·DB·볼륨·포트 변경은 계속 거절한다. 기존 GC 조정 도구처럼 별도 엄격한 설정 검사가 있는 도구를 임의로 우회하지 않는다.

## 검증 기록

최종 결과는 검사가 끝난 뒤 이 절에 기록한다. 선별 Java 검사와 Node 집계, 배포 도구 모의 검사부터 실행했다. 첫 전체 검사에서 시험 전용 엔티티가 다른 DB 검증에 섞이는 문제를 발견해, 엔티티 없이 실제 Hibernate native query와 메모리 DB로 연결 대기 검사를 바꿨다. 그 전 결과를 최종 코드의 통과 결과로 사용하지 않는다.

실제 HTTP 시험은 내부 Docker 네트워크의 폐기용 MariaDB와 외부 서비스 대역으로 실행했다. 내 정보·저금통 목록·상세·쪽지 목록에서 인증·서비스·DB 콜백·단계별 DB 귀속이 확인됐다. 내 정보 요청에서는 세션 버전 확인과 서비스 조회의 DB 기록이 각각 분리됐다. 이는 작은 로컬 시험 자료에서의 연결 검증이지 운영 쿼리 지연이나 처리량 측정 결과가 아니다.

일반 포트 관리 지표 403·내부 관리 읽기·민감 관리 경로/쓰기 차단과 개인정보 비포함 검사가 통과했다. 시험 컨테이너에는 공용 IPv4/IPv6·메타데이터 TCP 접근이 차단됐으며 호스트 방화벽 전체나 DNS 차단까지 검증했다는 뜻은 아니다. 생성한 시험 컨테이너·네트워크 잔존은 0개였다.

원본: `build/isolated-e2e-results/memoryjar-e2e-39f41c6d74ee/summary.txt`, `resources.json`, `egress.txt`. 이 경로는 Git 제외 영역이며 통째로 공개하지 않는다. 나머지 격리 조회 부하 전용 1개는 이번에 별도 실행하지 않았다.

최종 검사 구간의 관련 소스·시험·도구 18개 합성 SHA-256은 `31e139aeaf8b4cf217872cd6c37c7531ade9b1fd13a8a50a5e64c1d9db928fce`이며 검사 후 일치했다. 문서 2개는 이 소스 지문과 별도다. Git 기준은 `e6f9390` 위 미커밋 작업 폴더다.

추가 주의사항: 전체 테스트 종료 과정에서 스케줄러가 이미 닫힌 H2 메모리 DB의 JARS 테이블을 조회하는 오류 로그가 있었다. JUnit 실패·오류는 0개였지만 종료 로그까지 오류가 없었다고 표현하지 않는다. 이 종료 순서 문제의 운영 영향·기존 기준본 재현 여부는 별도 확인 대상이며 이번 계측 변경에 섞어 임의 수정하지 않았다. 컴파일의 일부 사용 중단 예정 API 경고도 남아 있다.

처음 전체 실행은 시험 전용 `read_diagnostics_probe` 엔티티 혼입으로 DB 구조 검증에서 281개 실패가 발생했다. 원인을 제거하고 최종 코드 전체를 다시 실행해 위 결과를 얻었다. 또한 최초 Python 배포 모의 검사는 샌드박스의 임시 파일 교체 권한 때문에 실패했고 필요한 로컬 권한으로 재실행해 통과했다. 이 과정을 운영 장애나 성능 결과로 해석하지 않는다.

프론트엔드·DB 스키마·일반 API DTO·인증 정책은 변경하지 않았다. UI 빌드·커밋·푸시·운영 배포·플래그 활성화·운영 부하 시험은 수행하지 않았다.

운영에서 지연이 해결됐다고 주장하거나 100 VU 이상을 실행하지 않는다. 이번 단계의 완료 기준은 **안전한 계측 코드와 로컬 검증**이며 실제 원인 판정은 새 계측 배포·활성화 뒤에 해야 한다.
