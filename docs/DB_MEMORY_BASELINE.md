# 부하 측정 전 DB 메모리 설정 보존

## 목적과 범위

2026-10-18 소량 인증 재시험까지 사용한 DB 캐시 값을 기본 운영 Compose(컨테이너 실행 설정 파일)에
보존한다. 성능 개선이 새로 발생했다는 의미는 아니며, 이후 측정 조건이 우연히 바뀌지 않게 하는 작업이다.
일반 API·프론트엔드·DB 스키마·인증 제한 시간·JVM 설정·부하 합격 기준은 변경하지 않는다.

| 설정 | 보존 값 | 설명 |
| --- | --- | --- |
| key_buffer_size | 8MiB | MyISAM 테이블의 인덱스 캐시 |
| aria_pagecache_buffer_size | 32MiB | Aria 엔진의 페이지 캐시. 내부 임시 처리에도 사용될 수 있음 |
| innodb_buffer_pool_size | 128MiB | InnoDB 데이터·인덱스 캐시. 기존 기본값 유지, 새 명령 옵션은 추가하지 않음 |

현재 앱 테이블 25개는 앞선 검사에서 모두 InnoDB였다. 다른 캐시가 전혀 사용되지 않는다는 뜻은 아니다.
서버 전체 메모리는 약 914MiB이며 자바·DB·운영 도구·OS가 공유한다. 이 설정만으로 스왑이나 지연이
해결됐다고 판단하거나 300명의 처리 능력을 보장하지 않는다.

## 변경 전

실행 중인 DB는 임시 `change.override.yml`에 의해 아래 명령으로 실행됐지만,
`/home/ubuntu/deploy/docker-compose.prod.yml`에는 DB 명령이 없었다.
API 전용 자동 배포는 DB를 유지하지만, 이후 기본 파일만 사용해 DB를 재생성하면 캐시 값이 달라질 수 있었다.

```yaml
services:
  db:
    command: ["mariadbd", "--key-buffer-size=8M", "--aria-pagecache-buffer-size=32M"]
```

전체 운영 Compose는 인증정보가 포함될 수 있으므로 저장소로 복사하지 않는다.
위 명령만 기본 파일의 `db`에 추가하고 기존 환경·포트·이미지·볼륨은 유지한다.

## 안전한 반영 도구

`tools/deploy/persist-db-memory.py`는 EC2의 고정 경로만 처리한다.

1. API 배포 도구와 같은 잠금을 사용해 동시 변경을 막는다.
2. 파일 소유자·수정 권한과 실행 중 DB 명령·실제 세 캐시 값을 확인한다.
3. 같은 폴더에 임시 후보를 만들고 실제 Docker Compose 해석 결과가 DB 명령 외에 동일한지 비교한다.
4. 기본 실행은 사전 검사만 한다. `--apply --expected-sha256 <검토한 원본 해시>`가 있어야 반영한다.
5. 원본은 서버 내부에 권한 600으로 백업하고 기본 파일을 원자적으로 교체한다.
   반영 파일도 권한 600으로 강화한다. API·DB를 중지하거나 재생성하지 않는다.
6. 파일 해석 결과·컨테이너 식별값·실제 캐시를 재확인한다. 실패하면 자신이 쓴 파일만 원본으로 복원한다.
   다른 작업자의 파일이 이미 들어왔으면 덮어쓰지 않는다.

원복이 필요하면 출력된 백업 경로를 확인하고, 이후 다른 편집이 없었는지 먼저 검토해야 한다.
파일 원복은 실행 중 DB 설정을 바꾸지 않는다. DB 재생성·재부팅과 복구 검증은 별도 작업이다.
정전·디스크 장애까지 자동 복원을 보장하는 도구는 아니다.

## 2026-10-18 반영 결과

- 사전 검사 및 반영 후 Compose 해석 결과에서 두 캐시 명령 외의 차이 없음.
- 기본 파일 해시: `74adf1f6bd5b9dad5d68c0d422bfcc5b627fece319939dff781d1c9267e52601`
  → `ca59060a58253aa6f5c1e9d078dc2f9ec0301ee8bc19e12d7399efd24507977b`.
- 서버 내부 원본 백업을 남겼다. 백업 내용과 운영 인증정보는 저장소에 포함하지 않는다.
- API·DB 식별값·이미지·기동 시각·재시작·메모리 부족 종료 상태와 실제 캐시 값은 유지됐다.
- 로컬 및 EC2 Linux에서 배포 도구 검사 24개 통과. 로컬 배포 경로 검사 2개 통과.
  최초 로컬 제한 환경에서는 파일 교체 권한 오류가 있었고, 권한을 허용한 재실행에서 통과했다.
- 실제 DB 재생성이나 재부팅 후 적용 검사는 하지 않았다. 기본 파일의 해석 결과와 실행 중 값이
  일치함을 검증한 것이며, 새 DB를 실제 기동해 확인한 것은 아니다.

## 다른 임시 상태와 다음 단계

- 로그인 상세 계측은 서버의 별도 `docker-compose.diagnostics.yml`로 활성화한다.
  기본 꺼짐 정책과 내부 관리 포트 보호를 유지하며 API 배포 도구가 이 파일을 검증한다.
- BuildKit(이미지를 빌드하는 도구) 컨테이너는 중지 상태이고 캐시·이미지·볼륨은 보존한다.
  EC2 배포와 이미지 빌드는 분리돼 있다. 필요하면 명시적으로 다시 시작할 수 있다.
- multipathd(여러 저장장치 경로를 관리하는 서비스)의 서비스·소켓은 임시 중지 상태다.
  부팅 활성화 설정은 유지하며 이번 작업에서 영구 비활성화나 재부팅을 하지 않는다.
  부하 시험 직전에 해당 상태를 다시 확인하고 기준본에 기록해야 한다.
- 다음은 요청 범위에 따라 한국어 커밋·푸시, 배포 확인, 자원과 자동 중단 장치 재확인,
  측정 기준본 고정 후 10 VU(동시에 동작하는 가상 사용자 10명) 조회 시험이다.
  자동 배포의 일시적 요청 실패 가능성이 있으므로 파일 보존과 실제 배포를 구분한다.
