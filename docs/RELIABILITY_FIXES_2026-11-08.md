# 로그인·저장 재시도·파일 정리·실시간 배달 안전성 보강

작업일: 2026-11-08. 대상: `C:/Users/whdgu/Desktop/graduation`의 `main`, 시작 커밋 `6840dd2` 이후 로컬 변경.
이 문서는 로컬 수정·검증 시점의 기록이다. 운영 서버·DB·S3는 직접 변경하지 않았다.
후속 커밋·푸시로 시작되는 자동 배포의 완료 여부는 이 로컬 검증과 구분한다.

## 1. 여러 탭의 로그인 갱신

예전에는 한 탭 안에서만 갱신 요청을 합쳤다. 같은 로그인 쿠키를 쓰는 두 탭이 동시에 갱신하면 한 요청이 실패할 수 있었다.

`frontend/src/api/authRefreshCoordination.mjs`와 `apiClient.js`에서 같은 출처의 탭들이 Web Locks(브라우저가 제공하는 탭 사이의 순서 대기 기능)를 사용하도록 했다.
차례를 얻은 탭은 `/me`로 현재 로그인을 확인한다. 앞 탭이 이미 갱신했으면 토큰을 다시 회전시키지 않고 원래 요청만 재시도한다.
한 탭 안의 `refreshPromise`도 유지한다. 서버의 토큰 1회 사용·회전 규칙은 바꾸지 않았다.

로그인·로그아웃 경계는 BroadcastChannel로 변경 신호만 전달한다. 다른 탭의 이전 계정 요청은 취소하고 기존 계정 화면을 비운다.
토큰·쿠키·회원 정보는 이 채널이나 로컬 저장소에 넣지 않는다. 단순 갱신 성공은 계정 변경으로 알리지 않는다.
Web Locks 미지원 환경에서는 갱신 401 뒤 유효한 세션이 있는지 다시 확인하는 보완 경로를 사용한다. 이는 Web Locks의 탭 간 직렬화와 같은 보장은 아니다.

## 2. 저장됐지만 응답을 못 받은 쪽지

`NoteCreateRequest`에 선택 `requestId`를 추가했다. 프론트 `NoteSection.jsx`는 같은 내용의 재시도에 같은 번호를 유지하고 내용이 달라지면 새 번호를 만든다.
서버는 현재 멤버 권한을 잠근 뒤 기존 결과를 찾는다. 같은 번호·같은 내용이면 최초 응답을 반환하고 첨부를 다시 소비하지 않는다.
같은 번호의 다른 내용은 409다. 요청 내용은 SHA-256 지문으로 비교하며, 응답 시각은 DB의 마이크로초 정밀도에 맞춰 재시도에도 일치시킨다.

V58의 `(jar_id, author_id, client_request_id)` 유일 제약과 멤버 행 잠금을 함께 사용한다.
잠금을 기다린 재시도가 먼저 저장된 결과를 읽도록 이 생성 트랜잭션은 `READ_COMMITTED`를 사용한다.
번호를 보내지 않는 기존 클라이언트도 호환되지만, 그 요청에는 중복 방지 효과가 없다. 프론트의 재시도 번호는 현재 작성 화면의 메모리에 유지하며 새로고침 복구 저장소를 추가한 것은 아니다.

## 3. 파일 완료 응답 복구

`FileUploadTransactionService`는 같은 소유자·파일 키·목적의 `COMPLETED`/`CONSUMED` 파일에 기존 완료 결과를 반환한다.
이미 완료된 파일은 S3에 다시 접근하지 않는다. 최초 요청에서 임시 파일 확인이나 DB 응답이 끊긴 경우에도 DB에 확정 결과가 있는지 재확인한다.
확인할 수 없으면 성공으로 추측하지 않고 원래 실패를 유지한다.

소유자·목적 검증, 불변 업로드 사본 검사, 완료 행 잠금은 유지했다. 만료·삭제 예약·삭제 완료 파일은 복원하지 않는다.
S3 요청은 여전히 DB 트랜잭션 밖에서 수행한다.

## 4. 다른 화면으로 넘어간 뒤 도착한 변경 응답

`useJarMembers.js`와 `useJarInvites.js`의 변경 요청에 기존 `useRequestGate`를 재사용했다.
저금통·권한·화면 수명이 바뀌면 이전 요청의 이동·알림·목록 갱신·로딩 종료를 적용하지 않는다.
CSRF 조회 뒤와 각 비동기 후속 단계에서도 다시 검사한다. 같은 순간의 연속 클릭도 동기식 진행 표시로 막는다.
이미 서버에 도착한 변경 자체를 취소하는 기능은 아니며, 완료 결과가 다른 화면에 개입하는 것을 막는다.

## 5. 쪽지에 넣지 않은 완료 파일 정리

V58은 NOTE 완료 파일의 정리 예정 시각과 정리 완료 시각을 추가한다. 완료 후 7일간 쪽지에 연결하지 않은 파일이 대상이다.
기존 완료 파일에도 완료 시각을 기준으로 예정 시각을 채운다.

`FileUnusedCleanupPersistenceService`는 실제 첨부 참조가 없는지 다시 확인하고 짧은 트랜잭션에서 `UNUSED_DELETING` 상태로 예약한다.
첨부 연결의 `COMPLETED → CONSUMED` 변경과 같은 행을 경합하므로 연결 또는 삭제 예약 중 한쪽만 성공한다.
예약이 커밋된 뒤 `FileUnusedCleanupScheduler`가 S3를 삭제하고 `UNUSED_DELETED`를 기록한다.
저장소 장애나 재시작으로 끊기면 예약된 파일만 재시도한다.

기존 파일 정리 전용 스케줄러를 재사용하며 기본 5분 간격·한 번에 최대 50개다.
실제 첨부 참조가 있는 파일, 사용 완료 파일, 최근 파일, NOTE 이외 파일, `.pending` 임시 파일은 이 정리에서 제외한다.
임시 업로드 정리는 기존 경로를 유지한다. 기존 첨부의 소프트 삭제 기록도 참조로 취급해 보수적으로 보호한다.

## 6. 실시간 배달 권한 조회

기존 정상 저금통 메시지 배달은 수신자마다 로그인 검사와 멤버 검사를 따로 조회했다.
`WebSocketDeliveryAuthorizationInterceptor`와 `SessionValidityService`, `UserRepository`에서 로그인 버전·기기 세션·현재 멤버·저금통 생존을 한 DB 쿼리로 확인한다.
권한을 캐시해 탈퇴·로그아웃을 늦게 반영하는 방식은 사용하지 않는다.

멤버 권한만 사라지면 그 저금통 메시지를 차단하면서 본인 상태 채널은 유지한다. 로그인도 폐기됐으면 연결을 닫는다.
개인 알림과 AI 채널, 수신 구독 권한 검사는 기존 경로를 유지했다.

실제 MariaDB의 수신자 300명·작업 스레드 16개 시험에서 정상 배달의 조회 수는 **600회 → 300회, 50% 감소**했다.
이 시험의 시간은 연결 획득 대기를 포함하는 Repository 호출 시간이다. 실제 300개 소켓의 네트워크 전송 지연이나 운영 수용 인원을 측정한 값은 아니다.
별도 SimpleBroker 검사에서는 실제 배달 프레임이 멤버 권한 폐기 뒤 차단되는 것을 검증한다.

최종 전체 테스트의 해당 로컬 시험 1회에서 기록한 수치는 다음과 같다. 기존 방식 다음에 통합 방식을 실행했으며, 실행 순서·캐시·JIT(자주 실행한 코드를 빠르게 준비하는 JVM 기능)의 영향을 분리한 반복 성능 실험은 아니다. 시간 감소율을 운영 개선율로 발표하지 않는다.

| 측정 항목 | 기존 두 조회 | 통합 조회 |
| --- | ---: | ---: |
| DB 쿼리 수 | 600 | 300 |
| 권한 확인 평균 | 18.59ms | 8.59ms |
| 권한 확인 P95(95%가 이 시간 이내) | 35.11ms | 28.81ms |

## 7. 프론트 수정에 따른 불필요한 API 교체

`publish-ghcr.yml`에 백엔드 소스·Gradle·Docker·배포 도구 경로 필터를 추가했다. 프론트·문서만 바뀐 푸시는 백엔드 배포를 시작하지 않는다.

동시에 `deploy-api.py`의 최신 커밋 검사도 보완했다. 빌드 중 프론트 전용 커밋이 추가된 경우에는 GitHub의 변경 파일 비교로 백엔드가 동일함을 확인해야 기존 검증 이미지를 배포할 수 있다.
분기 이탈·백엔드 변경·백엔드에서 이동한 파일·비교 응답 누락·300개 이상 파일의 잘린 비교는 거절한다.
검증한 이미지의 SHA·digest 확인, 준비 상태 점검, 실패 시 복구는 유지한다.

실제 백엔드 변경 배포는 기존 단일 API 컨테이너 교체 방식이다. 이번 변경이 백엔드 교체 자체의 무중단 배포를 구현한 것은 아니다.
이전 로그인 502의 당시 원인을 이번 코드 변경만으로 확정하지 않는다.
