# 서버 부하 시험 준비부터 10명 조회 재시험까지

- 작성일: **2026년 10월 19일**
- 날짜 기준: **한국 시간(KST)**
- 정리한 작업 기록: **2026년 10월 17일~19일**
- 시작 질문: **“우리 서버가 10명·300명의 요청을 얼마나 잘 처리하나?”는 아직 검사 전이라고 했는데, 이제 무엇을 해야 하나?**
- 독자: 이 프로젝트나 서버 용어를 처음 접하는 사람

질문 자체의 정확한 전송 시각은 이 문서에서 확정하지 않는다. 날짜가 확인된 작업 기록을 기준으로 순서를 정리했다.
반복된 “바로 가자”, 명령어 복사 실수, 같은 개념을 여러 번 설명한 대화는 묶었다.
대신 실패한 시험과 아직 확인하지 못한 부분은 지우지 않았다.

## 1. 지금 어디까지 왔나?

**시험 준비만 하던 상태에서 출발해, 실제 EC2(인터넷에서 서비스를 실행하는 AWS 서버)에서 10 VU 조회를 두 차례 통과했다.**
VU(사람처럼 정해진 행동을 반복하는 가상 사용자)는 실제 회원 수와 다르다.

| 구분 | 확인한 상태 |
| --- | --- |
| 처음 10 VU 조회 | 10월 18일, 60초 동안 576건 조회·오류 0건 |
| 50 VU 시도 | 10월 18일, **첫 로그인 준비에서 시간 초과. 50명 조회는 시작하지 못함** |
| 로그인 지연 진단 | 메모리를 디스크에서 다시 읽는 현상과 긴 메모리 정리가 지연과 겹치는 것을 확인 |
| 대책 적용 후 인증 | 전용 계정 3개로 인증 전체 흐름 성공. 15분 이상 쉬었다가 재시험해도 성공 |
| 대책 적용 후 10 VU 재시험 | 10월 19일, 다시 60초 동안 576건 조회·오류 0건 |
| 100·200·300 VU | **미실행** |
| 현재 주의점 | 마지막 10 VU 관측에서 서버 전체 가용 메모리가 최소 약 **80MiB**로 여유가 작았음 |

따라서 지금은 **“정해진 짧은 조회 시나리오에서 10 VU는 통과했다. 300 VU와 전체 서비스 수용 능력은 아직 모른다.”**가 정확한 결론이다.

## 2. 우리의 목표는 무엇이었나?

쉽게 말해, 가게에 손님을 조금씩 늘려 보내며 **주문을 얼마나 빨리, 틀리지 않고 처리하는지** 확인하려는 것이다.

1. 실제 두 사용자의 계정과 자료는 시험에 사용하지 않는다.
2. 서버가 요청을 제대로 처리하는지 먼저 확인한다.
3. 가상 사용자를 10 → 50 → 100 → 200 → 300명으로 단계적으로 늘린다.
4. 느려지거나 자원이 부족해지면 요청을 늘리지 않고 중단한다.
5. 기록을 남겨 나중에 같은 조건으로 다시 비교한다.

장기 목표는 일반 사용자 **500명**을 고려한 서비스 준비다.
하지만 회원 500명, 동시에 접속한 500명, 계속 요청하는 500 VU는 서로 다른 조건이다.
300 VU 통과 여부만으로 실제 사용자 500명의 모든 행동을 감당한다고 말하지 않는다.

## 3. 어떤 시험을 하기로 했나?

| 시험 구분 | 실제로 하는 일 | 하지 않거나 대신 처리하는 일 |
| --- | --- | --- |
| 외부 서비스 모의 시험 | 우리 서버의 생성 상태·작업 대기열·실패·인증 처리 검사 | AI·이미지 심사·메일·그 흐름의 파일 저장은 대역(실제 서비스 대신 정해진 응답을 주는 가짜 서비스) 사용 |
| 일반 서비스 시험 | 저금통·쪽지 조회, 이후 저장·권한·동시 요청·실시간 전달 검사 | 실제 유료 외부 API(다른 서비스에 기능을 요청하는 통로)와 S3 파일 전송 제외 |
| 별도 실제 S3(파일을 보관하는 AWS 서비스) 시험 | 승인 후 테스트 파일 업로드·존재 확인·다운로드 검사 | AI 생성·이미지 심사·메일 발송 제외. **아직 미실행** |

로컬(개발자 PC)에서는 도구와 기능이 맞는지 확인하고, 성능 기준값은 실제 EC2 측정값으로 남기기로 했다.
PC가 빠르다고 EC2도 빠르다고 판단하지 않는다.

시험 경로에서 실제 Cloudflare AI·Rekognition(이미지 심사 서비스)·SES(이메일 발송 서비스)·S3 전송을 제외했다.
그렇다고 AWS 청구액 전체가 0원이라는 뜻은 아니다. 기존 EC2·디스크 등의 기본 비용은 별개다.
별도의 유료 서버 증설은 이 과정에서 하지 않았다.

## 4. 시험의 합격 기준과 중단 장치

### 우리가 합의한 기준

| 항목 | 기준 | 쉬운 뜻 |
| --- | --- | --- |
| 일반 조회 API별 p95 | 500ms 이하 | p95(요청 중 95%가 완료되는 시간) 기준으로 0.5초 안에 처리 |
| 오류율 | 1% 미만 | 요청 100개 중 실패가 평균 1개보다 적어야 함 |

| DB 연결 풀 | 70%부터 경고, 80% 초과 지속 시 중단 | DB(자료를 저장하는 곳)와 통신하는 연결 통로가 부족해지지 않기 |

| 컨테이너 | 예상 밖 재시작·OOM 없음 | 컨테이너(프로그램을 정해진 환경에서 실행하는 단위)가 갑자기 꺼지거나, OOM(메모리 부족으로 강제 종료됨)이 없어야 함 |

일반 조회의 500ms 기준과 소량 인증 진단의 **요청별 3초 제한**은 서로 다른 기준이다.
로그인이 3초 안에 끝났다고 일반 조회 p95 기준까지 통과한 것은 아니다.

## 6. 왜 로그인에서 계속 막혔나?

### 6-1. 작은 책상에 많은 일을 올려놓은 상태였다

서버는 1GiB급이며 운영체제에 보이는 RAM(프로그램이 지금 일할 때 사용하는 메모리)은 약 **914MiB**다.
자바 서버, DB, 운영체제, Docker(컨테이너 실행 도구), 배포 도구 등이 이 공간을 함께 썼다.

RAM을 책상, 디스크를 서랍이라고 생각하면 쉽다.
책상이 좁으면 당장 안 쓰는 자료를 서랍에 넣어 두었다가 필요할 때 다시 꺼낸다.
이것이 **스왑(RAM의 일부 자료를 디스크로 옮겨 보관하는 기능)**이다.
서랍에서 꺼내는 작업은 책상 위 자료를 바로 읽는 것보다 느릴 수 있다.

중요한 점은 다음과 같다.

- 스왑을 사용 중이라는 숫자만으로 지금 느리다고 확정할 수는 없다.
- 실제로 스왑을 읽는 양·디스크 대기·요청 지연이 함께 늘어나는지 봐야 한다.
- CPU 사용률이 낮아도 디스크를 기다리느라 응답이 늦을 수 있다.
- Heap 밖에도 클래스 정보·실행 코드·스레드(프로그램 안에서 작업을 수행하는 실행 단위) 등이 메모리를 사용한다.
- 가용 메모리가 생겨도 전에 서랍에 넣은 자료가 자동으로 즉시 모두 돌아오는 것은 아니다.

### 6-2. 메모리를 한꺼번에 정리하는 긴 작업도 겹쳤다

GC(자바가 더 쓰지 않는 객체를 찾아 메모리를 정리하는 작업)를 추가로 확인했다.
기존 Serial(주로 한 정리 스레드로 메모리를 정리하는 방식)에서 긴 전체 정리와 로그인 지연이 겹쳤다.

한 실패 사례에서는 서버의 로그인 처리 약 **7.75초** 중 비밀번호 확인 구간이 약 **7.70초**였고,
같은 요청 구간의 JVM(자바 프로그램 실행 환경) 전체 GC 누적 시간이 약 **7.54초** 증가했다.
전체 정리 카운터의 시간 증가도 약 **7.48초**였다.

이는 긴 정리가 지연과 겹쳤다는 강한 근거다.
하지만 GC 카운터는 서버 전체 값이라 해당 로그인만의 정확한 정지 시간으로 단정하지 않는다.
모든 과거 실패가 같은 원인이었다고도 말하지 않는다.

### 6-3. 시험 도구의 뒤처리에도 문제가 있었다

클라이언트(요청을 보내는 쪽)가 3초 뒤 포기해도 서버는 로그인을 나중에 완료할 수 있었다.
기존 임시 시험 도구는 지표 수집까지 실패하면 기다리기를 너무 일찍 끝낼 수 있었다.
그 결과, 정리 직후에는 0개였던 시험 세션(로그인 유지 기록)이 나중에 1개 남는 경우를 확인했다.

이 문제는 서버의 모든 인증 기능에 같은 버그가 있다는 뜻이 아니라, **시험 후 정리 순서의 문제**다.
발견한 세션은 전용 계정 범위에서 폐기했다. 실제 두 사용자의 세션은 건드리지 않았다.

MyISAM·Aria·InnoDB는 DB가 자료를 관리하는 서로 다른 저장 방식의 이름이다.

자료를 다시 계산하지 않게 보관하는 일반적인 캐시와는 목적이 다르다.

G1 적용 시 DB 컨테이너는 재시작하거나 교체하지 않았다.
이전의 모든 작업에서 DB를 한 번도 재시작하지 않았다는 뜻은 아니다.
계측(상태를 숫자로 읽는 기능) 추가도 메모리와 실행 시간에 부담이 있으므로, 계측 전·후 이미지와 설정을 구분했다.

## 9. 가용 메모리 80MiB는 얼마나 남았다는 뜻인가?

가용 메모리는 **운영체제가 새 작업에 쓸 수 있다고 추정하는 RAM**이다.
완전히 비어 있는 공간뿐 아니라 필요할 때 회수할 수 있는 일부 공간도 고려한다.
디스크 저장 공간이나 자바 Heap만의 여유를 말하는 것이 아니다.

전체 약 914MiB 중 최저 약 80MiB면 대략 **9%의 여유**다.
설정한 즉시 중단선 64MiB까지는 약 **16MiB**밖에 남지 않았다.

따라서 이번 10 VU가 실패했다는 뜻은 아니지만, **안전선 위였다는 이유만으로 50 VU가 안전하다고 판단하면 안 된다.**
64MiB는 이번 감시 도구의 보호 기준이지, 그보다 1MiB만 높으면 무조건 안전하다는 경계가 아니다.

## 11. 기록과 배포를 어떻게 보존했나?

- 커밋(파일 변경을 묶어 식별 번호와 함께 저장하기)과 푸시(그 기록을 원격 저장소로 보내기)는 한국어 메시지로 했다.
- SHA(커밋 식별 번호)·이미지 digest(실행 이미지의 고유 식별값)·시작 시각·설정을 구분해 기록했다.
- `latest`라는 바뀔 수 있는 이름만 믿고 배포하지 않도록 보강했다.
- CI(변경을 올리면 자동으로 검증하는 절차) 성공과 실제 배포 성공은 따로 확인한다.
- 비밀번호·개인 키·토큰·실제 사용자 자료·DB 백업·시험 계정 자격 증명은 커밋하지 않았다.
- 처음 보는 기술 용어는 **용어(짧고 쉬운 설명)** 형식으로 설명하도록 작업 지침에 남겼다.
- 실수로 한국어가 아닌 언어로 작성했던 프로젝트 내 문구는 정리했다. 이미 전송한 채팅 자체를 삭제한 것은 아니다.

이번 수정 소스는 **`4928d3f7a298326a4b3bb7c98742b15f4da8bef6`**로 한국어 커밋·푸시했다.
커밋 제목은 **`fix: 로그인 메모리 정지 대응과 시험 세션 정리 강화`**다.

마지막 G1 10 VU는 이 커밋의 자동 배포 **전**에 얻은 결과다.
당시 실행 이미지의 소스 커밋은 `0816198`이고, 여기에 운영 JVM 설정을 바꿔 측정했다.
따라서 푸시 후 만들어진 새 이미지에서 이미 같은 부하를 통과했다고 적으면 안 된다.

이 문서도 사용자가 요청한 작업 기록이므로 별도의 한국어 문서 커밋으로 남긴다.
본문에 자기 자신의 커밋 번호를 넣으면 다시 내용이 바뀌므로, 문서 커밋 번호는 Git 이력에서 확인한다.

| 6 | 허용된 경우 50 → 100 → 200 → 300 VU | 기존 전용 300계정 자료를 먼저 재확인하고 **한 단계씩**, 실패 시 중단·다음 단계 보류 |
| 7 | 조회와 별도의 쓰기·WebSocket 부하 | 저장 결과·메시지 전달 시간·누락·중복·재연결·권한 검사 |
| 8 | 모의 외부 서비스 큐·지속 부하·회복 | 실제 과금 호출 없이 대기열 포화·실패 복구·장기 자원 누적 검사 |
| 9 | 별도 실제 S3 | 요청 수·파일 크기·보관 기간·비용 한도에 별도 승인 후 실행 |

서버 RAM 증설은 비용과 측정 조건을 바꾸므로 별도 선택 사항이다.
가격 비교는 논의했지만 이 과정에서 증설을 실행하지 않았고, 과거 가격을 현재 확정 청구액으로 적지 않는다.
증설하더라도 자동으로 300 VU나 500명 처리 능력이 증명되는 것은 아니다.

## 13. 포트폴리오에 지금 쓸 수 있는 표현

> 전용 시험 계정과 비용 서비스 제외 경로를 구성하고, 실제 EC2에서 10 VU·60초 조회를 수행했다.
> G1 적용 후 시험에서는 조회 576건의 오류가 0건이었고, API별 p95는 약 68~121ms였다.
> 5초 자원 수집과 부하 중단 장치를 마련했으며, 로그인 지연 구간에 긴 메모리 정리와 디스크 읽기가 겹치는 현상을 진단했다.
> 이 결과는 지정한 짧은 조회 시나리오의 결과이며, 300 VU·전체 서비스 수용 능력은 별도 검증 대상이다.

아직 쓰면 안 되는 표현:

- “300명 또는 500명 동시 사용 검증 완료”
- “50 VU에서 서버의 최대 성능을 확인했다” — 실제로는 조회 전 로그인 준비 실패다.
- “응답 속도 몇 % 개선” — 동일 조건 전후 비교가 아니다.
- “스왑 문제·메모리 누수 완전 해결” — 짧은 시험만 통과했다.
- “모든 외부 API와 모든 기능 검증 완료”
