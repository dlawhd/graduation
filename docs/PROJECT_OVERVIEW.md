# Memory Jar — 서비스 주제 및 기능 기획서

문서명: `docs/PROJECT_OVERVIEW.md`기준 소스: `graduation-main (36).zip`작성 기준일: 2026년 9월 16일

> 이 문서는 Memory Jar의 기획 배경, 서비스 목적, 핵심 기능, 기술 구조 및 향후 개발 방향을 정리한다. 현재 구현된 기능과 향후 개발할 기능을 구분하며, 코드에 없는 기술을 구현된 것으로 표현하지 않는다.
>

## 1. 프로젝트 주제 및 기획 배경

### 1-1. 프로젝트를 시작하게 된 계기

여자친구와 함께 1년이라는 기간을 정하고, 그동안 있었던 재미있는 일이나 소중한 추억을 종이에 적어 저금통에 넣는 활동을 했다.

함께 있을 때는 재미있는 일이 생기면 바로 종이에 적어 저금통에 넣을 수 있었다. 하지만 여자친구가 졸업하면서 서로 떨어져 지내게 되었고, 이전처럼 같은 저금통에 추억을 넣기 어려워졌다.

이 경험에서 다음과 같은 생각을 하게 되었다.

"서로 멀리 떨어져 있어도, 함께했던 추억을 같은 저금통에 모을 수 있다면 어떨까?"

종이 저금통을 온라인으로 옮기면 서로 다른 장소에서도 추억을 남길 수 있고, 정해진 날이 되었을 때 함께 저금통을 열어볼 수 있을 것이다.

이렇게 시작한 아이디어를 연인뿐 아니라 가족, 친구, 동아리 등 소중한 관계를 맺고 있는 사람들이 사용할 수 있는 서비스로 확장하고자 한다.

단순히 사진과 글을 저장하는 웹사이트가 아니라, 추억을 모으는 과정과 기다림, 그리고 함께 열어보는 경험을 제공하는 서비스를 만드는 것이 목표다.

### 1-2. 서비스 한 줄 정의

Memory Jar는 소중한 사람들과 온라인 저금통에 추억을 모으고, 약속한 날 함께 열어보는 비공개 추억 공유 서비스다.

### 1-3. 프로젝트 목표

| 구분 | 목표 |
| --- | --- |
| 사용자 경험 | 멀리 떨어져 있어도 같은 저금통에 추억을 남길 수 있도록 한다. |
| 감성적 가치 | 추억을 모으는 설렘과 정해진 날 함께 열어보는 경험을 제공한다. |
| 관계 확장 | 커플뿐 아니라 가족·친구·동아리도 사용할 수 있도록 한다. |
| 서비스 운영 | 실제 사용자가 가입하고 이용할 수 있는 웹서비스를 구축한다. |
| 기술적 목표 | 인증, 데이터 무결성, 파일 업로드, 실시간 통신, 배포를 직접 설계하고 구현한다. |
| 포트폴리오 | 실제 문제에서 출발한 서비스의 설계·구현·개선 과정을 설명할 수 있도록 한다. |

## 2. 서비스의 핵심 가치

### 2-1. 추억을 함께 모으는 경험

사용자가 저금통을 만들고 초대코드를 공유하면, 초대받은 사람들이 같은 공간에 추억을 남길 수 있다.

각자 다른 장소에 있어도 하나의 저금통을 함께 채울 수 있다는 것이 핵심이다.

### 2-2. 기다림이 있는 추억 보관

일반적인 게시판은 작성한 글을 바로 읽는 것이 기본이지만, Memory Jar는 사용자가 정한 오픈 날짜까지 일부 정보를 숨길 수 있다.

이를 통해 추억을 남기는 순간뿐 아니라 다시 만나 함께 열어보는 순간에도 의미를 부여한다.

### 2-3. 추억을 다시 이야기하는 공간

저금통이 열린 뒤에는 쪽지를 읽고, 리액션을 남기고, 댓글과 답글로 당시의 이야기를 다시 나눌 수 있다.

또한 오늘의 추억 한 장 기능을 통해 과거의 추억을 하루에 하나씩 다시 발견할 수 있다.

### 2-4. 관계 중심의 비공개 공간

Memory Jar는 불특정 다수에게 게시물을 공개하는 SNS보다 초대받은 사람들 사이의 공유에 초점을 맞춘다.

저금통의 이름과 참여 인원, 공개 날짜를 정하고 초대코드로 멤버를 관리한다.

현재는 외부 공개용 읽기 전용 링크를 제공하지 않는다. 초대코드 역시 공개 게시물 주소가 아니라 로그인한 사용자가 저금통에 참여하기 위한 수단이다.

# 3. 주요 사용자와 이용 시나리오

## 3-1. 주요 사용자

| 사용자 | 활용 예시 |
| --- | --- |
| 커플 | 1년 동안 있었던 일들을 모아 기념일에 열어보기 |
| 가족 | 가족 여행과 생일 등 일상의 추억을 함께 보관하기 |
| 친구 | 서로 다른 지역에서 지내며 추억을 모으기 |
| 동아리·모임 | 활동 기록을 모아 졸업이나 모임 종료일에 열어보기 |

특정 관계를 위한 별도의 회원 유형을 만들기보다는, 사용자가 저금통의 이름·설명·참여 인원을 자유롭게 설정할 수 있도록 한다.

## 3-2. 대표적인 사용 시나리오

```
① 회원가입 또는 로그인
          ↓
② 새로운 추억 저금통 생성
          ↓
③ 이름·테마·인원·오픈 날짜 설정
          ↓
④ 초대코드 또는 링크 공유
          ↓
⑤ 친구·가족·연인이 저금통에 참여
          ↓
⑥ 각자 추억 쪽지 작성
          ↓
⑦ 사진·영상 첨부 및 저금통에 저장
          ↓
⑧ 저금통 채팅으로 일상 공유
          ↓
⑨ 약속한 오픈 날짜 도달
          ↓
⑩ 저금통 오픈 이벤트
          ↓
⑪ 함께 추억을 읽고 댓글·리액션 작성
          ↓
⑫ 오늘의 추억 한 장으로 다시 돌아보기
```

이 흐름은 현재 구현된 주요 기능을 기준으로 구성했어. 종이가 접혀 저금통으로 들어가는 연출과 저금통 오픈 애니메이션도 프론트엔드 코드에 구현되어 있어.

# 4. 핵심 기능

이 장에서는 현재 `(36)` 코드에 구현된 기능을 기준으로 정리한다. 기능의 존재는 소스에서 확인했으며, 모든 기능의 운영 환경 동작을 새로 검증했다는 의미는 아니다.

## 4-1. 회원가입 및 계정 관리

현재 구현

### 지원하는 로그인 방식

| 방식 | 설명 |
| --- | --- |
| 자체 로그인 | 로그인 아이디와 비밀번호 사용 |
| 네이버 로그인 | OAuth2 기반 소셜 로그인 |
| 구글 로그인 | OAuth2 기반 소셜 로그인 |
| 카카오 로그인 | OAuth2 기반 소셜 로그인 |

하나의 Memory Jar 사용자에게 여러 소셜 로그인 방법을 연결할 수 있는 구조다.

자체 회원가입은 이메일 인증을 거치며, 가입 후 자동으로 로그인된다.

### 계정 관련 기능

- 로그인 아이디 중복 확인
- 이메일 인증번호 발송 및 확인
- 자체 회원가입·로그인
- 이메일 인증을 통한 로그인 아이디 찾기
- 비밀번호 재설정
- 닉네임 변경
- 로그아웃 및 토큰 재발급

비밀번호는 원문 대신 Argon2id 기반 해시로 저장한다. 비밀번호 재설정 시 기존 Refresh Token을 폐기해 이전 로그인 상태를 정리한다.

현재 프로필 관리에서 사용자가 변경할 수 있는 항목은 닉네임이야. 프로필 사진 변경, 회원 탈퇴, 사용자별 알림 수신 설정은 아직 구현되지 않았다.

## 4-2. 저금통 생성 및 관리

현재 구현

저금통은 Memory Jar의 핵심 단위다.

사용자는 여러 저금통을 만들거나 참여할 수 있고, 저금통마다 서로 다른 멤버와 추억을 관리할 수 있다.

### 생성 시 설정하는 정보

| 설정 | 설명 |
| --- | --- |
| 이름 | 저금통의 이름 |
| 설명 | 저금통을 만든 목적이나 소개 |
| 테마 | 저금통의 시각적 디자인 |
| 최대 인원 | 2~50명 |
| 오픈 날짜 | 추억을 공개할 날짜와 시간 |
| 오픈 방식 | 전체 공개 또는 Daily Draw 중심 방식 |
| 잠금 수준 | 오픈 전에 보여줄 정보의 범위 |

현재 테마는 총 8종이다.

```
SPRING
SUMMER
AUTUMN
WINTER
LAVENDER
DEW
SAND
MOONLIGHT
```

테마는 저금통의 색상과 장식, 화면 분위기에 사용한다.

저금통 생성 후 목록·상세 조회·설정 수정·삭제 기능을 제공하며, 이미 열린 저금통은 오픈 정책을 변경할 수 없다.

### 멤버 역할

| 역할 | 주요 권한 |
| --- | --- |
| OWNER | 저금통 소유자. 설정·초대·멤버 관리·삭제 가능 |
| ADMIN | 설정·초대·멤버 관리 가능 |
| MEMBER | 추억 작성·조회·채팅 등 일반 기능 이용 |

현재는 OWNER 권한을 다른 사람에게 이전하는 기능이 없다. 또한 OWNER는 일반 멤버처럼 저금통 나가기 기능을 사용할 수 없다.

### 초대 기능

초대코드를 발급하고 만료 시간과 최대 사용 횟수를 설정할 수 있다.

관리자는 초대코드를 조회하거나 폐기할 수 있으며, 초대받은 사용자는 로그인한 뒤 저금통에 참여한다.

과거에 나갔던 멤버가 다시 참여하면 기존 멤버 기록을 재활성화한다.

## 4-3. 추억 쪽지

현재 구현

### 쪽지 작성

사용자는 다음 내용을 작성할 수 있다.

| 항목 | 설명 |
| --- | --- |
| 제목 | 추억을 나타내는 제목 |
| 내용 | 한 줄 또는 긴 글 |
| 추억 날짜 | 실제 추억이 있었던 날짜 |
| 장소 | 추억이 있었던 장소 |
| 태그 | 추억을 구분하는 키워드 |
| 첨부파일 | 사진·영상, 최대 10개 |

첨부파일별 설명(`caption`)도 작성할 수 있다.

### 종이 저금통 연출

실제 종이에 추억을 적어 저금통에 넣던 경험을 웹에서도 느낄 수 있도록 구성했다.

```
새 쪽지 작성
      ↓
작성 내용 확인
      ↓
최종 저장
      ↓
종이가 접히는 애니메이션
      ↓
작은 쪽지가 저금통으로 이동
      ↓
쪽지 목록 갱신
```

단순히 글을 저장하는 기능을 넘어, 추억을 저금통에 넣는 행동 자체를 사용자 경험으로 표현했다.

### 쪽지 조회와 보존 정책

쪽지 목록과 상세 조회를 지원하며, 저금통 오픈 전에는 잠금 수준에 따라 제목·내용·작성자 등의 정보를 제한한다.

현재 일반 사용자용 쪽지 수정·삭제 API는 없다. 작성 후 내용을 임의로 고치는 게시판보다 한번 넣은 추억을 보존하는 저금통의 성격을 유지한다.

또한 쪽지 검색 UI에 입력창이 일부 존재하더라도, 현재 백엔드에는 키워드·태그·작성자·기간별 검색 API가 구현되어 있지 않다. 이를 완성된 검색 기능으로 표현하지 않는다.

현재 남아 있는 정책 검토 사항: 오픈 이후에도 새 쪽지를 작성하는 요청을 막는 규칙은 확인되지 않았으며, 댓글 목록 등 일부 관련 API에는 오픈 상태 검사가 별도로 존재하지 않는다. 저금통의 공개 정책을 더 엄격하게 적용하려면 추가 검토가 필요하다.

## 4-4. 오픈 날짜·잠금·오픈 이벤트

현재 구현

사용자는 저금통을 생성할 때 오픈 날짜를 설정한다.

오픈 전에는 쪽지 내용을 제한하고, 오픈 날짜가 되면 서버가 저금통을 연다.

### 오픈 방식

| 방식 | 현재 동작 |
| --- | --- |
| ALL_AT_ONCE | 오픈 후 쪽지 전체 내용을 조회할 수 있음 |
| DAILY_DRAW | 오픈 후 하루 한 장씩 추억을 뽑는 경험을 중심으로 구성 |

현재 코드에서는 두 방식 모두 오픈 후 전체 쪽지 조회와 Daily Draw를 이용할 수 있다.

따라서 DAILY_DRAW를 선택하면 하루에 한 장 외에는 다른 추억을 절대 볼 수 없다는 식으로 설명하지 않는다.

### 자동 오픈 처리

```
오픈 예정 시간 도달
       ↓
Spring Scheduler 실행
       ↓
DB에 오픈 기록 저장
       ↓
오픈 SYSTEM 메시지 저장
       ↓
WebSocket으로 오픈 이벤트 전송
       ↓
프론트엔드에서 오픈 연출 표시
```

서버 스케줄러가 처리를 놓쳤더라도, 사용자가 저금통을 조회할 때 오픈 시간이 지났는지 확인해 보정할 수 있다.

중복 오픈 방지를 위해 DB 행 잠금과 `jar_open_events`의 UNIQUE 제약을 사용한다.

저금통 오픈 기록은 내부 DB에 저장되며, 사용자가 오픈 히스토리만 별도로 조회하는 공개 API는 아직 없다.

## 4-5. 오늘의 추억 한 장

현재 구현

오픈된 저금통에서 하루에 한 장의 추억을 무작위로 뽑아 보는 기능이다.

### 현재 규칙

- 저금통 단위로 하루 한 장을 선정한다.
- 같은 날 여러 명이 요청해도 동일한 결과를 반환한다.
- 이전에 뽑았던 쪽지는 다음 날짜의 후보에서 제외한다.
- 오늘의 카드와 과거 뽑기 기록을 조회할 수 있다.
- 한국 날짜를 기준으로 하루를 구분한다.

중복 뽑기는 Redis 분산락이 아니라 MariaDB의 저금통 행 잠금과 UNIQUE 제약으로 방지한다.

새로운 카드가 공개되면 WebSocket 이벤트를 전송해 다른 멤버들에게도 변화를 알릴 수 있다.

이 기능은 연인이 아니더라도 가족이나 친구가 함께 추억을 다시 발견하는 계기가 된다.

## 4-6. 리액션·댓글·답글

현재 구현

오픈된 추억에 감정을 표현하고, 해당 추억에 대한 이야기를 나눌 수 있도록 한다.

### 리액션

8종의 감정 리액션을 제공한다.

```
LOVE       SMILE
LAUGH      TOUCHING
MISS_YOU   PROUD
CHEER      THANKFUL
```

사용자 한 명은 같은 쪽지에 리액션 하나를 가질 수 있다.

기존 리액션을 변경할 수 있으며, 같은 리액션을 다시 누르면 취소된다.

### 댓글·답글

쪽지에 댓글을 작성하고 다른 사람의 댓글에 답글을 달 수 있다.

댓글 작성·조회·수정·삭제가 구현되어 있으며, 작성자 본인에게 수정·삭제 권한을 적용한다.

댓글·답글·리액션의 변경 사항은 WebSocket으로 전달할 수 있다.

# 5. 현재 기술 구조

이 부분은 기존 기획서에서 수정이 가장 많이 필요한 영역이야. 초기에는 S3·Redis·Kubernetes를 모두 사용하는 구조를 생각했지만, 현재 `(36)` 소스는 하나의 Spring Boot 애플리케이션을 중심으로 구성되어 있어.

```
                  사용자
                    │
                    ▼
               React 웹사이트
                    │
         ┌──────────┴──────────┐
         │                     │
         ▼                     ▼

                    │
```

현재는 별도의 `api-server`, `ws-server`, `worker` 애플리케이션으로 분리하지 않았어.

## 5-3. AWS S3 — 사진·영상 저장

현재 구현

사진과 영상은 애플리케이션 서버에 직접 저장하지 않고 S3에 저장해.

### 업로드 방식

```
React
  │
  │ ① 업로드 URL 요청
  ▼
Spring Boot
  │
  │ ② Presigned URL 발급
  ▼
React
  │
  │ ③ 파일 직접 업로드
  ▼
AWS S3
  │
  │ ④ 업로드 완료 알림
  ▼
Spring Boot
  │
  │ ⑤ S3 파일 검증
  ▼
MariaDB
  │
  │ ⑥ 쪽지 작성 시 파일 연결
  ▼
note_attachments
```

현재 `file_uploads` 테이블은 다음 상태를 관리해.

```
PRESIGNED
    ↓
COMPLETED
    ↓
CONSUMED
```

서버는 업로드한 파일의 존재 여부와 크기, Content-Type 등을 확인하고 첨부파일로 연결해.

### 현재 파일 제한

기본 설정 기준으로 이미지는 최대 10 MiB, 영상은 최대 30 MiB야. 해당 값은 서버 설정으로 변경할 수 있어.

현재 사진·영상 외의 임의 파일 형식 업로드를 지원한다고 표현하지 않아.

### 썸네일 처리

`note_attachments`에는 `thumbnail_url` 컬럼이 있고, 썸네일 주소를 갱신할 수 있는 Service 메서드도 존재해.

하지만 현재 별도의 썸네일 Worker가 자동으로 파일을 처리하는 구조는 구현되어 있지 않아.

향후 계획: 이미지·영상 업로드량이 증가하면 썸네일 생성 작업을 비동기로 분리하고, 처리 실패와 재시도 정책을 마련한다.

## 5-4. WebSocket — 실시간 소통

현재 구현

현재는 Spring Boot의 STOMP WebSocket을 사용해 채팅과 주요 상태 변경을 실시간으로 전달한다.

```
사용자 A
    │
    │ 메시지 전송
    ▼
Spring Boot
    │
    ├── MariaDB에 메시지 저장
    │
    └── STOMP 채널로 메시지 전송
                 │
                 ▼
              사용자 B
```

채팅 외에도 저금통 오픈, 멤버 변경, 쪽지 댓글·리액션, Daily Draw, 알림 이벤트에서 WebSocket을 활용해.

프론트엔드는 공용 STOMP 연결을 사용해 필요한 채널을 구독하는 구조야.

### Redis를 사용하지 않는 이유

현재 Redis 관련 Publisher·Subscriber·설정 파일은 전체가 주석 처리된 상태이고, Redis 의존성도 비활성화되어 있어.

따라서 현재 WebSocket 메시지를 Redis Pub/Sub로 중계한다고 설명하지 않아.

현재 구조는 Spring Boot의 메모리 기반 STOMP 브로커를 사용하므로, 여러 서버 인스턴스로 확장할 때는 메시지가 다른 서버의 구독자에게도 전달되도록 별도의 중계 방식을 설계해야 해.

그때 Redis Pub/Sub나 외부 STOMP 브로커 등을 비교하고 실제 요구사항에 맞는 방식을 선택할 수 있어.

Redis가 반드시 필요한 것은 아니며, 확장 요구사항이 생겼을 때 도입 여부를 결정하는 기술로 정리하는 것이 정확해.

## 5-5. MariaDB — 서비스 데이터 저장과 동시성 제어

현재 구현

MariaDB는 사용자, 저금통, 멤버, 초대코드, 쪽지, 댓글, 채팅, 알림 등의 데이터를 저장해.

Flyway로 V1~V31까지의 마이그레이션을 관리하고 있으며, JPA의 `ddl-auto`는 `validate`로 설정되어 있어.

### 현재 동시성 제어

| 대상 | 사용 방식 | 목적 |
| --- | --- | --- |
| 저금통 오픈 | DB 행 잠금 + UNIQUE 제약 | 오픈 기록 중복 방지 |
| Daily Draw | DB 행 잠금 + UNIQUE 제약 | 하루 중복 뽑기 방지 |
| 리액션 | 사용자·쪽지 UNIQUE 제약 및 Service 로직 | 동일 사용자 중복 반응 방지 |
| 초대코드 사용 | 사용 횟수 검사와 동시성 제어 | 사용 횟수·정원 초과 방지 |

이처럼 현재의 동시성 문제는 MariaDB와 트랜잭션을 중심으로 해결하고 있어.

분산락을 위해 Redis를 설치했다고 설명하지 않는다.

## 5-6. Docker 및 GitHub Actions — 배포

현재 배포 코드 존재

현재 GitHub Actions는 백엔드 테스트를 실행하고 Docker 이미지를 빌드해 GitHub Container Registry(GHCR)에 게시하는 과정을 포함해.

이후 배포 워크플로가 EC2 서버의 Docker Compose를 사용해 이미지를 가져오고 컨테이너를 재시작하는 구조야.

```
GitHub main 브랜치
        │
        ▼
GitHub Actions
        │
        ▼
백엔드 Gradle 테스트
        │
        ▼
Docker 이미지 빌드
        │
        ▼
GHCR에 이미지 게시
        │
        ▼
EC2 Self-hosted Runner
        │
        ▼
Docker Compose
        │
        ▼
애플리케이션 컨테이너 갱신
```

현재 소스의 CI 워크플로에는 백엔드 Gradle 테스트 단계가 명시되어 있어.

다만 워크플로 파일이 존재한다는 사실만으로 최근 배포가 성공했다거나 모든 운영 기능이 정상이라는 것까지 증명할 수는 없어. 실제 실행 결과와 운영 로그는 별도의 검증 자료로 관리해야 해.

## 5-7. Kubernetes는 현재 사용하지 않는다

초기 기획서에 작성했던 다음 구조는 아직 도입되지 않았어.

```
Kubernetes
 ├── api-server
 ├── ws-server
 ├── worker
 ├── Ingress
 └── HPA
```

현재 배포 기준은 EC2와 Docker Compose야.

Kubernetes는 서버를 여러 대로 운영하거나 서비스별 확장이 실제로 필요해지는 시점에 검토할 수 있어.

포트폴리오에서는 사용하지 않은 Kubernetes를 사용했다고 표현하기보다, 현재 구성에서 어떤 문제가 생기면 왜 확장 구조를 도입해야 하는지 설명하는 것이 더 정확해.

# 6. AI 커스텀 저금통 — 다음 개발 기능

별도 PoC·설계 진행

현재 (36) 미구현

초기 아이디어는 정해진 테마의 저금통에 추억을 넣는 것이었지만, 다음 단계에서는 사용자가 직접 그린 그림을 저금통 디자인으로 만들 수 있도록 확장할 계획이다.

사용자가 직접 그린 그림을 AI가 저금통으로 변환해, 세상에 하나뿐인 추억 저금통을 만드는 기능이다.

현재 별도의 Cloudflare Workers AI PoC와 프롬프트 실험을 진행했지만, `(36)` 프로젝트 소스에는 아직 해당 기능이 통합되지 않았어.

## 6-1. 기능 목표

사용자가 토끼를 그리면 토끼 모양의 저금통을, 별을 그리면 별 모양의 저금통을 만들 수 있도록 한다.

단순히 그림을 예쁘게 바꾸는 것이 아니라 원본의 특징을 보존하면서 저금통으로 변환하는 것이 중요하다.

### 사용자 경험

```
기본 저금통 생성
        ↓
저금통 상세 화면
        ↓
AI 커스텀 저금통 만들기
        ↓
Canvas에 그림 그리기
        ↓
스타일 선택
        ↓
AI 이미지 생성
        ↓
결과 미리보기
        ↓
다시 생성 또는 최종 적용
        ↓
나만의 저금통 완성
```

이미지 생성과 실제 저금통 적용을 분리한다. 생성된 결과가 마음에 들지 않으면 다시 생성할 수 있고, 사용자가 선택한 결과만 최종 저금통에 적용한다.

또한 기본 테마를 없애지 않고 기존 화면 배경·파티클·버튼 등의 디자인과 AI 저금통 이미지가 함께 동작하도록 한다.

## 6-2. 계획한 기술 구조

| 영역 | 기술 |
| --- | --- |
| 그림판 | React + HTML Canvas |
| 이미지 생성 | Cloudflare Workers AI |
| 생성 모델 | FLUX.2 Klein 4B |
| 백엔드 | 기존 Spring Boot |
| 이미지 저장 | 기존 AWS S3 |
| 생성 기록 | MariaDB |
| DB 변경 | Flyway 신규 마이그레이션 |

별도의 Python 서버나 GPU EC2를 구축하지 않고 Spring Boot가 Cloudflare API를 직접 호출하는 방향으로 설계했다.

```
React Canvas
      ↓
원본 그림 PNG
      ↓
AWS S3
      ↓
Spring Boot
      ↓
Cloudflare Workers AI
      ↓
AI 생성 이미지
      ↓
AWS S3
      ↓
React 미리보기
      ↓
사용자가 최종 적용
```

## 6-3. DB 설계 방향

생성에 실패하거나 여러 번 다시 만든 결과까지 관리하기 위해 생성 이력 테이블을 별도로 둘 계획이다.

```
[예정]

jar_ai_generations
    ├── generation_id
    ├── jar_id
    ├── created_by
    ├── 생성 상태
    ├── 원본 이미지 정보
    ├── 생성 결과 이미지 정보
    └── 실패 및 추적 정보

jars
    └── active_ai_generation_id 추가 예정
```

현재는 위 테이블과 컬럼이 존재하지 않아. 실제 구현 시에는 가장 최신 Flyway 버전을 확인하고 신규 마이그레이션을 작성해야 한다.

## 6-4. AI 기능의 운영 고려사항

AI 기능에는 이미지 생성 외에도 다음 요소가 필요하다.

- 사용자와 저금통의 생성·적용 권한 검사
- 업로드 이미지의 실제 파일 형식·크기·해상도 검증
- 외부 AI 서비스로 그림이 전송된다는 안내
- 사용자별·저금통별 생성 횟수 제한
- AI 요청 실패·중복 요청·서버 중단 시 복구 처리
- 사용하지 않는 생성 이미지와 원본의 저장·삭제 정책

무료 할당량이 존재하더라도 서버가 사용량을 직접 제한하도록 설계한다.

이 기능은 별도의 AI 개발 계획에 따라 단계적으로 진행하며, 현재 구현된 기능 목록에는 포함하지 않는다.

## 7-4. 데이터 암호화

향후 검토

초기 기획에서는 사용자들이 함께 정한 암호를 이용해 쪽지 내용을 AES로 암호화하는 기능을 고려했다.

# 9. Redis·Kubernetes 도입 기준

초기에는 기술을 먼저 정하고 서비스에 적용하려 했지만, 앞으로는 실제 문제를 확인한 뒤 필요한 기술을 도입하는 방향으로 정리한다.

| 기술 | 현재 상태 | 도입을 검토할 상황 |
| --- | --- | --- |
| Redis Pub/Sub | 비활성화된 초안 존재 | 다중 서버 간 실시간 이벤트 전달이 필요할 때 |
| Redis Cache | 미구현 | DB 조회 부하가 실제로 커질 때 |
| Redis 분산락 | 미구현 | DB 잠금만으로 요구사항을 충족하기 어려울 때 |
| Kubernetes | 미구현 | 여러 서버·서비스의 배포와 확장을 관리해야 할 때 |
| HPA | 미구현 | 부하에 따른 자동 확장이 필요할 때 |
| 별도 Worker | 미구현 | 이미지 처리 등 무거운 작업을 분리할 필요가 있을 때 |

### 기술 도입 원칙

```
현재 구조에서 문제 확인
          ↓
문제를 재현하고 측정
          ↓
원인 분석
          ↓
해결 방법 비교
          ↓
필요한 기술 도입
          ↓
같은 조건으로 재측정
          ↓
개선 효과와 트레이드오프 기록
```

예를 들어 단일 서버에서 정상적으로 동작하는 채팅을 다중 서버로 확장하게 된다면, 서버 간 이벤트 전달 문제를 먼저 재현하고 Redis Pub/Sub 등의 도입을 검토한다.

단순히 Redis나 Kubernetes를 사용했다는 사실보다 어떤 문제를 해결하기 위해 선택했고, 그 결과 무엇이 달라졌는지를 기록하는 데 초점을 맞춘다.

# 11. 취업 포트폴리오용 프로젝트 소개

기존 기획서의 면접용 문장은 Kubernetes, Redis Pub/Sub, 독립 Worker를 이미 구현했다고 설명하고 있었어.

현재 코드에 맞춰 다음처럼 수정하면 돼.

## 11-1. 프로젝트 소개 — 한 문단

Memory Jar는 멀리 떨어져 있는 연인과 추억을 공유하고 싶다는 개인적인 경험에서 출발한 웹서비스입니다. 커플뿐 아니라 가족과 친구도 함께 사용할 수 있도록 저금통 생성, 멤버 초대, 추억 쪽지 작성, 오픈 날짜 설정 및 Daily Draw 기능을 구현했습니다. Spring Boot와 React를 기반으로 JWT·OAuth2 인증, S3 Presigned URL 파일 업로드, STOMP WebSocket 채팅·실시간 알림을 구현했으며, MariaDB와 Flyway로 데이터를 관리합니다. 저금통 오픈과 Daily Draw에는 DB 잠금과 UNIQUE 제약을 적용해 동시 요청으로 인한 중복 처리를 방지하도록 설계했습니다. Docker와 GitHub Actions를 이용한 백엔드 배포 자동화 구성을 갖추고, k6를 활용한 채팅 성능 비교 및 개선을 위한 테스트 코드를 작성했습니다.

## 11-2. 백엔드 포트폴리오에서 설명할 기술적 경험

| 경험 | 설명할 수 있는 내용 |
| --- | --- |
| 인증 설계 | 자체 로그인과 다중 소셜 계정 연결, JWT 갱신 |
| 보안 | HttpOnly Cookie, CSRF, 비밀번호 해시, 권한 검사 |
| 데이터 모델링 | 저금통·멤버·쪽지·채팅·알림 테이블 관계 |
| 동시성 | 오픈 및 Daily Draw 중복 방지 |
| 파일 처리 | Presigned URL, S3 파일 검증, 트랜잭션 분리 |
| 실시간 통신 | REST Polling과 STOMP WebSocket 구조 |
| 테스트 | Spring 테스트 코드와 k6 부하 테스트 스크립트 |
| 배포 | Docker 이미지 빌드, GHCR, GitHub Actions, EC2 |

이 항목들을 면접에서 설명할 때는 단순히 기술 이름을 나열하는 대신 다음 구조를 사용한다.

```
문제 상황
    ↓
기존 구조의 한계
    ↓
해결 방법을 선택한 이유
    ↓
구현 과정
    ↓
테스트 및 검증
    ↓
결과와 남은 개선점
```

예를 들어 Daily Draw는 여러 사용자가 동시에 뽑기 요청을 보낼 수 있다는 문제에서 출발해, DB 잠금과 UNIQUE 제약을 함께 사용한 이유를 설명할 수 있어.

성능 개선 수치를 제시할 때는 실제 측정 로그와 테스트 조건을 근거로 사용한다.

## 13. 프로젝트의 최종 방향

Memory Jar는 단순히 여러 사람이 글과 사진을 올리는 서비스가 아니다.

소중한 사람들과 추억을 모으고, 함께 기다리고, 다시 꺼내 보며 이야기를 나누는 경험을 제공하는 서비스다.

기존 종이 저금통의 감성은 유지하면서, 서로 떨어져 있어도 함께 사용할 수 있다는 웹서비스의 장점을 활용한다.

현재 구현된 기능을 안정적으로 운영하고, 이후에는 사용자가 직접 디자인하는 AI 커스텀 저금통으로 경험을 확장한다.

기술적으로는 특정 기술을 많이 사용하는 것 자체를 목표로 삼기보다, 실제 문제를 분석하고 필요한 기술을 선택하며 그 결과를 검증하는 과정을 중요하게 생각한다.

이러한 과정을 통해 개인적인 경험에서 출발한 아이디어를 실제 사용자가 이용할 수 있는 서비스로 발전시키고, 설계부터 구현·테스트·배포·개선까지의 경험을 포트폴리오로 정리한다.
