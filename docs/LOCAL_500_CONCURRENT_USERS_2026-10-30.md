# 로컬 동시 사용자 500명 후속 시험

원인 분석은 [CPU·연결 풀·GC·측정 도구 대조 진단](LOCAL_READ_DIAGNOSIS_2026-10-30.md)에 별도로 기록했다. 아래 원래 500명 수치는 그대로 유지한다.

2026-10-30 실행 `memoryjar-e2e-7b935b0d74f0`.

**500개 계정으로 조회 4,844건을 수행했고 응답 오류는 0건이었다. 그러나 쪽지 목록 p95가 502.84ms로 기준 500ms를 넘어 자동 중단됐다. 예정한 30초를 완주한 결과는 아니다. 시험 데이터와 임시 자원은 모두 삭제했다.**

## 1. 이전 시험과 맞춘 조건

이 시험은 [1,000명 시험](LOCAL_1000_CONCURRENT_USERS_2026-10-30.md)의 후속이다. 격리 방식·응답 내용 검증·데이터 삭제 방식은 기존 도구를 재사용했다.

- 별도의 빈 임시 MariaDB에 계정 10,000개·저금통 9,300개·멤버 12,000개·쪽지 21,000개를 생성했다.
- 이전과 동일하게 서로 다른 비밀번호를 가진 **1,000개 계정의 로그인을 순차 준비**했다. 그중 첫 500개 계정으로 최종 조회 단계를 실행했다. 로그인 500건만 준비한 시험은 아니다.
- 500명은 10명씩 50묶음으로 나뉘며, 서로 다른 저금통 150개·쪽지 6,000개를 조회했다. VU(사용자의 요청 흐름을 흉내 내는 가상 사용자)마다 자기 인증 세션 하나를 사용했다.
- 단계는 **100명 20초 → 300명 20초 → 500명 30초 예정**이다. 이전 단계의 k6 프로세스를 제거하고 5초 대기한 뒤 다음 단계로 진행했다.
- 목록·상세·쪽지 비율 약 30%·30%·40%, 요청 완료 후 사용자별 1초 대기, 첫 요청은 0~0.99초에 분산했다.
- 각 API **p95 ≤500ms**, 오류율 **<1%**, 요청 제한 시간 **3초**를 유지했다. p95(요청 95%가 이 시간 안에 끝나는 지연 지표) 기준을 통과시키기 위해 완화하지 않았다.
- 앱 **2 CPU·메모리 1,536MiB·heap 768MiB**, DB **메모리 768MiB**, 부하 도구 **2 CPU·메모리 2,048MiB**를 유지했다.
- 기존 서비스·DB 구조·캐시·인증 설정을 최적화하거나 운영에 배포하지 않았다.

실제 브라우저 500개, WebSocket 500개, 3D 화면 출력, 동시 로그인은 시험하지 않았다. 이 결과의 동시 사용자는 로그인 후 API를 조회하는 가상 사용자 수다. 초당 요청 500건이나 HTTP 요청 500개가 항상 동시에 진행됨을 뜻하지 않는다.

## 2. 실제 결과

| 동시 사용자 | 조회 건수 | 오류 | 목록 p95 | 상세 p95 | 쪽지 p95 | 판정 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 100명 | 1,975 | 0 | 18.02ms | 22.36ms | 22.45ms | 통과 |
| 300명 | 5,855 | 0 | 60.33ms | 60.28ms | 70.24ms | 통과 |
| **500명** | **4,844** | **0** | **494.34ms** | **499.10ms** | **502.84ms** | **지연 기준 초과·자동 중단** |

500명 단계의 `activated_users`와 `vus_max`는 각각 500이었다. HTTP 200 응답 4,844건이 집계됐고, 상태·사용자 권한·저금통 ID·쪽지 ID·정렬·페이지 등 응답 내용 검사도 4,844건 모두 통과했다.

**쪽지 p95만 기준보다 약 2.84ms 높았다.** 이 기준 초과로 k6가 종료 코드 99를 반환했고 전체 실행과 JUnit도 실패로 종료했다. 오류율 0%를 근거로 지연 기준까지 통과했다고 기록하지 않았다.

30초 예정이었으나 기준 평가 후 조기 중단됐다. 따라서 4,844건을 30초로 나눠 처리량을 발표하지 않는다. 종료 시 미완료 반복도 있어 모든 작업이 끝났다고 설명하지 않는다.

이번 실행 전체는 조회 **12,674건·응답 검사 실패 0건**이다. 전체 합계가 500명 단계의 지연 기준 초과를 없애는 것은 아니다.

## 3. 자원 사용과 해석의 한계

500명 단계의 앱·DB·k6를 각각 5회 샘플링했다. 초기화와 종료 대기 구간도 포함하며 실제 순간 최대값을 보장하지 않는다.

| 대상 | 샘플 최대 CPU | 샘플 최대 컨테이너 메모리 |
| --- | ---: | ---: |
| 앱 | 173.76% | 726.3MiB |
| DB | 107.12% | 462.7MiB |
| k6 | **191.25%** | 534.3MiB |

CPU 100%는 대략 코어 하나다. 부하 발생기도 2코어 제한 근처까지 사용했다. 같은 PC에서 앱·DB·k6가 자원을 공유하므로 지연을 서버 코드의 문제로만 단정할 수 없다. 메모리·시간 보호 중단이나 k6의 OOM(메모리 부족 강제 종료)은 발생하지 않았다.

**이번 조건에서 300명은 통과했고, 500명은 500ms 기준 부근에서 초과했다.** 단일 실행이고 기준과의 차이가 작으므로 300명을 최대 용량으로 확정하거나, 500명은 항상 실패한다고 일반화하지 않는다. 이전 1,000명 결과와 이번 수치로 코드 개선율도 계산하지 않는다. 이번에는 서비스 코드를 개선한 것이 아니라 부하 규모를 바꿨다.

장시간 안정성·실제 운영 용량·부하 도구의 영향 분리는 추가 검증이 필요하다. 원인 확인 없이 서버 자원·캐시·쿼리·스레드 설정은 바꾸지 않았다.

## 4. 정리 확인

- 조회 전후 비즈니스 데이터 행 수가 동일했다. 로그인용 refresh token 1,000개 생성은 별도로 확인했다.
- 실행 접두사와 가짜 이메일 범위만 외래 키를 유지하며 자식부터 물리 삭제했다.
- **앱 테이블 24개가 모두 시작 상태인 0건으로 복원**됐다.
- **임시 컨테이너·네트워크는 각각 0개**다. 계정 암호 명세와 세션 파일도 제거했다.
- 보관 요약에는 숫자 `metrics`만 남겼고 k6의 `setup_data` 세션을 제거했다.
- 기존 `graduation-local-db`는 컨테이너 ID·시작 시각을 유지한 채 실행 중이다. 기존 DB 내용 전체를 대조한 것은 아니다.
- 운영 서버·운영 DB에는 연결하지 않았고 커밋·푸시·배포도 하지 않았다.
