# 반복 로그인 시간 초과: 메모리 정리 방식과 시험 정리 경로 수정

## 범위

대상 소스는 `081619893801ce4b0191c34b95fc3c93bcdb9067`을 기준으로 한 현재 작업 폴더다.
서버는 기존 1GiB EC2이며 API 이미지와 DB 스키마는 변경하지 않는다.
실제 두 사용자의 계정을 시험하지 않고 기존 전용 계정만 사용한다.
비밀번호 해시 강도·3초 요청 제한·일반 조회 성능 기준은 유지한다. 증설이나 유료 외부 API 시험은 하지 않는다.

## 확인한 문제

### 1. 전체 메모리 정리와 디스크 읽기가 인증 지연과 겹침

2026-10-18 23:36 KST의 첫 로그인은 클라이언트 3.08초 시간 초과, 서버 내부 약 6.27초였다.
같은 구간에 디스크 대기 44.39%, 스왑 읽기 13.64MiB/s가 있었다.
이후 자바의 약 154MiB가 스왑에 있으며 대부분 익명 메모리 영역인 것도 확인했다.
Heap(자바 객체 저장 메모리) 사용률이나 CPU가 낮다고 디스크 읽기 지연까지 낮다는 뜻은 아니었다.

스왑 우선순위만 60→10으로 낮춘 제한적인 실험에서는 두 로그인은 0.31초·0.27초였지만
세 번째가 3.15초에 시간 초과됐다. 서버 진단에서는 이 세 번째 요청이 약 7.75초,
비밀번호 확인이 약 7.70초였고 같은 요청 구간 JVM 전체 GC 누적 시간이 7542ms 증가했다.
`MarkSweepCompact` 누적 시간은 521→7998ms로 증가했다.
전체 메모리 정리를 할 때 애플리케이션을 멈추는 기존 Serial 방식과 실제 디스크 읽기가
몇 초간의 정지에 함께 나타난 것이다. GC 누적 시간은 요청 전용 정지 계측이 아니므로 단순 비율 계산은 하지 않는다.

같은 느린 요청에서 계정 조회 약 4.25ms, 토큰 발급 트랜잭션 약 23.85ms였다.
그 요청의 직접 지연 구간을 단일 SQL이나 비밀번호 해시 강도 자체로 오인해 바꾸지 않았다.
로그에서 메모리 부족 예외와 DB 풀 대기 오류는 관측하지 못했다.
모든 과거 실패가 완전히 같은 원인이었다는 의미는 아니다.

### 2. 수집 장애 후 늦게 성공한 로그인 세션이 남음

기존 임시 인증 프로브는 실패 후 `pump(30)`이 지표 수집 예외를 던지면 즉시 관측을 끝냈다.
관리 API도 긴 GC 동안 응답하지 못할 수 있어, 서버 로그인 완료 전에 세션 정리를 실행하는 경쟁 상태가 있었다.
해당 실행은 정리 순간 잔존 0개를 기록했지만 이후 실제 전용 세션 1개가 남은 것을 확인했다.
그 세션은 전용 계정 범위에서 별도로 폐기했다. 따라서 해당 실행의 정리 순간 0개를 최종 보존 보장으로 해석하지 않는다.

| `.github/workflows/publish-ghcr.yml` | 인증 프로브·복구 검사를 자동 파이프라인에 연결 |

G1(메모리를 영역별로 나눠 긴 정지를 줄이려는 정리 방식)을 아래 옵션으로 적용했다.

```text
-Xmx224m -XX:+UseG1GC -XX:MaxGCPauseMillis=200
```

224MiB는 기존 Serial의 실측 최대 약 222.38MiB와 거의 같은 수준이며 서버 RAM을 늘린 것이 아니다.
200ms는 목표일 뿐 모든 정지가 200ms 이하라는 보장은 아니다. G1도 CPU·추가 관리 메모리가 필요하고
심한 압박에서는 전체 메모리 정리를 할 수 있다. 사용 근거와 한계는
[Oracle G1 문서](https://docs.oracle.com/en/java/javase/17/gctuning/garbage-first-g1-garbage-collector1.html)를 따른다.

API 기본 Compose의 `JAVA_TOOL_OPTIONS`만 추가했다. 해석 결과에서 환경·이미지·DB·포트·볼륨 등의
다른 변경이 없는지 확인했다. 파일 소유권·권한과 진단 설정도 유지했다.
원래 Compose는 서버 안의 권한 제한 폴더에 보관하고, 상태 검증 실패 시 설정과 같은 이미지를 복구하도록 했다.
실제 서버에서는 원복이 필요한 상태 검사 실패가 없었다. DB ID·기동 시각·캐시는 유지됐다.

스왑 우선순위 실험은 채택하지 않았다. 원래 60으로 복원했고 `/etc/sysctl.d`에 영구 파일도 추가하지 않았다.
실험 코드와 결과는 Git에서 제외되는 `build/login-root-cause-y57hlthd/`에만 보존한다.
[Linux 공식 설명](https://docs.kernel.org/admin-guide/sysctl/vm.html#swappiness)대로 이 값은 상대적인 회수 우선순위이며
모든 스왑을 없애거나 이미 밀린 페이지를 즉시 되돌리는 설정이 아니다.

## 재실행·복구 시 주의

기존 이미지·DB·파일을 확인한 뒤 도구를 사용한다. 운영 Compose에는 비밀값이 있을 수 있어 저장소로 복사하지 않는다.
GC 설정 교체는 API 재시작을 포함하므로 요청·실시간 연결의 일시적인 실패가 가능하다.
이미 다른 운영자가 설정을 바꿨으면 도구가 덮어쓰지 않고 중단한다.

실패 후 30초 관측은 이번에 관측한 늦은 완료를 다루기 위한 제한이다. 서버 처리가 그보다 오래 멈추면
잔존 세션을 추가 확인해야 하며 모든 장애에서 영구적인 세션 정리를 보장하는 장치는 아니다.
최초/유휴 인증과 짧은 10 VU 시험이 통과해도 장시간 부하·500명 수용·모든 메모리 문제 해결을 뜻하지 않는다.
