# 로컬 500명 조회 지연의 원인 진단

최종 진단 실행: `memoryjar-e2e-ec9ae387a24a`, 2026-10-30.

**앱 CPU 한도와 부하 발생기의 CPU 한도가 응답 시간에 영향을 주는 것을 원상 복구 대조로 확인했다. DB 연결 대기는 크게 쌓였지만, 연결 풀을 10개에서 20개로 늘리는 것만으로 전체 응답 시간이 좋아지지는 않았다.**

이번 결과는 원인을 나누기 위한 로컬 실험이다. 소프트웨어를 최적화해 얻은 개선율이나 운영 서버의 동시 접속 한계로 발표하지 않는다. 기존 [500명 시험](LOCAL_500_CONCURRENT_USERS_2026-10-30.md)의 p95 502.84ms와 [1,000명 시험](LOCAL_1000_CONCURRENT_USERS_2026-10-30.md)도 그대로 보존한다.

## 1. 무엇을 어떻게 확인했나?

운영과 기존 로컬 DB를 사용하지 않고, 새 Docker internal 네트워크와 임시 MariaDB·앱·k6를 만들었다. 계정 10,000개 중 1,000개를 실제 로그인한 뒤, 최종 단계마다 서로 다른 500개 계정으로 저금통 목록·상세·쪽지를 조회했다. 사용자별 요청 완료 후 1초 대기, p95 ≤500ms, 오류율 <1%, 요청 제한 시간 3초를 유지했다.

데이터는 저금통 9,300개·멤버 12,000개·쪽지 21,000개다. 조회 대상은 50묶음의 저금통 150개·쪽지 6,000개다. 이미지·AI·메일·브라우저 3D·WebSocket 부하는 포함하지 않았다.

100명·300명 준비 단계 후 같은 JVM·같은 DB에서 아래 조건을 한 번에 하나씩 바꾸고 복구했다.

- 상세 k6 기록 저장: 켜기 → 끄기 → 끄기 → 켜기.
- 부하 발생기 CPU: 4 → 2. 앱 CPU는 2로 유지.
- 앱 CPU: 4 → 2. 부하 발생기는 4로 유지.
- DB 연결 풀: 20 → 10. 앱 CPU는 2, 부하 발생기는 4로 유지.

정상 기준을 넘은 실행도 실패로 남겼다. 진단 모드에서만 **지연 기준 초과·오류율 1% 미만**인 경우 다음 대조를 계속했다. 오류율·메모리·시간 보호 중단과 정상 모드의 중단 규칙은 유지했다.

기존 읽기 구간 계측은 요청 10개 중 1개에 적용했다. Hibernate 통계·MariaDB 정규화 SQL 집계·20ms 간격 JFR(실행 스택과 대기·GC를 표본으로 기록하는 JVM 기능)·1초 간격 자원 관찰을 사용했다. 이러한 계측 자체의 비용이 있어 원래의 무계측 성능 기록을 대체하지 않는다.

## 3. 확인한 주된 영향: CPU 할당 제한

### 부하 발생기

앱은 2 CPU로 유지했다. 부하 발생기를 4 CPU로 둔 쪽지 p95는 198.99ms였고, 다시 2 CPU로 제한하자 386.13ms로 늘었다. 2 CPU 복구 단계에서 부하 발생기 CPU는 Docker 샘플 최대 192.20%였다. CPU 100%는 대략 논리 CPU 하나의 사용량이다.

따라서 기존 결과에는 서버뿐 아니라 부하를 만드는 도구의 처리 여유도 영향을 주고 있었다. 같은 PC에서 두 프로세스가 자원을 공유하므로, 이것만으로 운영 서버 성능을 판단할 수 없다. 상세 기록을 끈 실행도 느렸으므로 파일 저장을 단독 원인으로 확정하지 않는다.

### 앱

부하 도구는 4 CPU로 고정했다. 앱을 4 CPU로 둔 쪽지 p95는 39.96ms였고, 2 CPU로 복구하자 114.45ms로 늘었다.

CPU throttling(정해진 CPU 사용량을 소진해 실행이 제한되는 상태)도 함께 관측했다. 요청 처리나 DB 연결 사용이 관측된 샘플 구간에서 제한이 발생한 CPU 주기의 비율은 **4 CPU에서 0%, 2 CPU 복구 후 약 33.3%**였다. 이 수치는 CPU 사용률이나 요청 시간의 33.3%를 뜻하지 않는다.

이 구간의 평균 CPU 사용량은 각각 약 171.7%·166.6%로 비슷했다. 평균이 2 CPU보다 낮아도 짧은 시간에 여러 작업이 몰려 할당량을 소진하면 제한이 걸릴 수 있다. 평균 CPU만 보면 놓치는 지연이었다.

앱 CPU를 늘렸을 때 DB 연결 대기도 줄고, 복구했을 때 다시 늘었다. CPU 제한과 연결 점유·반환 지연이 함께 작용한다는 해석을 뒷받침한다. 특정 메서드 하나만의 잘못으로 확정한 것은 아니다.

## 4. DB 연결 대기는 실제였지만 풀 확대만으로 해결되지는 않았다

연결 풀은 DB 연결을 빌려 쓰는 통로다. 연결이 모두 사용 중이면 다음 요청은 반납을 기다린다.

- 가장 느린 `summary-b2`에서 연결 10개가 모두 사용 중이었고, 기다리는 요청은 샘플 최대 **136개**였다.
- 해당 구간에서 수집된 쪽지 요청 표본의 평균 서버 처리 시간은 약 **320.56ms**, 연결 획득 시간 합계는 **281.03ms**, JDBC 실행 시간 합계는 **19.82ms**였다.
- 이는 전체 요청의 무작위 표본이 아닌 선택된 계측 표본이다. 전체 사용자 평균으로 발표하지 않는다. 중첩 구간도 더하지 않는다.

앱 4 CPU 구간의 쪽지 표본은 평균 연결 획득 약 1.43ms였고, 2 CPU 복구 후 약 12.06ms였다.

풀만 20개로 늘리면 기다리는 요청은 최대 4개로 줄었다. 그러나 쪽지 p95는 120.70ms였고, 다시 10개로 복구한 값은 106.88ms였다. **연결 대기를 줄인 것이 이번 실험의 전체 응답 개선으로 이어지지는 않았다.** 작은 차이를 통계적으로 유의한 악화라고 주장하지도 않는다.

따라서 연결 풀부터 무작정 확대하는 방향을 선택할 근거는 부족하다.

## 5. SQL·인증·스레드에서는 무엇을 확인했나?

### SQL과 N+1

수집된 정상 요청 표본에서 실제 JDBC 실행 수는 다음과 같이 일정했다. 인증의 세션 버전 확인 조회도 포함한 값이다.

| API | 요청당 SQL 수 |
| --- | ---: |
| 저금통 목록 | 6 |
| 저금통 상세 | 6 |
| 쪽지 목록 20개 | 10 |

작성자 fetch join과 첨부·리액션·댓글의 묶음 조회를 코드와 대조했다. 이번 데이터에서 쪽지마다 추가 쿼리가 붙는 N+1은 관측하지 않았다. 태그도 별도 컬렉션 쿼리가 아니라 JSON 칼럼 변환이다.

모든 최종 대조 단계에서 DB 행 잠금 대기·InnoDB 물리 페이지 읽기·디스크 임시 테이블 증가가 0이었다. `summary-b2`에서 쪽지 조회 SQL 형태의 DB 서버 평균 실행은 약 0.58ms였고, 쪽지 요청 표본의 연결 대기는 훨씬 컸다. 평균 SQL 시간만으로 드문 느린 쿼리까지 모두 배제하지는 않는다.

비어 있는 리액션·댓글 테이블에서 `no index used` 집계가 있었지만 조사 행 수가 0인 경우였다. 이 표시만으로 인덱스 누락이 병목이라고 판단하지 않았다.

### 인증

JWT 검증 중 한 번, claims 추출 때 한 번 토큰을 파싱하는 중복을 코드에서 확인했다. 또한 로그아웃·세션 폐기를 확인하는 DB 조회가 요청마다 실행된다.

그러나 여유 있는 4 CPU 구간에서 JWT 두 구간의 표본 평균은 각각 대체로 1ms 미만이었고, 가장 느린 구간에서는 DB 연결 대기가 큰 부분이었다. 중복 파싱은 개선 후보이며 현재 지연의 단독 원인으로 확정하지 않았다. 세션 버전 확인이나 권한 검사를 생략하지 않았다. 비밀번호 해싱은 로그인 준비에만 있고 조회 루프에는 없다.

### 요청 작업 스레드

Tomcat(HTTP 요청을 처리하는 서버)의 최대 작업 스레드는 200개였다. 대기 작업 증가가 관측됐지만, 표본만으로 이 상한 자체가 주원인이라고 확정할 수 없다. 스레드 수 확대 실험은 하지 않았다.

JFR에서 보인 `FileDispatcherImpl.write0`도 전체 호출 경로를 확인했다. 해당 추출 구간의 대부분은 MariaDB 소켓으로 SQL이나 트랜잭션 명령을 전송하는 경로였다. 메서드 이름만 보고 로그 파일 쓰기 문제로 단정하지 않았다.

## 6. GC도 지연에 기여했다

실제 사용된 GC는 Serial 계열이었다. JMX에서 `Copy`·`MarkSweepCompact`, JFR에서 `DefNew`·`SerialOld`를 확인했다.

- `json-a1`에 전체 GC 약 **214.48ms**가 1회 있었다.
- `generator-c2`에는 약 **239.83ms**가 1회 있었다.
- 원인은 JFR의 `Allocation Failure`였다. 객체를 배치할 공간 때문에 GC가 시작됐다는 용어이며 OOM(메모리 부족으로 할당 실패 예외가 발생하는 상태)과 같지 않다.
- 실제 OOM 중단은 없었다. 500명 대조에서 1초 간격으로 본 heap 사용량 최대는 단계별 약 26~33%였지만, 짧은 순간의 최고 사용량까지 잡았다는 뜻은 아니다.

전체 GC는 일부 지연에 기여할 수 있다. 다만 `summary-b2`는 전체 GC 0회·최대 관측 GC 정지 약 50ms인데 쪽지 p95가 약 1초였다. 앱 4→2 CPU 비교도 두 단계 모두 전체 GC 없이 지연 차이가 재현됐다. **GC 하나만으로 이번 지연 전체를 설명할 수 없다.**

객체 할당의 정확한 원인별 비중과 GC 설정 변경 효과는 아직 검증하지 않았다. heap이나 GC 옵션을 임의로 바꾸지 않았다.

## 7. 판단과 다음 우선순위

1. **측정 조건부터 고정한다.** 부하 도구 CPU 여유·기록 방식·준비 순서·시간을 맞춘다. 동시 사용자 수만 같다고 같은 부하 조건은 아니다.
2. **앱 CPU 제한과 요청당 처리 비용을 함께 본다.** 자원 대조 효과를 코드 개선율로 포장하지 않는다. 코드 개선을 한다면 같은 자원에서 요청당 CPU·할당 비용과 전체 응답을 검증해야 한다.
3. **연결 풀 확대를 우선 해법으로 선택하지 않는다.** 대기는 줄었지만 전체 지연 개선은 재현되지 않았다.
4. **중복 JWT 파싱·JPA/DTO 객체 생성은 후속 후보로 남긴다.** 실제 실행 표본은 Hibernate·JDBC·자료구조·직렬화 등 여러 경로에 분산됐다. 보안 검사 유지와 할당 표본 확인이 필요하다.

이번에는 서비스 기능을 최적화한 것이 아니라 원인 분리용 계측과 대조를 했다. 운영 서버·별도 물리 장비·장시간 부하·실제 이미지와 첨부를 포함한 데이터에서는 추가 검증이 필요하다. 1,000명 처리 성공이나 운영 최대 용량을 새로 증명한 결과도 아니다.

## 8. 초기 진단 도구 오류와 제외한 실행

초기에 수집기 자체의 cgroup 경로 호환, 이름 없는 JVM 스레드 처리, Windows 파일 교체 경쟁을 발견해 수정했다. Tomcat 실행기 형식과 bind 주소가 포함된 스레드 이름도 실제 런타임에 맞춰 처리했다. 단계별 명령·응답은 덮어쓰지 않는 새 파일을 사용한다.

`94782e495724`, `cd24ee215d2a`, `7b918e3d8859`, `da95097a7dd8`의 불완전 진단은 최종 대조 표에서 제외했다. 일부 정상 기록은 도구 회귀 확인에만 사용했다. 앞의 세 실행 및 부분 대조를 완성된 500명 원인 시험으로 발표하지 않았다.

최종 실행 `ec9ae387a24a`에서는 예정된 대조 10개가 모두 수집됐고 수집기 오류 파일은 없었다. 지연 실패 두 단계 때문에 부하 종료 코드와 통합 JUnit은 실패 상태를 유지했다. 이는 계측 누락이나 데이터 정리 실패와 구분한다.
