# 로컬 동시 사용자 1,000명 시험

후속: [같은 자원·데이터 규모의 500명 시험](LOCAL_500_CONCURRENT_USERS_2026-10-30.md)을 별도로 수행했다. 이 문서의 기존 1,000명 결과는 유지한다.

2026-10-30, 실행 `memoryjar-e2e-464bd4a49f36`.

**100명·300명 단계는 통과했다. 1,000명 단계에서는 응답 시간이 기준을 넘어 약 10초에 자동 중단됐다. 1,000명 안정 처리에 성공한 결과는 아니다. 시험 후 데이터와 임시 자원은 모두 삭제했다. 운영에는 연결하지 않았다.**

## 1. 무엇을 시험했나?

앞선 [1만 계정 저장 시험](LOCAL_10000_USERS_2026-10-30.md)은 실제 로그인 사용자가 10명이었다. 이번에는 같은 로컬 격리 도구를 확장해 **서로 다른 1,000개 계정으로 실제 로그인**하고 조회 부하를 만들었다.

VU(사용자 한 명의 요청 흐름을 흉내 내는 가상 사용자) 100명 → 300명 → 1,000명을 차례로 실행했다. 각 VU는 자기 계정으로 저금통 목록·상세·쪽지 목록을 조회하고, 요청이 끝난 뒤 1초를 쉰다. 따라서 **동시 사용자 1,000명은 초당 요청 1,000건이나 동시에 진행 중인 HTTP 요청 1,000개와 같은 뜻이 아니다.**

브라우저 1,000개·3D 화면 출력·WebSocket 연결·동시 회원가입·동시 로그인은 시험하지 않았다. 로그인 1,000건은 부하 전에 순차적으로 준비했다.

## 2. 운영과 기존 로컬 DB는 어떻게 보호했나?

- 기존 `graduation-local-db`와 별개로 새 MariaDB·시험 앱·k6를 생성했다.
- Docker `desktop-linux`의 실행별 `internal` 네트워크만 사용했다. 호스트 포트·영구 DB 볼륨·Docker 소켓을 앱에 연결하지 않았다.
- 외부 기본 경로 부재와 IPv4·IPv6·메타데이터 TCP 차단 검사를 통과했다.
- 앱에서 실제 JDBC 목적지 `db:3306/isolated_e2e`를 확인하고, Flyway 이력을 제외한 앱 테이블 24개가 처음에 모두 비어 있음을 검사했다.
- 실제 Controller·Service·Repository·CSRF·비밀번호 검증·인증 쿠키·MariaDB를 사용했다. S3·메일·AI와 예약 작업은 시험 대역으로 분리했다.
- 시험용 계정은 고유 접두사와 `example.invalid` 이메일을 사용했다. 실제 운영 사용자·사진·비밀번호를 가져오지 않았다.
- 실행 후 기존 로컬 DB의 컨테이너 ID·시작 시각·실행 상태가 작업 전과 같음을 대조했다. 기존 DB의 내용 전체를 대조한 것은 아니다.

## 3. 데이터와 실행 조건

| 데이터 | 개수 |
| --- | ---: |
| 전체 사용자·자체 로그인 자격정보 | 각각 10,000 |
| 실제 로그인 계정 | **1,000** |
| 배경 계정 | 9,000 |
| 전체 저금통 | 9,300 |
| 전체 저금통 멤버 | 12,000 |
| 전체 쪽지 | 21,000 |
| 오픈 기록 | 9,300 |

로그인 계정을 **10명씩 100묶음**으로 나눴다. 묶음마다 별도 저금통 3개·쪽지 120개를 사용했다. 각 계정은 해당 묶음의 저금통 3개에만 참여한다. 조회 대상은 총 300개 저금통·12,000개 쪽지다. 나머지 9,000개 계정은 배경 DB 규모를 만들며 실제로 요청하지 않는다.

기존 Entity와 PasswordEncoder를 사용했다. 로그인 계정 1,000명은 서로 다른 난수 비밀번호를 사용하고, 배경 계정은 준비용 난수 암호 하나의 해시를 공유한다. 계정 준비 시간을 1만 건의 실제 회원가입 성능으로 해석하지 않는다.

| 항목 | 설정 |
| --- | --- |
| 단계 | 100명 20초 → 300명 20초 → 1,000명 30초 예정 |
| 단계 사이 | 이전 프로세스를 제거하고 5초 대기 |
| 로그인 | 1,000개 계정 순차 준비 후 ID·세션·멤버십 검증 |
| 조회 비율 | 목록·상세·쪽지 약 30%·30%·40% |
| 요청 간격 | 요청 완료 후 사용자별 1초 대기 |
| 첫 요청 | 0~0.99초 범위에 분산 |
| 응답 시간 기준 | 각 API의 p95 ≤500ms |
| 오류 기준 | 응답 내용 오류율 <1% |
| 요청 제한 시간 | 3초 |
| 중단 | 10초 이후 응답 시간·오류율 기준 초과 시 k6 자동 중단 |
| 별도 보호 | 컨테이너 메모리 92%, PC 여유 메모리 768MiB 미만, 단계 시간 상한에서 중단 |

p95(요청 95%가 이 시간 안에 끝나는 지연 지표)는 k6의 HTTP 요청 시간이다. 연결 준비 대기와 브라우저 화면 출력까지 포함한 사용자 체감 시간은 아니다.

## 4. 실제 결과

**로그인 1,000건과 세션 검증은 모두 통과했다. 비로그인 401·비회원 403도 확인했다.** 순차 로그인 p95는 96.79ms였다. 준비 과정의 의도된 403 한 건은 조회 오류에 포함하지 않는다.

| 동시 사용자 | 집계 조회 | 실패 | 목록 p95 | 상세 p95 | 쪽지 p95 | 판정 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 100명 | 1,950건 | 0건 | 50.11ms | 71.90ms | 85.14ms | 통과 |
| 300명 | 5,858건 | 0건 | 60.87ms | 59.35ms | 71.28ms | 통과 |
| **1,000명** | **3,742건** | **15건 / 0.40%** | **1,968.36ms** | **2,080.58ms** | **2,037.41ms** | **지연 기준 실패·자동 중단** |

모든 단계에서 설정한 VU 수만큼 실제 실행 시작이 집계됐다. 1,000명 단계의 `activated_users`와 `vus_max`는 각각 1,000이다.

1,000명 단계는 30초 예정이었으나 **약 10초에 중단**됐다. 오류율은 1% 미만이었지만 세 API의 p95가 모두 500ms를 넘어 k6가 종료 코드 99로 종료했다. 이 결과를 30초 완주·안정 처리나 장시간 최대 처리량으로 발표하지 않는다.

이 단계의 HTTP 상태 집계는 **200 응답 3,727건·상태 0인 실패 15건**이다. 실행 로그에는 요청 제한 시간 초과 경고가 있었다. 상태 0은 HTTP 응답을 받지 못했다는 뜻이며 서버가 HTTP 500을 반환했다는 뜻이 아니다. 강제 중단된 미완료 반복도 있으므로 집계 요청만으로 시도된 모든 작업이 완료됐다고 해석하지 않는다.

세 단계에서 총 11,550건이 집계됐고 응답 검사 성공 11,535건·실패 15건이었다. 전체 합계로 1,000명 단계의 실패를 가리지 않는다.

## 5. 자원 기록에서 알 수 있는 것

Docker에는 CPU 8개·약 7.6GiB 메모리가 할당돼 있었다. 앱·DB·k6는 같은 PC에서 자원을 나눠 썼다.

| 대상 | 제한 | 1,000명 단계 샘플 최대 CPU | 샘플 최대 메모리 |
| --- | --- | ---: | ---: |
| 앱 | 2 CPU, 컨테이너 1,536MiB, heap 768MiB | **207.71%** | 732.2MiB |
| MariaDB | 메모리 768MiB, DB 파일용 tmpfs 512MiB | 108.35% | 469.7MiB |
| k6 | 2 CPU, 메모리 2,048MiB | **186.98%** | 985.1MiB |

CPU 100%는 대략 CPU 코어 하나다. 샘플 구간에 따라 제한 근처에서 작은 초과 표기가 가능하다. 단계당 각 대상의 샘플은 100명 4개·300명 6개·1,000명 5개였으며, 프로세스 초기화·종료 대기 구간도 포함한다. 실제 순간 최대값이나 JVM heap 사용량과 같지 않다.

확인한 사실:

- 앱 CPU가 2코어 한도 근처까지 사용됐다.
- k6도 CPU를 많이 사용했다. 부하 발생기의 영향까지 분리한 시험은 아니다.
- k6의 OOM(메모리 부족 강제 종료)은 없었고 별도 메모리·시간 보호 중단도 발동하지 않았다.
- 연결 준비와 응답 대기도 늘었다. 이것만으로 특정 SQL·DB 연결 풀·GC·Tomcat·인증 로직 중 하나가 원인이라고 확정할 수 없다.

**이번 조건에서 300명은 통과했고 1,000명은 지연 기준을 만족하지 못했다.** 300명이 최대 한계라는 뜻도 아니다. 301~999명은 측정하지 않았고, 부하 도구와 서버를 물리적으로 분리하지 않았기 때문이다.

다음 분석이 필요하다면 앱 CPU 프로파일·GC·DB 연결 풀 대기·쿼리 수/시간을 같은 시간축으로 수집하고, 부하 발생기 여유를 함께 확인해야 한다. 이번에는 원인을 추측해 서비스 코드·캐시·DB 설정을 바꾸지 않았다.

## 6. 실패 후에도 데이터는 삭제됐나?

**삭제와 정리 검증은 통과했다.** 부하 실패를 성공으로 바꾸지 않고, SQL 정리를 먼저 수행한 뒤 JUnit과 전체 실행을 실패 상태로 종료했다.

| 확인 | 결과 |
| --- | --- |
| 조회 전후 비즈니스 데이터 행 수 | 동일. 로그인 세션 1,000개 생성은 별도 확인 |
| 데이터 삭제 | 외래 키를 유지하고 해당 실행 접두사·가짜 이메일 범위만 자식부터 삭제 |
| 사용자·자격정보·세션·저금통·쪽지 | 모두 0건 |
| 전체 앱 테이블 | **24개 모두 시작 상태인 0건으로 복원** |
| 임시 컨테이너·네트워크 | 각각 **0개** |
| 임시 계정 명세·세션 파일 | 제거 |
| 보관 요약 | k6의 `setup_data`를 제거하고 숫자 `metrics`만 유지 |
| 기존 로컬 DB | ID·시작 시각 유지, 계속 실행 중 |
| 운영·커밋·푸시·배포 | 이번 작업에서 실행하지 않음 |
