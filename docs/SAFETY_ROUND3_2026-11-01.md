## 2. 기존 동작과 문제

1. **원본 사진:** Draft 생성에서 예외가 나면 사진·테두리를 즉시 삭제했다. DB가 실제로는 저장을 확정했지만 결과만 전달하지 못한 경우에는 정상 Draft가 참조하는 사진을 잃을 수 있었다.
2. **작성 권한:** 쪽지·댓글 등의 쓰기 작업은 멤버 여부를 조회한 다음 저장했다. 그 사이 강퇴가 먼저 확정돼도 예전 검사 결과로 저장을 이어갈 수 있었다.
3. **동시 뽑기:** 저금통 잠금보다 먼저 일반 조회를 시작했다. MariaDB 기본 `REPEATABLE READ`(처음 조회한 시점의 데이터를 같은 작업 안에서 계속 읽는 방식)에서는 잠금 대기 후에도 다른 요청의 오늘 카드를 못 보고 중복 INSERT를 시도할 수 있었다. DB 고유 제약이 중복은 막지만 API는 오류를 반환할 위험이 있었다.
4. **목록 화면:** 다른 API에서 로그인 만료를 감지해 App의 사용자 정보를 지워도, 이미 표시한 저금통 목록은 자체 상태에 남았다.
5. **이용 안내:** 공통 API가 이전 계정 요청을 취소해도 안내 Provider의 catch/finally가 새 계정의 오류·저장 표시를 바꿀 수 있었다.

## 3. 바꾼 동작

### 원본 생성과 실패 후 확인을 같은 잠금으로 연결

원본 업로드 서비스는 DB 트랜잭션(저장 결과를 함께 확정하거나 취소하는 범위) 밖에서 이미지 검증·심사·S3 요청을 수행한다. 짧은 Draft 생성 구간에서만 사용자 행을 잠근다. 생성 실패 후에는 별도 새 트랜잭션으로 같은 사용자 행을 잠가 생성의 확정·취소 결과를 기다린다.

DB에 원본 참조가 없다는 것을 확인해야 사진과 테두리를 삭제한다. 참조가 있거나, 사용자·DB 결과를 확인할 수 없으면 보존한다. 확인 중 별도 오류가 나도 최초 오류를 그대로 반환한다. native SQL(직접 작성한 DB 조회)로 삭제 표시된 Draft의 참조도 제외하지 않는다.

### 쓰기 권한은 저장 확정까지 유지

쪽지 생성, 댓글 생성·수정·삭제, 리액션, 채팅 전송, 추억 뽑기는 기존 멤버 잠금 메서드를 재사용한다. 강퇴·탈퇴가 먼저 멤버를 잠갔다면 기다린 뒤 최신 참여 상태로 403을 반환한다. 쓰기가 먼저 잠갔다면 강퇴가 기다렸다가 진행한다.

잠금 순서는 멤버 → 쪽지 또는 저금통으로 맞춘다. 전체 저금통을 먼저 잠근 뒤 멤버를 기다리는 순서를 추가하지 않는다. `requestId`가 없는 기존 채팅 요청에도 같은 권한 보호를 적용하고, 식별자가 있는 요청의 중복 방지 동작은 유지한다. 일반 조회에는 쓰기 잠금을 추가하지 않는다.

### 잠금 대기 후 최신 뽑기 결과 확인

`drawToday`만 `READ_COMMITTED`(조회할 때마다 다른 작업이 확정한 최신 데이터를 읽는 방식)로 실행한다. 저금통 잠금을 기다린 두 번째 요청은 첫 요청이 저장한 오늘 카드를 읽는다. 기존 첫 생성 201·이미 존재하는 결과 200 계약과 DB 고유 제약은 유지한다.

### 로그인 상태와 목록 화면을 함께 초기화

App이 확인한 사용자와 로그인 확인 상태를 목록 화면에 전달한다. 계정별 React key(계정이 바뀌면 화면의 이전 상태를 새로 만드는 기준)를 사용해 목록·페이지·오류를 초기화한다. 로그인 확인 중이거나 사용자가 없으면 기존 목록을 표시하지 않고 조회도 시작하지 않는다.

같은 화면의 목록 조회에는 기존 `useRequestGate`를 적용한다. 오래된 성공·오류·로딩 종료가 새 상태를 덮지 못한다. 이미 있던 카드 UI·이용 안내·페이지 이동은 유지한다.

### 이용 안내의 모든 응답을 현재 계정에 한정

기존 `useRequestGate`로 초기 조회·수동 새로고침·완료 저장의 성공·실패·종료 처리를 확인한다. 계정 변경 직후에는 안내 진행 상태와 오류·저장 표시를 먼저 지운다. 이전 계정의 취소 오류를 새 계정 안내 오류로 표시하지 않으며, 늦은 finally가 새 저장의 진행 표시를 해제하지 못한다.

완료 버튼을 같은 순간 두 번 눌러도 저장 요청은 하나만 시작한다. 오래된 요청의 오류는 호출자에게 전달하되 현재 Provider의 화면 상태는 바꾸지 않는다.

## 4. 수정 이유와 영향 범위

데이터 손실 가능성이 있는 삭제는 DB 결과를 확인한 뒤에만 수행한다. 권한 확인과 저장을 같은 잠금 범위로 묶고, 화면 응답은 현재 계정에서 시작한 요청에만 적용한다.

Controller·DTO·CSRF·쿠키·CORS 계약은 바꾸지 않았다. 쓰기 경합에서 강퇴가 먼저 확정되면 기존 권한 오류인 403으로 거절한다. 뽑기 결과와 목록 응답 필드는 그대로다. Draft를 기존 Jar에 적용하는 구조 변경도 하지 않았다.

기존 변경의 `3e0f0e9` 푸시와 이번 로컬 수정을 구분한다. 이번 5개 수정에 대한 추가 커밋·푸시·배포는 이 문서 작성 시점에 수행하지 않았다.
