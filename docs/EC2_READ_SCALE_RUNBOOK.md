# 독립 계정 50~300 VU 조회 시험 준비

## 목적과 데이터

사용자가 VU당 별도 계정 유지를 선택했다. 기존 10명 묶음을 보존하고 같은 구조의 묶음 29개를 추가한다.
총 시험 계정 300개·저금통 90개·멤버 관계 900개·쪽지 3600개·오픈 이벤트 90개다.
계정마다 저금통 3개·각 저금통 쪽지 40개를 조회하므로 계정당 데이터 조건은 기존과 동일하다.
전체 DB 데이터 양은 늘어나므로 첫 10 VU 결과와 완전히 동일한 DB 상태는 아니다.
독립 계정 300개도 실제 사용자 300명의 행동·장시간 사용·쓰기·WebSocket·이미지 부하를 대표하지 않는다.

기존 도구는 10계정만 허용했다. 그 제한을 느슨하게 하지 않고 상위 단계 도구를 분리했다.
기존 운영 API·DTO·인증 정책·migration·프론트엔드·Heap/풀 크기는 변경하지 않는다.
새 의존성을 추가하지 않는다. 실제 비밀번호·JWT·원본 SQL·사용자 정보는 로그/Git에 출력하지 않는다.

## 안전 절차

1. 현재 배포·최신 백업·PC 사본 확인. plan은 build 아래에만 생성한다.
2. backup 복원 전용, network=none 컨테이너에서 정확한 SQL의 강제 롤백·중복 거절·기존 행 checksum 보존 검사.
3. proof의 plan/SQL/백업 해시, 30분 이내 백업, 동일 배포를 확인한 경우에만 명시 승인으로 한 번 INSERT.
4. 불확실한 통신 오류가 발생하면 INSERT를 재시도하지 않는다. 먼저 DB 반영 여부를 확인한다.
5. 확장 후 집계·외부 사용자 혼입·활성 세션 확인 및 새 백업·복원 검사.
6. 50 → 100 → 200 → 300을 한 단계씩만 실행. API 기준, 자원 기준, 종료 후 회복 상태를 검토한다.
7. 인증 준비·조회·세션 정리를 분리한다. 실제 비용 서비스 API는 포함하지 않는다.

상위 단계는 로그인 준비량이 많으므로 setup 상한 20분·정리 상한 15분을 두되 단건 요청 제한은 기존 3초다.
조회 구간은 단계마다 60초, 응답 후 1초 휴식이다. 각 단계는 감시기 소유 k6로 실행한다.
감시기 전체 실행 상한도 설정한다. 정상 표본 2개 전에는 k6를 시작하지 않는다.
강제 중단 시 k6 summary/로그아웃이 누락될 수 있으므로 원본과 남은 전용 세션을 반드시 확인한다.
