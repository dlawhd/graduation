# 화요일 배포 이후, 부하 시험을 어디까지 했을까?

- 정리 날짜: **2026년 10월 21일 수요일**, 한국 시간 기준.
- 대상 기간: **2026년 10월 20일 화요일~21일 수요일 새벽**.
- 대화 시작점: “오케이 배포까지 완료했는데 이제 뭐 해야 하지?” 이후의 점검·측정·의사결정.
- 작성 근거: 현재 시험 코드, 날짜별 결과 문서, 로컬 원본 JSON 기록. 질문마다의 정확한 발언 시각은 재구성하지 않았다.

## 1. 우리의 목표

**현재 EC2(인터넷에서 빌려 쓰는 서버)가 여러 사람의 요청을 얼마나 잘 처리하는지, 개선하기 전에 믿을 만한 기준값을 남기는 것**이다.

처음부터 “300명을 처리했다”는 결과를 만드는 것이 목표는 아니다. 어디까지 괜찮고, 어느 조건에서 느려지거나 실패하는지 알아야 나중에 같은 시험으로 개선 효과를 비교할 수 있다.

시험은 실제 두 사람의 계정이 아닌 **전용 시험 계정**으로 진행했다. VU(동시에 반복 요청하는 가상 사용자)마다 서로 다른 계정을 사용했다. VU 50명은 실제 가입자 50명이나 초당 요청 50건과 같은 뜻이 아니다.

## 2. 먼저 알아두면 쉬운 말

| 용어 | 쉬운 설명 |
| --- | --- |
| 부하 시험 | 여러 사람이 동시에 서비스를 쓰는 상황을 만들어 보는 시험 |
| 계측 | 어디서 얼마나 기다리는지 알아보도록 시간을 재고 기록하는 일 |
| p95 | 응답 시간을 빠른 순으로 줄 세웠을 때 약 95%가 끝나는 경계 시간 |
| 요청 제한 시간 | 이 시간이 지나도 답이 없으면 해당 요청을 포기하는 상한 |
| Heap | 자바가 객체를 보관하는 메모리 공간 |
| GC | 더는 필요 없는 자바 객체의 메모리를 정리하는 작업 |
| DB 연결 풀 | 서버가 DB와 통신할 연결을 미리 만들어 빌려 쓰는 곳 |
| 스왑 | RAM이 아닌 디스크에 메모리 내용을 보관하는 기능 |
| 디스크 대기 | CPU가 계산하기보다 디스크 작업이 끝나기를 기다리는 상태 |
| 유휴 | 사용자 업무 요청 없이 쉬고 있는 상태. 감시 요청까지 없는 상태는 아님 |
| 회복 확인 | 시험을 끝냈을 때 메모리·연결·디스크 이동이 안정되는지 살펴보는 일 |

스왑에 자료가 남아 있는 것 자체가 실패는 아니다. **필요한 메모리를 디스크에서 자주 가져오느라 응답이 늦어지는지**가 중요하다.

## 3. 어떤 순서로 진행했나?

| 순서 | 한 일 | 확인한 내용 |
| --- | --- | --- |
| 1 | 배포와 설정 확인 | 새 계측이 들어간 이미지·기동 상태·메모리 설정·관리 지표 보호 확인 |
| 2 | 느린 요청을 나눠 재는 기능 준비·배포 | 인증·서비스·DB 연결 획득·SQL 실행을 구분하는 계측 추가 |
| 3 | 전용 계정 3개로 소량 확인 | 24개 요청 성공, 조회 상세 기록 12개 확인. 예전 4.61초 내 정보 지연은 이때 재현되지 않음 |
| 4 | 유휴 문제와 동시 부하를 분리 | 유휴 후 느린 첫 요청은 미해결로 남기고, 동시 조회를 별도로 평가하기로 결정 |
| 5 | 10 VU·60초 조회 | 조회와 직후 회복 조건 통과 |
| 6 | 10 VU·30분 조회 | 조회는 통과. 직후 회복 자료에는 공백 발생 |
| 7 | Heap 증가 원인 구분 | 자연 GC 뒤 사용량이 크게 줄어드는지, 오래 남는 객체 영역이 계속 커지는지 비교 |
| 8 | 50 VU·500ms 목표 | 짧은 조회 구간에서 목표 초과로 자동 중단. 종료 후 스왑 이동도 회복 기준 일부 미달 |
| 9 | 임시 목표를 2초로 변경 | 별도 기록으로 재시험했지만 목표 초과로 중단 |
| 10 | 임시 목표를 5초로 변경 | 두 번째 계정 준비 중 내 정보 조회 시간 초과. 동시 조회는 시작하지 못함 |
| 11 | 다음 방향 결정 | 개선 전 측정은 하되 준비 실패를 숨기지 않고, 자원 안전장치는 유지하기로 함 |

계측 코드를 넣는 것은 **느린 원인을 찾을 도구를 추가하는 것**이지, 그 자체로 성능을 개선했다는 뜻은 아니다. 상세 조회 계측은 소량 진단 때 켰다가 종료했고, 아래 동시 조회 시험에서는 OFF(꺼짐), 자원·로그인 계측은 유지했다.

## 4. 실제 조회 결과

각 행은 **서로 다른 실행**이다. 같은 시험의 숫자를 바꾼 것이 아니다.

| 실행 | 당시 API별 p95 목표 | 완료 조회 | 목록 / 상세 / 쪽지 목록 p95 | 판정 |
| --- | ---: | ---: | --- | --- |
| 10 VU·60초 | 500ms | 576건 | 87.841 / 74.737 / 110.067ms | 조회·직후 60초 회복 통과 |
| 10 VU·30분 | 500ms | 17,271건 | 41.505 / 40.998 / 48.736ms | 조회 통과, 직후 회복 미관찰 |
| 50 VU·첫 시험 | 500ms | 325건 | 1,147.065 / 1,171.790 / 1,170.751ms | 조회 약 7.8초에서 중단 |
| 50 VU·2초 재시험 | 2,000ms | 62건 | 2,617.935 / 2,699.113 / 2,643.435ms | 조회 약 5.6초에서 중단 |
| 50 VU·5초 시도 | 5,000ms | **0건** | 측정할 동시 조회 없음 | **준비 단계 실패** |

10 VU·30분 조회는 평균 약 **9.60 req/s(초당 요청 수)**였다. 응답을 받은 뒤 1초 쉬는 조건이므로 서버의 최대 처리량은 아니다. 조회 비율은 목록 30%·상세 30%·쪽지 목록 40%로 정했다.

첫 네 실행에서 완료·검증된 조회 표본의 오류는 0건이었다. 하지만 **완료 표본의 오류율 0%와 시작한 모든 요청의 성공률은 다르다.** 2초 재시험 중 중단된 진행 중 요청 50건은 Nginx(요청을 자바 서버에 전달하는 프로그램)에서 499(클라이언트가 먼저 연결을 닫음)로 따로 확인됐다.

두 50 VU 조회 모두 예정한 60초를 채우지 못했다. 짧은 구간의 결과를 장기 수용 능력이나 안정 상태의 최대 처리량으로 설명하면 안 된다. 준비·로그아웃을 포함한 전체 실행 시간을 동시 조회 시간으로 쓰지도 않는다.

## 5. 30분 조회 후 왜 바로 50명으로 가지 못했나?

30분 조회가 끝난 뒤 로컬 결과 정리 도구에서 **시각 읽기 오류**가 발생했다. 자릿수가 긴 시각을 Python 3.8이 읽지 못한 문제였다. 원본은 보존하고 파서(자료를 읽는 코드)를 고쳐 다시 집계했다. 서버에 30분 요청을 또 보낸 것은 아니다.

그 사이 약 **3시간 17분의 회복 관측 공백**이 생겼다. 따라서 “30분 시험 직후에도 안정적이었다”고 말할 수 없다.

나중에 다시 관찰했을 때 Heap이 75%를 30초 이상 넘어 기존 안전 기준이 발동했다. 이것만으로 메모리 누수를 확정하지 않았다.

| 추가 확인 | 결과와 의미 |
| --- | --- |
| 자연 GC 전후 | Heap이 약 81%대에서 28.29%로 감소 |
| Old Gen(오래 살아남은 객체가 모이는 영역) | 자연 GC 전후 약 61.99MiB로 유지 |
| 기존 30분 자료의 Old Gen 중앙값 | GC 직후 표본에서 초반 약 66.71MiB → 후반 약 62.09MiB |
| 새 10분 준비 관찰 | 조건 통과. 그 뒤 50 VU 실행 |

관측 범위에서는 “계속 남는 객체가 증가한다”기보다 **정리 전 객체가 쌓였다가 회수되는 모습**에 가까웠다. 모든 기능에 메모리 누수가 없다는 증명은 아니다. 강제 GC·서버 재시작으로 수치를 낮추지도 않았다.

## 6. 스왑과 디스크에서 무엇을 발견했나?

첫 50 VU 시험 후 회복 관찰에서 마지막 6개 표본 평균 스왑 쓰기가 약 **1.641MiB/초**로, 기존 회복 기준 1MiB/초를 넘었다. 나중에 안정된 관찰이 있어도 이 실패 기록은 지우지 않았다.

2초 재시험의 느린 구간에서는 다음 현상이 함께 관측됐다.

| 같은 구간의 지표 | 관측값 |
| --- | ---: |
| CPU | 약 11.14% |
| 디스크 대기 | 약 66.97% |
| 스왑 읽기 / 쓰기 | 약 13.49 / 4.88MiB/초 |
| DB 연결 사용 / 대기 | 10개 / 10개 |
| GC 누적 시간 증가 | 11ms |

**CPU가 낮아도 서버가 빠르다는 뜻은 아니다.** 책상에서 계산을 못 하는 게 아니라, 창고에서 자료가 오기를 기다리는 상황일 수 있다.

Java 전체 메모리는 Heap만이 아니다. 클래스·실행 코드·스레드 등도 메모리를 쓴다. 따라서 Heap 상한 224MiB만 보고 약 914MiB 서버의 나머지가 모두 여유라고 계산할 수 없다.

스왑 이동과 디스크 대기가 강한 병목 후보지만, 특정 코드·SQL·설정 하나를 원인으로 확정한 것은 아니다. DB 연결 대기가 보였다는 이유로 연결 수를 무작정 늘리지 않았다.

새 부하 없는 10분 관찰과 실패 뒤의 별도 10분 관찰에서는 안정 조건을 만족했다. 다만 이 관찰은 기존 시험 직후의 모든 시간을 포함하지 않으며, 부하 중 응답 실패를 사후 통과로 바꾸지 않는다.

## 7. 가장 최근 5초 조건에서는 정확히 어디서 실패했나?

2026년 10월 21일 **00:58경**, 50개 계정의 준비를 시작하다 다음 위치에서 중단됐다.

| 순서 | 결과 |
| --- | --- |
| 첫 계정 로그인 → 내 정보 → 저금통 목록 | 성공 |
| 두 번째 계정 로그인 | 성공, 약 0.37초 |
| **두 번째 계정 내 정보 조회** | **약 5.01초 후 시간 초과** |
| 동시 조회 단계 | 시작하지 못함, 완료 조회 0건 |
| 로그인한 두 계정 로그아웃 | 모두 성공 |
| 전용 계정 잔존 활성 로그인 | 0건 확인 |

준비 실패 구간에 디스크 대기 최고 약 **69.0%**, 스왑 읽기 최고 약 **13.5MiB/초**가 관측됐다. CPU 최고 약 11.0%, Heap 최고 약 58.8%였다. 메모리를 디스크에서 가져오는 대기가 의심되지만, 이를 원인 확정이나 50명 동시 처리 실패로 표현하지 않는다.

계정 정리 뒤 약 61초·11개 표본 관찰은 회복 조건을 통과했다. API·DB 재시작 0회, OOM(메모리 부족으로 프로세스가 종료됨) 표시 없음도 확인했다. 이는 해당 관찰 시점의 결과이며 현재 서버 상태를 새로 확인한 것은 아니다.

## 8. 500ms → 2초 → 5초는 성능 개선일까?

**아니다. 합격선을 바꾼 것이지 서버가 빨라진 것이 아니다.**

| 구분 | 의미 |
| --- | --- |
| 기존 목표 500ms | 처음 합의한 조회 목표. 개선 목표로 보존 |
| 임시 목표 2초 | 별도 실행에 적용한 허용 목표. 해당 실행 실패 |
| 현재 임시 목표 5초 | 사용자 승인으로 선택한 허용 목표 |
| 개별 요청 제한 5초 | 답이 오지 않을 때 요청을 중단하는 상한. 목표 변경과 별개로 유지 |

목표와 요청 제한이 모두 5초라 현재 조건은 빠른 서비스의 증명보다 **제한 시간 안에 응답·본문 검증이 완료되는지 확인하는 성격**이 강하다. 과거 결과를 새 목표에 맞춰 통과로 바꾸거나, 목표 완화를 개선율로 적지 않는다.

## 9. 유지한 안전장치와 제외한 것

| 항목 | 유지한 조건 |
| --- | --- |
| 조회 오류율 | 1% 미만 |
| CPU·Heap·DB 풀 | 각각 70%·75%·80%를 초과한 상태가 30초 지속하면 부하 중단 |
| 즉시 중단 | Heap 90% 이상, 가용 RAM 64MiB 미만, 지표 수집 장애·서버 교체/재시작·OOM 등 |
| 종료 후 회복 | 가용 RAM 100MiB 이상, Heap 75% 이하, DB 대기 0, 마지막 표본의 평균 스왑 입출력 각각 1MiB/초 이하·디스크 대기 5% 이하 등 |
| 중단 대상 | 감시기가 시작한 부하 도구만 중단. API·DB는 종료하지 않음 |
| 데이터 보호 | 최신 백업·PC 사본·해시 확인, 전용 계정 검증과 세션 정리 |
| 실제 외부 호출 | Cloudflare AI·Rekognition·SES·S3 전송 제외 |

기존 EC2·통신·백업 자원을 쓰므로 전체 비용이 0원이라는 의미는 아니다. 부하 단계에서는 서버 크기·스왑 정책·DB 연결 상한을 바꾸지 않았고, 스왑 강제 해제·캐시 강제 삭제·불필요하다고 단정한 서비스 중지도 하지 않았다.

이 기록은 **일반 조회 시험**이다. 쓰기·댓글·리액션·채팅·WebSocket(연결을 유지하며 실시간 메시지를 주고받는 방식) 부하, 외부 서비스 대역 전체 장애 시험, 별도 실제 S3 전송 시험까지 완료했다는 뜻이 아니다.

새 라이브러리·운영 API·DB 구조·프론트 화면을 바꾸지 않았다. 유지보수 측면에서는 과거 조건을 재현하면서 새 조건을 명확히 선택할 수 있고, 안전 측면에서는 실패·빈 표본·잘못된 승인을 통과로 처리하지 않는다. **성능 개선 코드를 적용한 변경은 아니다.**

관련 Node 도구 시험 **34개를 이번 문서 정리·커밋 전에 다시 실행해 모두 통과**했다. 실제 k6의 옵션 해석 검사도 포함하지만 외부 HTTP 요청은 보내지 않았다. `git diff --check`도 통과했다. 이전 5초 시도 전에는 이 34개 및 로컬 실행 보조 검사 8개가 통과했다. 서로 겹치는 재실행 숫자를 누적해서 서로 다른 시험 수처럼 표현하지 않는다.

원본 분석 JSON 다섯 개와 위 조회 건수·오류·API별 p95를 다시 대조했다. 커밋 대상 10개 파일의 비밀키·AWS 자격 증명·JWT 형식 패턴 검사에서 발견 0건이었다. 이는 알려진 형태의 검사이며 모든 종류의 비밀값 부재를 자동으로 증명하는 것은 아니다.

운영 Java·프론트엔드 코드 변경이 없어 이번 정리에서는 해당 빌드나 운영 부하를 다시 실행하지 않는다. 이전 Java·격리 HTTP 검증은 [조회 계측 문서](READ_REQUEST_DIAGNOSTICS_2026-10-20.md)에 있으며 이번 재실행 결과와 구분한다.

## 11. 다음에 무엇을 할까?

최신 합의는 **개선 전 한계를 먼저 측정하고, 개선 뒤 같은 조건으로 비교하자**는 것이다. 단, 준비 실패를 무시하거나 안전 기준을 없애지는 않는다.

| 순서 | 다음 작업 | 완료 조건 |
| --- | --- | --- |
| 1 | 이번 코드·기록을 한국어로 커밋·푸시 | 시험 산출물·비밀값·관련 없는 파일 제외 |
| 2 | 자동 배포 여부와 새 기준본 확인 | 실제 이미지·기동 상태·설정·자원 확인. 푸시 성공과 배포 성공을 구분 |
| 3 | 계정 준비와 실제 조회 측정을 더 분리할 수 있는지 검토 | 준비 단계의 시간 초과를 별도 기록. 준비 실패를 건너뛰거나 임의 제한 연장하지 않음 |
| 4 | 준비가 정상 종료되면 개선 전 50 VU 재측정 | p95 5초·요청 제한 5초·오류율·자원·회복 모두 평가 |
| 5 | 통과한 경우에만 100 → 150 → 200 → 300 VU | 매 단계 독립 계정·백업·실행 조건·종료 후 회복 확인. 하나라도 실패하면 중단 |
| 6 | 처음 실패한 조건에서 원인 분석·개선 | 메모리·디스크·인증·DB·요청 대기 중 어디가 병목인지 근거로 결정 |
| 7 | 같은 조건으로 다시 측정 | 서버·데이터·비율·대기 시간·계측·목표가 같은 비교 결과 보존 |

**아직 구현하지 않은 부분:** 현재 5초 상위 실행 모드는 50·100 VU까지만 지원한다. 150·200·300 VU의 5초 실행·선행 단계 통과 확인은 추가 구현·시험이 필요하다. 승인받았다는 사실과 실행 준비·실행 성공은 서로 다르다.

계정 준비 분리를 위해 서버 코드를 미리 최적화하거나 실패를 숨기는 방식은 쓰지 않는다. 분리 도구를 변경한다면 새 실행 조건으로 명시하고, 인증 준비의 성능과 순수 조회의 성능을 각각 보고한다. 안전 기준 미달이면 준비 분리 여부와 관계없이 중단한다.

## 12. 이력서에는 어떻게 쓸 수 있을까?

현재 근거로는 다음 정도까지 설명할 수 있다.

> 독립 시험 계정으로 실제 EC2의 10 VU·30분 조회를 측정해 17,271건의 완료 조회와 오류 0건을 확인했다. 상위 부하에서는 응답 지연·스왑·디스크 대기를 함께 관측하고 자동 중단과 시험 세션 정리를 검증했다. 종료 직후 회복 관측에는 공백이 있어 장기 안정성 전체 통과로 주장하지 않았다.

아직 “300명 처리 성공”, “응답 시간 ○% 개선”, “메모리 누수 완전 해결”이라고 쓸 근거는 없다. 같은 조건의 개선 전후 측정이 끝난 뒤에만 `(개선 전 시간 - 개선 후 시간) ÷ 개선 전 시간 × 100`으로 감소율을 계산한다.
