# 저장된 저금통의 3D 텍스처 읽기

- `GET /api/v1/jars/{jarId}/design/texture?part=IMAGE|BODY`: 로그인한 활성 멤버만 저장된 디자인 PNG를 읽는다. 탈퇴/비멤버는 403, 없는 디자인/테두리는 404, 잘못된 part/번호는 400이다.
- 응답은 `image/png`, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`. 오류 시 S3 키/서명을 노출하지 않는다. 외부 URL/키를 요청 입력으로 받지 않는다.
- `JarDesignResponse`에 선택 필드 `imageTextureUrl`, `bodyArtworkTextureUrl`을 추가한다. 기존 `imageUrl`, `bodyArtworkUrl`, 저장 좌표와 DTO 생성자를 유지한다. DB 마이그레이션은 없다.
- 짧은 읽기 트랜잭션에서 멤버/저장 키를 조회하고 S3 I/O는 트랜잭션 밖에서 실행한다. PNG/16MiB 제한을 적용한다.
- 프론트는 3D를 켤 때만 기존 인증 API 모듈로 Blob을 읽고 로컬 URL로 사용한다. 회전/사진 배치만 바뀌면 다시 읽지 않는다. 종료/변경 시 요청 취소와 Blob URL/GPU 해제를 수행한다.
- 서버 필드가 없는 이전 응답/로컬 예시는 기존 URL로 호환된다. 저장 전 Draft의 Presigned 이미지 읽기는 기존 CORS 경로를 유지한다.
- 백엔드와 프론트 반영이 모두 필요하다. 운영 배포/S3 접근과 실제 사용자 이미지 검증은 로컬 합성·Mock 검증과 별개다.

## 최종 이미지의 서버 메모리 재사용

- 매 요청의 JWT/세션 확인, 활성 멤버 권한 확인 및 현재 디자인 조회는 유지한다. 그 뒤 DB에서 얻은 `(bucket, objectKey)`로 검증된 PNG 바이트만 재사용한다. 클라이언트가 임의 캐시 키를 지정하는 API는 없다.
- 최초 S3 읽기에서 기존 PNG/16MiB 검증과 스트림 닫기를 모두 마친 뒤 저장한다. 실패·잘못된 PNG는 저장하지 않는다. 최종화는 UUID가 포함된 별도 영구 키를 생성하므로 새 디자인은 다른 항목이다. 같은 S3 키의 외부 덮어쓰기·삭제는 최대 유효 기간 동안 즉시 반영되지 않을 수 있다.
- 기본값: 저장 후 60초 고정 만료(읽을 때 연장하지 않음), 이미지 1개당 최대 4MiB, 저장 이미지 바이트 합계 최대 16MiB, 최대 64개. 초과 시 최근에 쓰지 않은 항목부터 제거한다. 4MiB 초과~기존 허용 16MiB 이미지는 정상 반환하지만 캐시에 보관하지 않는다.
- 만료 항목은 조회 시 사용하지 않고, 15초 주기의 기존 Spring 스케줄러 작업으로도 참조를 제거한다. 작업 지연이나 JVM GC(쓰지 않는 메모리를 회수하는 작업)에 따라 실제 메모리 회수 시점은 다르다. 재시작/종료 시 캐시를 비우며 디스크·Redis·CDN에는 저장하지 않는다.
- 같은 객체의 진행 중 읽기는 최대 8개 객체까지 공유한다. 다른 객체의 I/O를 전역 잠금으로 직렬화하지 않는다. 공유 객체 수 상한을 넘는 새 객체는 기존 직접 읽기로 우회한다. 공유 대기자는 최대 125초 대기하고, 중단/시간 초과가 다른 요청의 원본 S3 읽기를 취소하지 않는다.
- 응답마다 배열 복사본을 반환해 응답 코드가 캐시/대기자의 원본을 수정하지 못하게 한다. 16MiB 제한은 저장된 이미지 바이트 합계이며, 객체/키 메타데이터·진행 중 다운로드·응답 복사본·요청별 메모리를 포함한 JVM 전체 상한이 아니다.
- 활성 멤버가 아닌 사용자나 삭제된 디자인은 캐시가 남아 있어도 기존 403/404로 거절한다. 권한 확인 이후 응답 완료 전 권한이 바뀌는 동시성 창은 기존 S3 읽기와 동일하며 즉시 회수를 보장하는 새 정책은 아니다.
- `Cache-Control: no-store`, PNG 응답, API/DTO/DB 구조, 사진 해상도·내용은 그대로다. 서버 메모리 재사용만 추가하며 로그나 진단 API에는 객체 키·사진·인증정보를 출력하지 않는다.
- 서버별 메모리 캐시이므로 여러 인스턴스 간 공유하지 않는다. 비활성화는 `--app.jar-design.texture-cache-enabled=false` 후 재시작한다. 실제 배포와 운영 성능 검증은 별도다.

## 로컬 전용 S3 구간 진단

- 캐시 기능과 계측 스위치는 별개다. 캐시는 기본 유지하고, 세부 숫자는 `local` 프로필 + `--app.monitoring.texture-diagnostics-enabled=true`일 때만 수집한다. `prod`가 함께 활성화되면 수집하지 않는다. 분석 후 계측 인수만 제거해도 캐시는 유지된다.
- 실제 S3 읽기에만 요청별 SDK 관찰자를 연결해 인증정보 준비·서명·연결 획득·연결/전송/응답 헤더 수신·재시도 등의 허용된 숫자를 기존 loopback 관리 진단에 추가한다. 서비스 API/DTO·PNG·no-store·권한 검사·인증 제공자·재시도 정책은 유지한다. 객체 키·사진·URL·인증정보·AWS 요청 ID·예외 원문은 수집하지 않고 외부로 전송하지 않는다.
- 캐시 HIT에는 S3 요청/지표가 없고, MISS/WAIT/상위 구간과 SDK 세부 구간은 중첩될 수 있어 합산하지 않는다. 연결 획득 지표는 DNS/TCP/TLS를 개별 분리하지 않으며 SDK 스트리밍 마지막 바이트 지표를 전체 이미지 읽기로 간주하지 않는다. 요청별 누락/잘림을 표시하고 관찰자 실패가 다운로드 결과를 바꾸지 않게 한다.
- 실측 및 한계는 `docs/performance/3d/README.md`와 `backend-texture-sdk-breakdown-2026-10-25.json`에 기록했다. 최초 요청 지연은 캐시 HIT 개선과 별개이며 이번 단일 3회 비교만으로 해결됐다고 판단하지 않는다.

### 실제 HTTP 경계 추가 관찰

- 같은 로컬 계측 스위치에서만 `TextureHttpTransportDiagnostics`를 연결한다. 설치된 Apache 구현의 CONNECTION_ACQUIRE는 풀 객체 대여 시간이고, 실제 DNS/TCP/TLS 연결 전체 시간이 아니다.
- 기본 연결 관리자 connect/upgrade, 본문 없는 GET의 기본 송신·flush와 그 뒤 응답 헤더 수신을 각각 숫자로 관찰한다. 직접 HTTPS의 connect에는 DNS·TCP·TLS가 함께 포함되며 개별 TLS 시간으로 오해하지 않는다. 헤더 수신 구간도 네트워크/파싱이 포함돼 순수 S3 시간과 다르다. 기존 S3 READ는 전체 이미지 읽기 구간으로 유지한다.
- SDK 공개 훅이 없어 현재 기본 SDK/Apache 구조의 한정된 내부 필드를 시작 시 연결하는 로컬 진단 전용 코드다. 지원 구조가 달라지면 시작 시 거절하고 계측 인수를 끄도록 알린다. 원래 TLS 공장·신뢰/이름 검증·연결 풀·프록시·시간 제한·재시도는 그대로 위임한다. 운영에서는 설치하지 않으며 진단 후 제거할 수 있는 관찰 코드와 계속 유지할 캐시 기능을 구분한다.
- 실제 요청 URL·헤더·사진·원문 예외·패킷/JFR을 수집하지 않는다. 루프백 HTTP/HTTPS 및 기존 관련 테스트 검증과 실제 AWS의 새 구간 실측은 구분한다.
