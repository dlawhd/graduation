# Memory Jar 부하 시험 사전 준비 — 2026-10-17

## 1. 목표

장기적으로 일반 서비스 사용자 500명을 목표로 서비스의 정확성과 처리 여력을 검증한다.
이번 측정은 10 → 50 → 100 → 200 → 300 VU로 단계적으로 올려 수정 전 성능 기준값을 확보하는 것이 목표다.
VU는 시나리오를 반복하는 가상 사용자이며 실제 가입자 수나 초당 요청 수와 같지 않다.
300 VU를 통과해도 곧바로 실제 사용자 500명 수용을 입증하는 것은 아니다.
이전 성능 결과를 기억이나 추정으로 만들지 않고, 재현 가능한 현재 상태를 기준으로 새로 측정한다.

측정 시 API별 결과·원본 파일·시나리오·요청 비율·시험 계정 수·자원 조건을 함께 보존한다.
추후 전후 비교는 같은 조건으로 반복 실행하여 판단한다.

## 3. 비용과 시험 범위

| 구분 | 실제 실행 | 대역 또는 제외 |
| --- | --- | --- |
| 외부 서비스 모의 시험 | 백엔드 로직·시험 DB·작업 큐·이미지 처리 | Cloudflare·Rekognition·SES 및 이 흐름의 S3는 대역 |
| 일반 서비스 시험 | API·DB·WebSocket·권한·동시성 | 유료 외부 경로 제외, 시험 계정·데이터 사용 |
| 별도 실제 S3 시험 | 승인한 파일의 PUT·HEAD·GET | AI 생성·이미지 심사·메일 발송 제외 |

실제 AI·Rekognition·SES 연동 시험은 진행하지 않는다.
실제 S3 시험도 아직 실행하지 않았고, 파일 크기·요청 수·보관 기간·비용 한도 확정 후 별도 승인한다.
일반 부하에서 회원가입·메일 발송·실제 이미지 업로드·실제 저금통 삭제·대량 초대 알림을 섞지 않는다.

## 4. 합의한 성능 기준

| 항목 | 기준 |
| --- | --- |
| 일반 API 응답 시간 | API별 p95 500ms 이하 |
| 오류율 | 1% 미만 |
| EC2 CPU | 지속 70% 이하 |
| JVM Heap | 지속 최대 Heap의 75% 이하 |
| Hikari 연결 풀 | 활성/최대 연결 70% 경고, 80% 초과 감시·중단 기준 설계 |
| WebSocket | 의도하지 않은 비정상 종료 없음 |
| 컨테이너 | 예상치 못한 재시작·OOM 없음 |

지속 시간·평가 구간·자동 중단 동작을 구현하고 검증한 뒤 실행한다.
의도적으로 주입한 장애는 일반 오류와 구분한다.
지표 수집 실패·미측정을 정상이나 0%로 처리하지 않는다.
최소 5초 간격 수집을 준비하되 급격한 OOM을 완전히 예방할 수는 없다.

추가 기록 후보: 요청당 DB 쿼리 수, req/s, 연결·잠금 대기, WebSocket 전달 p95,
중복·변경 유실 등 데이터 정합성, 부하 종료 후 자원 회복.
이 항목들의 전체 수집 기능이 구현됐다는 뜻은 아니다.

## 5. 오늘 실행·확인한 작업

| 작업 | 결과 | 한계 |
| --- | --- | --- |
| 선택한 로컬 기능 검사 | 8개 클래스·48개 검사 통과 | 전체 API 검증 아님 |
| AI 서비스 통합 | 임시 MariaDB·실제 실행기 연결, 중복 접수·큐 포화·거절·복구 검사 3개 통과 | 시험에서 worker 1개·대기 1개 사용, 운영 설정 부하 검증 아님 |
| HTTP·이메일 인증 | 실제 쿠키·CSRF·가입·로그인·갱신·로그아웃, 인증 오류·만료·재발송·사용 완료·SES 장애 검사 | SES는 대역, 실제 메일 도착·OAuth 로그인은 제외 |
| WebSocket | 실제 STOMP 채팅·DB 저장·REST 방송·재접속·재전송 멱등성·비멤버 차단 | 강제 장애 후 프론트 자동 재연결·모든 이벤트 검증 아님 |
| 외부 TCP 차단 | Docker internal 네트워크, 기본 외부 경로 부재 및 공용 IPv4/IPv6·메타데이터 연결 실패 확인 | 해당 시험 컨테이너 범위. 운영 EC2나 호스트 방화벽·DNS 차단 확인 아님 |
| 최신 DB 백업 | appdb 논리 백업 생성, 압축·완료 표시·체크섬 검증 후 PC로 복사 | 서버 전체 복구·자동 정기 백업 아님 |
| 백업 복원 | 외부 네트워크 없는 임시 MariaDB에 복원, 25개 테이블·V52·실패 마이그레이션 0개 확인 | S3 파일·계정 권한·서버 설정 제외 |
| 데이터 읽기 확인 | 복원된 모든 테이블 읽기 성공, 합산 2,996행 | 운영 원본과 같은 시점의 행별 대조·모든 참조 무결성 검증 아님 |
| Heap·Hikari 계측 | 단위 검사 8개, 관리 포트 보안 포함 E2E 4개 및 배포 빌드 통과 | 운영 배포 후 수집은 별도 확인 필요 |

위 실행 수는 서로 다른 시점·범위의 결과이며 합산해서 전체 테스트 수나 전체 완료율로 쓰지 않는다.
커밋 전 전체 백엔드 회귀 검사와 bootJar 빌드도 성공했다.
139개 클래스에서 1,843개 테스트를 발견했으며 1,839개 통과·4개 건너뛰기·실패 및 오류 0개였다.
건너뛴 4개 E2E는 일반 호스트 실행에서 의도적으로 제외되며, 별도 격리 Docker 실행에서 4개 모두 통과했다.
실제 사용자 데이터·인증정보는 채팅이나 저장소에 기록하지 않았으며 임시 복원 DB는 정리했다.
백업 원본과 안전하게 복사한 파일은 프로젝트 밖에 보관한다.

## 6. 현재 운영 서버에서 확인한 사실

| 항목 | 확인 내용 |
| --- | --- |
| 사용 상황 | 배포 서비스는 실제 두 명이 사용 중. 별도 비운영 EC2는 확인되지 않음 |
| EC2 | t3.micro, OS에 보이는 메모리 약 914MiB |
| 자원 공유 | Spring·MariaDB·BuildKit이 같은 서버에서 실행 |
| 메모리 | 앞선 단발 조회에서 가용 약 231MiB |
| Swap | 약 512MiB 점유. 관찰한 짧은 구간에서 지속적 swap-out은 없었음 |
| CPU | 점검 시점 컨테이너 사용률 낮음. 부하 수용 능력을 의미하지 않음 |
| 디스크 | 약 5GiB 여유, 사용률 68% |
| OOM·재시작 | 조회 컨테이너 RestartCount 0·OOMKilled=false, 보관된 최근 7일 커널 로그에서 OOM 문구 미검출 |
| DB | MariaDB 10.11.19, appdb 25개 InnoDB 테이블, 추정 크기 2.34MiB |
| DB 설정 | buffer pool 128MiB, max_connections 151 |
| DB 연결 | 관찰 시 현재·기동 후 최대 11개, 한도 초과 연결 오류 0 |
| 영구 저장 | Docker named volume 사용. 영구 볼륨은 백업과 다름 |
| 스냅샷 | 서울 리전 내 소유 EBS 스냅샷 목록에 없음. 다른 리전·별도 서비스 전체를 조사한 것은 아님 |
| 기존 계측 | health 경로 404, jcmd·jstat 없음 |

Docker 메모리 사용량은 Heap 사용량과 다르고, MariaDB 전체 연결 수는 Hikari 활성 연결 수와 다르다.
확인한 실행 인자·환경변수·JAR 설정에서 명시적 Heap 옵션·대상 Hikari 설정은 검출되지 않았다.
외부 설정 관련 환경변수·실행 인자는 미검출, 애플리케이션 마운트 0개를 확인했다.
이를 근거로 실제 Heap 최대량이나 Hikari 상한을 추측해 확정하지 않는다.

## 7. 최소 계측 구현

| 항목 | 구현 |
| --- | --- |
| API | /actuator/resources |
| 접근 | 컨테이너 내부 127.0.0.1:9091, GET만 허용 |
| Heap | 실제 사용량·최대량·사용률 |
| Hikari | 실제 최대 연결·활성·유휴·전체·연결 대기 요청 수 |
| 방식 | MemoryMXBean·HikariPoolMXBean 조회, DB 쿼리·새 연결 없음 |
| 미측정 | measurable=false 또는 null로 구분 |
| 보안 | 일반 API 포트·비-loopback 인터페이스·민감 경로·쓰기 차단 검증 |
| 서버 조회 | SSH 접속 후 호스트 nsenter·curl 사용. 포트 공개 불필요 |
| 변경하지 않은 것 | 서비스 비즈니스 로직·Heap 크기·DB 풀 크기·AI 실행량 |

Actuator와 별도 관리 서버의 메모리·시작 시간 부담은 있으므로 운영 배포 후 확인한다.
현재 단발 조회 스크립트까지 준비됐고, 주기적 기록·자동 중단은 아직 준비 중이다.
상세 실행 방법은 [RESOURCE_MONITORING.md](RESOURCE_MONITORING.md)를 따른다.

## 8. 남은 순서

| 순서 | 작업 | 완료 조건 |
| --- | --- | --- |
| 1 | 시험·계측 코드 커밋·푸시 | 비밀값·백업·빌드 산출물을 제외하고 변경 검증 |
| 2 | CI·자동 배포 확인 | 테스트·이미지 빌드·배포 성공, 새 digest·기동·접근 보호 확인 |
| 3 | 운영 지표 확인 | EC2에서 실제 Heap·Hikari 조회, 계측 추가 후 메모리 여유 확인 |
| 4 | 부하 시나리오·모니터링·중단 장치 | 시험 계정·데이터, 유료 경로 제외, CPU·Heap·풀·오류·OOM·수집 실패 감시 |
| 5 | 10 VU 사전 검증 | 점검 시간에 작은 부하로 지표·중단 경로 확인 |
| 6 | 일반 조회 부하 | 10 → 50 → 100 → 200 → 300 VU. 실패 시 중단·다음 단계 보류 |
| 7 | 쓰기·WebSocket 부하 | 조회와 분리해 저장·전달·권한·재연결 측정 |
| 8 | 모의 큐·지속 부하·회복 | 운영에 맞춘 조건에서 포화·복구와 자원 누적 확인 |
| 9 | 별도 실제 S3 | 비용 한도·요청 수·파일 크기 승인 후 진행 |
| 10 | 문제 수정·동일 조건 재측정 | 기준값과 원본 결과를 보존하고 실제 개선량 계산 |

main 푸시는 자동 배포를 유발한다. 푸시 성공과 CI·배포 성공은 별개다.
현재 운영 서버를 사용하는 측정은 두 사용자가 이용하지 않는 점검 시간에 진행하고,
지연·중단 가능성을 사전에 인정한다. 계측 배포 허락과 부하 실행 허락은 구분한다.

## 9. 아직 주장할 수 없는 성과

- 300 VU 또는 500명 처리 검증 완료
- 응답 시간 몇 % 감소, 처리량 몇 배 증가
- 모든 기능·모든 API·모든 동시성 문제 검증 완료
- 자동 중단·장기 자원 회복·정기 백업 구축 완료

현재 성과는 외부 비용 경계를 분리한 로컬 시험 기반, 실제 백업 복원 확인,
비공개 Heap·Hikari 계측 구현 및 해당 범위의 검증이다.
