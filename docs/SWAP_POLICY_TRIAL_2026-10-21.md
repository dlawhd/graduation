# 스왑 정책 한 가지를 바꾼 비교 실험

작성일: **2026년 10월 21일**, 한국 시간 기준. 실제 시험은 15:30~15:36경이었다.

## 결론

**`swappiness`(메모리 회수 때 스왑의 상대 비용을 판단하는 설정)를 60→10으로 낮추는 것만으로 로그인 지연이 해결됐다는 근거는 얻지 못했다.** 시험 값은 원래 **60으로 원복**했고, 서버에서 값 60과 자동 원복 타이머 비활성을 확인했다. 영구 설정으로 채택하지 않았다.

원래 값 60에서도 이번 소량 로그인은 빨랐다. 임시 값 10의 로그인도 성공했지만 더 빠르지 않았고, 후속 관찰에서는 Heap(자바 객체용 메모리)이 경고 기준을 넘었다. 안전 조건에 따라 예정한 마지막 A 인증과 상위 부하는 하지 않았다.

이것은 10이 항상 나쁘다는 증명도, 60이 최적이라는 증명도 아니다. 현재 자료로 단순 정책 변경을 해결책이라고 주장하지 않겠다는 결론이다.

## 1. 목적과 고정한 조건

로그인 지연에 메모리의 디스크 재접근이 관측됐으므로, 여러 설정을 한꺼번에 바꾸지 않고 정책 한 값만 시험했다.

| 항목 | 조건 |
| --- | --- |
| 비교 계획 | A: 60 → B: 10 → A: 60 |
| 전용 계정 | 각 조건 같은 3계정, 순차 실행. 조건 내 실패 시 추가 요청 중단 |
| 요청 제한 | 로그인·보안 토큰·로그아웃 모두 기존 5초 |
| 인증 흐름 | 보안 토큰 확인 → 로그인 → 보안 토큰 재확인 → 로그아웃 |
| 서버·DB | 같은 이미지·기동 상태 유지, 재시작하지 않음 |
| JVM | `-Xmx224m -XX:+UseG1GC -XX:MaxGCPauseMillis=200` 유지 |
| DB 캐시·연결 상한 | 기존 값 유지, 최대 연결 10개 |
| 비용 경로 | 실제 AI·이미지 심사·메일·S3 전송 없음. 인프라 증설 없음 |
| 강제 조치 | 강제 GC·스왑 해제·캐시 삭제·메모리 미리 읽기 없음 |

각 인증 프로브(소량 요청으로 동작을 살펴보는 도구)는 먼저 15초 자원 수집을 하고, 계정 사이 10초와 마지막 20초를 관찰했다. 최초 A와 B의 시작 사이에는 도구 검증 시간이 있어 동일 길이의 장기 유휴 조건을 맞춘 시험이 아니다. 메모리 캐시·자연 GC 상태까지 동일하게 고정할 수는 없었으므로 엄밀한 개선율을 계산하지 않는다.

## 2. 안전 절차

1. 배포·컨테이너 식별값·메모리 옵션·전용 세션을 확인했다.
2. 최신 DB 백업을 생성해 PC 사본과 해시(파일 일치 확인값)를 검증했다.
3. 자동 원복 도구를 실제 설정 변경 없는 대역으로 검사했다.
4. 서버에 **12분 후 자동 원복 타이머**를 예약하고 활성 상태를 확인한 뒤 10을 적용했다.
5. B 성공·실패와 관계없이 `finally`에서 즉시 60으로 되돌리도록 했다.
6. 원복 확인 후 자신이 만든 타이머만 중지했다. 서버의 다른 서비스는 중지하지 않았다.

자동 원복은 현재 값이 우리가 쓴 10일 때만 60으로 바꾼다. 다른 관리자가 20 등 다른 값으로 변경했다면 덮어쓰지 않는다. `/etc/sysctl.d` 같은 영구 설정 파일을 만들지 않았다. 실제 통신 단절로 12분 타이머가 발화하는 상황까지 실서버에서 재현한 것은 아니며, 원복 코드는 대역 검사·실제 수동 원복·실제 타이머 활성 확인으로 검증했다.

## 3. 인증 결과

| 조건 | 계정 1 로그인 | 계정 2 로그인 | 계정 3 로그인 | 인증 12단계 | 전체 프로브 판정 |
| --- | ---: | ---: | ---: | --- | --- |
| A: 기존 60 | 370.57ms | 153.25ms | 229.42ms | 모두 성공 | 완료 |
| B: 임시 10 | 857.54ms | 528.20ms | 247.76ms | 모두 성공 | **후속 자원 경고로 중단** |
| A: 원복 후 | — | — | — | 미실행 | B 중단으로 생략 |

실패 뒤 늦게 완료된 로그인 세션을 정리하는 기존 절차도 유지했다. 이번 A·B에서는 추가 강제 무효화 없이 모두 로그아웃했고, 최종 전용 10계정 집계의 활성 세션은 0개였다.

이전의 약 5.36초 로그인과 이번 B만 비교해 개선율을 계산하면 안 된다. 이번 A에서도 이미 1초 미만으로 끝났기 때문이다. 같은 값 60에서도 응답이 변한다는 사실은 메모리 상주 상태·GC·디스크 접근 등 실행 당시 조건이 중요하다는 근거다.

## 4. 자원 관측과 비교 한계

| 관측값 | A: 60 | B: 10 |
| --- | ---: | ---: |
| 정상 표본 | 13개 | 13개 |
| Heap 처음 → 마지막 | 164.50 → 112.90MiB | 115.90 → 180.90MiB |
| Heap 최고 | 73.89% | **80.76%** |
| JVM 전체 GC 증가 | 2회·703ms | **0회·0ms** |
| 가용 RAM 최소 | 132.90MiB | 168.54MiB |
| 스왑 읽기 최고 | 7.697MiB/초 | 4.494MiB/초 |
| 스왑 쓰기 최고 | 1.031MiB/초 | 0.066MiB/초 |
| 디스크 대기 최고 | 20.46% | 5.32% |

스왑 이동·디스크 대기의 최고값은 B에서 작았지만, 이 짧은 자료만으로 정책 효과라고 확정하지 않는다. A에서는 GC(필요 없는 자바 객체 메모리 정리)가 있었고 B에서는 없었다. 각 구간의 최고값도 정확히 같은 처리 단계가 아니므로 직접적인 개선율로 쓸 수 없다. 마지막 A를 실행하지 못해 완전한 A-B-A 비교도 아니다.

B에서는 세 로그인 후 Heap이 약 **65MiB 증가**했다. 코드의 Argon2(비밀번호를 안전하게 검증하는 계산)는 한 번에 약 19MiB의 작업 메모리를 사용하는 설정이다. 로그인마다 약 20MiB 안팎 증가한 표본은 이런 임시 할당과 일치하지만, GC 후 모두 회수되는지는 이번 B에서 검증하지 않았다. 높아진 Heap을 곧바로 누수라고 하거나, 정책 10이 누수를 만들었다고 단정하지 않는다.

스왑 정책은 자바의 객체 정리 시점을 직접 바꾸는 설정이 아니다. 이를 낮췄다고 이미 디스크에 있던 Java 메모리를 모두 RAM으로 복귀시키는 작업을 한 것도 아니다.

### 정확히 어떤 중단 조건이었나?

기존 `tools/load/auth-flow-probe.py`는 소량 인증 진단용으로 **자원 경고를 받으면 즉시 추가 요청을 중단**한다. B에서는 세 계정 로그아웃 뒤인 **15:35:47경 Heap 약 80.31%** 표본에서 이 경고 경로로 중단됐다. 일반 부하 감시기의 “75% 초과가 30초 지속하면 중단”보다 엄격한 기존 진단 규칙이다. 이번에 규칙을 바꾼 것은 아니며, 30초 연속 초과로 일반 부하 도구가 종료됐다고 표현하지 않는다.

그 뒤 30초 안전 대기를 하며 세션을 확인했고, 추가 인증 요청 없이 15:36:19경 60으로 원복했다. 후속 확인의 Heap 약 81.20%는 여전히 주의 상태이므로 자원 안정화 전체 통과로 기록하지 않았다.
