# Memory Jar — 50명 시험 재정비부터 Oracle 서버 생성 재시도까지

작성일: **2026년 10월 22일, 한국 시간**

정리 범위: 아래 요청을 한 시점부터, 마지막 Oracle 서버 생성 실패 로그까지.

> 배포는 완료됐어. 계정 준비와 실제 조회 시험을 분리하는 절차 정비.
> 준비 중 시간 초과를 숨기지 않고 별도로 기록하기.
> 준비·자원 조건을 통과하면 50 VU 재측정.
> 응답·오류·종료 후 회복까지 통과하면 100 → 150 → 200 → 300 VU.

이 문서는 **진행 기록**이다. 지금 새 부하 시험이나 서버 이전을 실행했다는 뜻이 아니다. 당시 대화·화면·로그를 현재 로컬의 관련 코드·결과 파일과 대조했다. 비밀번호, 개인 키, 토큰, 실제 계정 이메일, 서버 접속 주소는 넣지 않았다.

시간이 없으면 **1장 결론 → 3장 시험 결과 → 11장 저장·생성 결과 → 13장 다음 행동** 순서로 먼저 읽으면 된다.

## 1. 결론부터: 어디까지 끝났을까?

**시험 기록 방식은 고쳤다. 하지만 50명 동시 조회는 시작하지 못했고, 더 큰 무료 서버로 옮기는 작업도 아직 끝나지 않았다.**

| 작업 | 마지막으로 확인한 상태 |
| --- | --- |
| 계정 준비·조회·정리 결과를 따로 기록 | 완료 |
| 50 VU(동시에 요청을 반복하는 가상 사용자 50명) 재시험 | 첫 로그인 준비에서 시간 초과. 실제 동시 조회는 미시작 |
| 100·150·200·300 VU 시험 | 이 범위에서는 모두 미실행 |
| 느린 로그인 원인 조사 | 메모리를 디스크에서 다시 읽는 대기가 유력한 원인임을 뒷받침하는 자료 확보 |
| 스왑 정책 비교 실험 | 개선 효과를 입증하지 못함. 원래 값으로 복구 |
| 서버 메모리 예산 검토 | 여유를 포함한 약 1.4GiB 계획 제안. 증설은 하지 않음 |
| Oracle 무료 계정 가입 | 오사카를 홈 리전으로 가입 완료 |
| Oracle 네트워크 준비 | 가상 네트워크·공용 서브넷·인터넷 출입구 생성 확인, 경로·접속 규칙 설정 진행 |
| Oracle 서버 설정 저장 | `memoryjar-server` 스택으로 저장 완료 |
| Plan(서버를 만들기 전 생성 예정 내용을 확인하는 검사) | 성공. 서버 1대 추가, 기존 자원 변경·삭제 없음 |
| Apply(저장한 설정대로 실제 서버 생성을 실행하는 작업) | **A1 서버 여유 용량 부족으로 실패** |
| Oracle로 서비스·DB(서비스 데이터를 보관하는 저장소) 이전 | 미실행 |

**현재 방향은 기존 AWS 서비스를 유지하고, Oracle 설정은 저장해 두는 것이다.** Oracle 계정 가입이나 Plan 성공을 서버 확보 완료로 기록하지 않는다.

## 2. 처음 하려던 일: 시험 준비와 실제 시험을 구분하기

운동 대회에 비유하면 쉽다.

- **준비:** 참가자 확인, 출입증 발급, 경기장 입장 가능 여부 확인.
- **본시험:** 참가자들이 실제로 동시에 경기하기.
- **정리·회복:** 참가자 퇴장, 사용한 물건 정리, 경기장이 정상 상태로 돌아왔는지 확인.

우리 서비스에서도 먼저 시험 계정으로 로그인하고, 본인 정보와 접근 가능한 저금통이 맞는지 확인해야 한다. 이 준비가 실패하면 본시험을 시작하면 안 된다.

### 정비한 내용

1. 준비 요청에 `CSRF`(요청 위조를 막기 위한 보안 토큰 확인), `LOGIN`(로그인), `ME`(내 정보 확인), `JAR_LIST`(저금통 목록 확인)라는 단계 이름을 붙였다.
2. 준비를 끝낸 계정 수와 준비 성공·실패 표시를 따로 남겼다.
3. 준비·조회·정리·세션 정리·종료 후 회복을 각각 결과 파일로 남겼다.
4. 조회가 0건이면 **성공이 아니라 `NOT_STARTED`(시작하지 않음)**로 표시했다.
5. 직전 인원 단계와 종료 후 회복을 모두 통과해야 다음 인원 단계로 올라가게 했다.

**로그인과 조회를 서로 다른 프로그램으로 완전히 분리한 것은 아니다.** 같은 k6(서버에 시험 요청을 보내는 도구) 실행 안에서 준비 → 조회 → 정리 순서로 처리하되, 기록과 판정을 분리한 것이다.

### 시험 기준

- 예정 순서: **50 → 100 → 150 → 200 → 300 VU**.
- 각 단계의 예정 조회 시간: 60초.
- 당시 승인된 임시 목표: 각 API(프로그램끼리 요청하는 통로)의 **p95 ≤ 5초**. p95는 응답 100개를 빠른 순서로 놓았을 때 약 95번째 응답까지 끝나는 시간이다.
- 개별 요청 제한 시간: 5초.
- 조회 오류율: 1% 미만.
- 시험 계정은 사용자마다 따로 사용한다. 한 계정을 여러 가상 사용자가 공유하지 않는다.
- 기존 자원 감시·중단·회복 기준을 느슨하게 바꾸지 않는다.
- 과거 500ms·2초 기준의 실패 기록을 새 기준으로 소급해서 합격 처리하지 않는다.

목표를 5초로 정한 것 자체가 성능 개선은 아니다. 시험 기준을 정한 일과 실제 응답이 빨라진 일은 구분한다.

## 3. 실제 50 VU 재시험 결과

### 먼저 서버 접속과 배포 상태를 확인했다

처음에는 SSH(서버에 원격으로 접속하는 통로)가 시간 초과했다. 사용자가 AWS 보안 그룹에 접속 주소를 추가한 뒤 **기존 서버 주소로 접속에 성공**했다. 서버 주소 변경이 원인이었다고 결론 내리지 않았다.

그 후 당시 운영 배포가 커밋 `84d5301`과 일치하는지, 서버·DB가 불필요하게 재시작되지 않았는지, 자원 감시가 동작하는지 확인했다. 시작 전 자원 검사와 DB 백업·PC 사본의 일치 확인을 거쳐 시험을 진행했다.

### 2026년 10월 21일 15:09경의 결과

| 항목 | 실제 결과 |
| --- | --- |
| 첫 보안 토큰 요청 | 성공, 약 53.88ms |
| 첫 계정 로그인 | **약 5,010.78ms 후 시간 초과** |
| 준비 완료 계정 | 0개 |
| 동시 조회 완료 요청 | **0건** |
| 조회 판정 | **미시작** |
| 상위 인원 단계 | 모두 미실행 |
| 늦게 생성된 시험 세션 정리 | 1개 무효화, 확인한 50개 시험 계정의 남은 활성 갱신 세션 0개 |
| 종료 후 회복 관찰 | 약 60.7초·11개 표본에서 기존 회복 조건 통과 |

여기서 세션은 로그인 상태를 유지하기 위한 서버 측 기록이다. 시험용 갱신 세션을 정리했으며, 실제 사용자 두 명의 세션은 건드리지 않았다. 이미 발급된 모든 인증 정보를 즉시 없앴다는 뜻도 아니다.

**이 결과는 “50명이 동시에 조회하자 서버가 실패했다”가 아니다. “50명 시험을 준비하다 첫 로그인에서 멈췄다”가 정확하다.**

조회가 없으므로 이번 자료에서 조회 p95나 정상적인 조회 오류율을 계산해 합격·불합격을 주장할 수 없다. 종료 후 회복 관찰의 통과도 준비 실패를 성공으로 바꾸지는 않는다.

### 서버에는 성공인데, 사용자는 실패할 수 있다

같은 로그인은 서버 내부 기록에서 약 **5,359.41ms 후 HTTP 200(요청 처리 성공 상태)**으로 끝났다. 하지만 시험 프로그램은 약 5초에 기다리기를 포기했다.

식당에 비유하면, 손님이 5분을 기다리다 나간 다음 음식이 완성된 상황이다. 음식이 완성됐다고 이미 떠난 손님에게 제때 제공한 것은 아니다.

따라서 **서버 로그의 200을 근거로 사용자의 시간 초과를 성공 처리하지 않았다.**

## 4. 왜 로그인이 느렸는지 조사했다

RAM(프로그램이 작업 중인 자료를 빠르게 꺼내 쓰는 메모리)은 책상, 디스크는 서랍에 비유할 수 있다. 책상이 좁으면 자료를 서랍에 넣었다가 다시 꺼내느라 시간이 든다.

스왑은 운영체제가 메모리 일부를 디스크에 옮겨 보관하는 공간이다. 스왑에 자료가 있다는 사실만으로 장애라고 할 수는 없지만, 자주 필요한 자료를 다시 읽으면 지연이 커질 수 있다.

### 실제 근거

- 해당 느린 로그인 동안 GC(필요 없는 자바 객체를 정리하는 작업)는 **0회·0ms**였다. 이 요청의 5.36초를 GC 시간으로 설명할 수 없다.
- 로그인 시작과 겹친 약 5초 관측 구간에서 Java의 **Major page fault(필요한 메모리를 가져오려면 디스크 읽기가 필요한 상황)**가 **3,617회 증가**했다.
- 같은 구간에서 Java의 RAM 점유는 약 **14.9MiB 증가**, 스왑 점유는 약 **12.6MiB 감소**했다. MiB는 메모리 크기를 나타내는 단위다.
- 당시 조사에서 DB 행 잠금 대기·교착 기록은 0건이었다. DB 잠금이 해당 지연을 만들었다는 근거는 얻지 못했다.
- Nginx(외부 요청을 백엔드로 전달하는 앞단 프로그램)의 서버 응답 대기도 약 5초였다. 사용자 PC와 서버 사이의 인터넷 속도만으로 설명하기 어려웠다.

**가장 유력하게 좁힌 원인은 Java가 필요한 메모리를 디스크에서 다시 읽는 대기다.** 로그인 메서드 하나만의 계산 문제보다는 서버 전체 메모리·디스크 상황이 여러 처리 구간에 영향을 준다는 판단이었다.

다만 다음 한계는 남는다.

1. 약 5.36초 전부를 메모리 대기 하나로 정확하게 나눠 증명한 것은 아니다.
2. 계측한 바깥 처리 구간 합계는 약 2.98초이고, 약 2.37초는 해당 계측 밖에 있었다.
3. 비밀번호 검사 시간은 인증 처리 전체 안에 포함된다. 이런 시간을 중복해서 더하면 안 된다.
4. “이 요청은 GC가 없었다”와 “서비스의 모든 지연은 GC와 무관하다”는 다른 말이다.

그래서 제한 시간만 늘리거나 비밀번호 보안을 낮추는 대신, 메모리 대응을 한 가지씩 비교하기로 했다.

## 5. 스왑 정책을 바꿔 봤지만, 해결책으로 채택하지 않았다

`swappiness`(메모리를 회수할 때 스왑을 상대적으로 얼마나 활용할지 판단하는 설정)를 **60 → 10**으로 잠시 바꿨다. 숫자를 낮추면 무조건 빨라지는 설정은 아니다.

계획은 A(기존 60) → B(임시 10) → A(원래 60) 비교였다. 서버·DB·자바 메모리 제한은 그대로 두고, 같은 시험 계정 3개를 순서대로 사용했다.

| 조건 | 계정 1 로그인 | 계정 2 로그인 | 계정 3 로그인 | 판단 |
| --- | ---: | ---: | ---: | --- |
| A: 기존 60 | 0.371초 | 0.153초 | 0.229초 | 인증 흐름 완료 |
| B: 임시 10 | 0.858초 | 0.528초 | 0.248초 | 인증은 완료했으나, 후속 자원 경고로 중단 |
| 마지막 A: 원복 후 | 미실행 | 미실행 | 미실행 | 안전 조건에 따라 생략 |

기존 60에서도 이미 빠른 로그인이 나왔다. 따라서 이전 5.36초와 B만 비교해서 “10으로 바꾸니 해결됐다”고 할 수 없다.

B에서는 Heap(자바 객체가 쌓이는 메모리 공간)이 약 80%까지 올라가 소량 인증 진단 도구의 경고 조건에 걸렸다. **로그인 시간 초과가 아니라 자원 경고 때문에 중단된 것**이다. 일반 부하 감시기의 지속 시간 조건과 혼동하지 않는다.

### 안전하게 원복했다

- 변경 전에 **12분 뒤 자동으로 60으로 되돌리는 타이머**를 준비했다.
- 실제로는 시험 종료 후 즉시 60으로 되돌렸고, 값 60과 타이머 비활성을 확인했다.
- 자신이 적용한 값 10일 때만 되돌리도록 해서, 다른 관리자가 바꾼 값을 덮어쓰지 않게 했다.
- 영구 설정 파일은 만들지 않았다.
- 스왑 강제 해제, 캐시 강제 삭제, 강제 GC, 서버·DB 재시작은 하지 않았다.

이 실험에서 B의 인증은 성공했지만, 자원 상태까지 포함한 전체 판정은 중단이었다. 원복 직후 Heap 주의 상태도 남아 있어 “안정화 전체 통과”로 기록하지 않았다.

**결론: 스왑 정책 10의 개선 효과는 입증되지 않았다. 원래 값 60을 유지했다.** 마지막 A를 실행하지 못했으므로 완성된 A-B-A 비교라고 부르지도 않는다.

## 6. “메모리를 정리했는데 왜 여유가 부족할까?”

이후 자연 GC 뒤에 남는 메모리와 서버 전체의 메모리 예산을 살폈다. 강제 GC를 실행한 것은 아니다.

당시 보고된 값은 다음과 같다.

- Heap 사용량: 약 **72MiB**.
- Old Gen(오래 살아남은 자바 객체가 모인 영역): 약 **68MiB**.
- Java 전체: RAM 약 **364MiB**, 스왑 약 **133MiB**.

**Heap 사용량이 72MiB라는 말은 Java 전체가 72MiB만 필요하다는 뜻이 아니다.** 자바 실행기, 클래스 정보, 스레드, 미리 확보한 공간 등도 필요하다.

앞선 B 실험에서 늘어난 Heap 약 65MiB는 Eden(새 객체가 처음 쌓이는 영역)의 증가였고, Old Gen은 그대로였다. 이후 자연 GC 뒤의 Old Gen도 약 68MiB였다. 이 증가만으로 메모리 누수라고 단정할 근거는 없었다. 반대로 모든 장기 누수 가능성을 없앴다는 뜻도 아니다.

## 7. 무료로 메모리를 늘리는 방법을 찾아봤다

### 다른 회사의 RAM만 AWS에 붙이는 방식은 아니다

일반적인 EC2 사용에서 다른 서버의 RAM을 빌려 현재 서버의 RAM처럼 추가하는 방식으로 진행할 수는 없다. 검토한 방향은 **더 큰 메모리를 제공하는 별도 서버에 서비스를 옮기거나 작업을 나누는 것**이었다.

Oracle Always Free, Google Cloud 신규 체험, AWS 신규 고객 크레딧을 비교했다. 신규 가입자용 체험·크레딧은 기간과 자격 조건이 있고, 기존 AWS 계정에 자동으로 붙는 혜택은 아니므로 상시 무료 서버와 구분했다.

당시 공식 문서에서 확인한 Oracle A1 무료 한도는 **계정 전체 합계 2 OCPU(계산 자원)·RAM 12GB에 해당하는 월 사용량**이었다. 부팅 디스크와 추가 디스크의 무료 공간 합계는 홈 리전에서 200GB였다. 오래된 “4 OCPU·24GB” 안내를 현재 계정 조건으로 그대로 사용하지 않았다. [Oracle 무료 자원 조건](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)

하지만 **무료 사용 자격과 실제 빈 서버가 있는지는 다른 문제**다. 무료 자원에는 사용량·지역 조건과 유휴 자원 회수 가능성도 있으므로, “무조건 평생 유지되는 무료 운영 서버”라고 생각하지 않았다.

### AWS의 이메일·파일 서비스는 유지할 수 있다

서버를 Oracle로 옮겨도 아래 구성을 검토할 수 있다.

- 백엔드와 MariaDB: Oracle 서버에서 실행.
- SES(인증 이메일을 발송하는 AWS 서비스), S3(사진·파일 저장 서비스), Rekognition(이미지 검사 서비스): 기존 AWS 사용 유지.
- Cloudflare AI: 기존 외부 연결 유지 검토.

다만 이것은 가능한 구성안이지, 연결 완료 보고가 아니다.

1. 기존 EC2의 IAM 역할(서버에 부여한 AWS 이용 권한)은 Oracle로 자동 이전되지 않는다. 외부 서버용 인증을 별도로 구성해야 한다. IAM Roles Anywhere(외부 서버에 임시 AWS 권한을 주는 기능)는 검토 후보였고, 실제로 구성하지 않았다. [AWS 공식 설명](https://docs.aws.amazon.com/rolesanywhere/latest/userguide/introduction.html)
2. Oracle 서버가 무료여도 AWS 이메일·파일·이미지 검사·전송 사용료가 없어지는 것은 아니다.
3. 현재 프론트엔드는 발급받은 업로드 주소로 S3에 직접 파일을 보내는 경로가 있다. 모든 파일이 Oracle 서버를 거친다고 계산하면 안 된다.
4. DB 복원, 도메인, 암호화 통신, 자동 배포도 별도 검증이 필요하다.

ARM과 amd64는 CPU 계열의 차이다. 서버 크기만 다른 것이 아니라, 실행 파일의 지원 CPU도 맞아야 한다.

## 9. Oracle 네트워크와 서버 설정

### 공용 IP가 안 켜져 네트워크를 먼저 따로 만들었다

처음 서버 생성 화면에서는 “새 공용 서브넷”을 선택했는데도 공용 IPv4(인터넷에서 접속할 서버 주소) 스위치가 켜지지 않았다. 화면에는 공용 서브넷을 선택하라는 경고가 남아 있었다.

그렇다고 사용자가 사설 서브넷을 골랐다고 단정하지 않았다. 정확한 내부 원인은 확인하지 못했다. 별도 화면에서 네트워크를 만든 뒤 **기존 네트워크·서브넷으로 선택하자 공용 IPv4가 켜지는 것을 확인**했다.

### 준비한 네트워크

| 구성 | 이름 또는 설정 | 쉬운 설명 |
| --- | --- | --- |
| VCN(서버용 가상 네트워크) | `memoryjar-vcn`, `10.0.0.0/16` | 서버들이 사용할 전체 내부 공간 |
| 공용 서브넷(전체 네트워크 안의 작은 구역) | `memoryjar-public-subnet`, `10.0.0.0/24`, Regional | 공용 IP를 가질 수 있는 서버 구역 |
| DNS(주소 이름을 IP로 찾는 기능) | VCN 이름표 `memoryjar`, 서브넷 이름표 `public` | 내부 서버 이름 사용 준비 |
| Internet Gateway(인터넷 출입구) | `memoryjar-igw` | 인터넷과 통신하는 통로 |
| 서브넷 경로표 | `0.0.0.0/0` → `memoryjar-igw` | 외부 목적지로 갈 때 사용할 출구 |
| SSH 접근 규칙 | TCP 22, 출발지는 본인 공인 IPv4의 `/32`로 제한하는 절차 | 원격 접속은 허용한 IP 하나에서만 가능하게 설정 |

VCN·공용 서브넷·Internet Gateway는 화면의 `Available`(사용 가능) 상태를 확인했다. 경로 입력값을 확인했고, SSH 출발지 제한은 사용자가 수정 완료했다고 보고했다. **수정 후 SSH 규칙 값의 재캡처 확인과 실제 서버 통신 시험은 별개로 남아 있다.**

Internet Gateway 생성 시 고급 옵션의 Route Table 연결은 비워뒀다. 실제 외부 경로는 서브넷이 쓰는 `Default Route Table for memoryjar-vcn`에 추가하는 방식으로 진행했다. 이름이 비슷해도 두 설정은 구분했다.

여기서 `/16`, `/24`는 CIDR(사용할 IP 주소 범위를 나타내는 표기)이다. `/32`는 IPv4 주소 하나를 뜻한다.

`0.0.0.0/0`을 **경로표의 목적지**로 쓰는 것과 **SSH 허용 출발지**로 쓰는 것은 다르다. 경로표에 외부 통로를 추가했다고 모든 포트를 개방한 것은 아니다. SSH를 모든 IP에 허용하지 않도록 따로 제한했다.

공인 IP가 바뀌면 SSH 허용 규칙도 갱신해야 한다. DRG·NAT·Service Gateway·Local Peering은 이번에 만들 대상으로 진행하지 않았다. 서버가 없으므로 인터넷·SSH 연결 전체가 동작한다고 주장하지 않는다.

| 부팅 디스크(운영체제와 기본 파일을 담는 저장장치) | 사용자 지정 크기·성능 OFF, 화면 기본값 약 46.6GB |
| 추가 디스크 | 없음 |
| 디스크 전송 암호화 | ON |
| 암호화 키 | Oracle 기본 관리 키 |
| Cloud Guard Workload Protection(추가 보안 감시 기능) | **Disabled** |

부팅 디스크의 “46.6GB”는 당시 화면 표시값이다. 공식 안내에는 기본 크기 47GB·50GB 등 서로 다른 표기도 있어, 별도로 크기를 변경했다고 기록하지 않는다. 마지막 Plan에서도 디스크 크기는 적용 후 확인하는 값이었다.

추가 보안 감시 기능은 지금 사용하지 않을 기능이라 껐다. **이 기능이 켜졌다는 사실만으로 이미 과금됐다고 판단하지 않았다.** 무료·유료 구성이 별도로 존재한다. [Oracle Instance Security 설명](https://docs.oracle.com/en-us/iaas/Content/cloud-guard/using/cgis.htm)

### SSH 키는 무엇을 확인했나?

키 쌍 생성과 개인 키·공개 키 다운로드를 안내했고, 최종 Plan에 **SSH 공개 키가 등록된 것**은 확인했다.

다만 **개인 키 파일이 PC에 실제로 보관돼 있고 그 공개 키와 정확히 짝을 이루는지까지 직접 검사한 것은 아니다.** 생성 화면을 새로 열면 다른 키 쌍일 수 있으므로 이전 파일과 혼동하지 않아야 한다.

- 개인 키: 본인이 보관할 비밀 열쇠. 채팅·프로젝트·GitHub에 올리지 않는다.
- 공개 키: 서버에 등록할 자물쇠 정보. 재사용하려면 그 공개 키와 짝인 개인 키가 있어야 한다.
- 공개 키 업로드 화면에 개인 키를 올리지 않는다.

## 10. 실제 서버 생성은 왜 실패했나?

처음 일반 생성 화면에서 다음 오류가 나왔고, 재시도에서도 같은 종류의 오류가 나왔다.

```text
Out of capacity for shape VM.Standard.A1.Flex in availability domain AD-1.
```

뜻은 **“오사카 AD-1에서 요청한 A1 서버를 배정할 여유가 없다”**이다. 오류가 나온 시점의 요청을 배정하지 못했다는 의미이지, 언제까지 용량이 없을지 알려 주는 결과는 아니다.

Oracle은 이 경우 다른 AD(리전 안의 별도 서버 배치 구역)를 쓰거나 시간을 두고 재시도하라고 안내한다. 하지만 오사카는 AD가 하나이고, Fault domain(AD 안의 장애 분리 구역)도 이미 자동 선택이었다. 안내 문구에 따라 추가로 바꿀 배치 값이 없었다. [Oracle 지역 정보](https://docs.oracle.com/en-us/iaas/Content/General/Concepts/regions.htm), [용량 부족 FAQ](https://www.oracle.com/cloud/free/faq/)

**이 오류는 카드 오타나 로그인 지연 문제와 별개의 문제다.** 당시의 직접적인 생성 실패 원인은 Oracle 호스트 용량 부족이었다.

## 11. 매번 다시 입력하지 않도록 설정을 저장했다

### 저장 과정

1. 서버 생성 화면에서 **Save as stack(생성 설정 저장)** 선택.
2. 스택 이름은 `memoryjar-server`, Terraform(서버 설정을 코드로 관리하는 도구) 버전은 화면 기본값 `1.5.x` 유지.
3. 추가 변수·태그·사용자 지정 제공자는 넣지 않음.
4. **Run apply 체크 해제** 후 저장. 저장과 동시에 서버 생성을 실행하지 않음.
5. 스택의 **Active** 상태 확인.

스택은 서버의 조립 설명서에 가깝다. **설명서를 보관했다고 서버가 생기는 것은 아니다.** [설정 저장 공식 안내](https://docs.oracle.com/en-us/iaas/Content/ResourceManager/Tasks/create-stack-resource.htm)

### Plan은 성공했다

작업 이름: `plan-job-20261022003227`.

처음 `Accepted` 상태는 Plan 작업 접수·실행 대기였다. A1 자리를 기다리는 예약 대기열이 아니었다. 이후 **Succeeded** 상태가 됐고, 결과는 다음과 같았다.

```text
Plan: 1 to add, 0 to change, 0 to destroy.
```

의미는 **서버 자원 1개 생성 예정, 기존 자원 변경 0개, 삭제 0개**다. 기본 부팅 디스크 같은 부속 항목을 모두 별도 자원 수로 표시한다는 뜻은 아니다.

Plan에서 2 OCPU·12GB, 공용 IPv4 ON, IPv6 OFF, 기존 서브넷 지정, SSH 공개 키 등록, Cloud Guard OFF를 확인했다. 기존 네트워크를 새로 만드는 계획은 아니었다.

중간에 실행 도구의 잠금 파일 정보 경고가 있었지만 Plan은 완료됐다. 그 경고를 서버가 만들어졌다는 뜻이나 ARM 실행 검증 결과로 해석하지 않는다.

### Apply는 용량 부족으로 실패했다

작업 이름: `apply-job-20261022004233`.

최종 상태는 **Failed**였고 핵심 로그는 다음과 같다.

```text
oci_core_instance.generated_oci_core_instance: Creating...
Error: 500-InternalError, Out of host capacity.
```

도구 초기화 후 Oracle의 실제 서버 생성 요청까지 진행했지만, 서버 배정 단계에서 거절됐다. `main.tf line 3`은 실패가 보고된 자원 설정의 위치이지, 그 줄의 문법 오류를 뜻하지 않는다.

마지막 오류 시각은 로그의 **2026-10-21 15:42:57 UTC**다. UTC(세계 표준 시각)에 9시간을 더하면 **2026-10-22 00:42:57 한국 시간**이다. 이것은 과거 실행 기록이며 문서를 읽는 순간의 재고를 조회한 값이 아니다.

### 세 단계를 혼동하지 않기

| 표시 | 정확한 의미 | 아직 보장하지 않는 것 |
| --- | --- | --- |
| Stack Active | 설정 묶음 저장 완료 | 서버 생성·실행 |
| Plan Succeeded | 생성 예정 내용 검사 완료 | A1 자리 확보 |
| Apply Succeeded | 실제 적용 작업 완료 | 로그인·DB·서비스 정상 동작 전체 |

실제 적용이 성공하더라도 인스턴스 실행 상태와 SSH 접속, 애플리케이션 동작을 별도로 확인해야 한다. [Plan 안내](https://docs.oracle.com/en-us/iaas/Content/ResourceManager/Tasks/create-job-plan.htm), [Apply 안내](https://docs.oracle.com/en-us/iaas/Content/ResourceManager/Tasks/create-job-apply.htm)

## 12. 그럼 빈자리가 생기는 것을 어떻게 알까?

대화에서 확인한 방법과 아직 하지 않은 일을 구분한다.

- **공식 용량 조회 기능:** `Compute Capacity Report`(서버 여유 용량 보고서)가 있다. 하지만 우리 무료 계정의 권한·조회 가능 여부를 실제 실행으로 확인하지 않았다. 조회 결과도 자리를 예약하는 것은 아니다. [공식 명령 안내](https://docs.oracle.com/en-us/iaas/tools/oci-cli/latest/oci_cli_docs/cmdref/compute/compute-capacity-report/create.html)
- **저장한 설정으로 재시도:** 스택을 사용하면 서버 설정을 매번 다시 입력하지 않아도 된다. 실제 성공은 생성 결과로 확인해야 한다.
- **자동 재시도:** 프로그램으로 구현할 수 있다고 설명했을 뿐, 만들거나 실행하지 않았다. 실제 자원 생성 요청이므로 별도 실행 범위와 중복 생성 방지 조건이 필요하다.
- **자리 알림·예약:** 우리 계정에 자동 자리 알림이나 예약을 설정한 기록은 없다. 스택·Plan이 이 역할을 대신하지도 않는다.

“곧 자리가 난다”, “도쿄로 가면 된다”, “지정 시각에 누르면 된다”는 보장할 근거가 없었다. 계속 버튼을 누르는 것만으로 문제를 해결했다고 할 수 없다.

## 13. 다음에 이어서 할 일

### A. Oracle 생성만 다시 시도할 때

1. Oracle에서 **오사카** 지역 선택.
2. **Developer Services → Resource Manager → Stacks → `memoryjar-server`** 열기.
3. 이전 Apply 이후 생성된 자원이 있는지와 진행 중인 작업이 없는지 확인. 성공했거나 실행 중이면 중복 생성을 시도하지 않기.
4. 새 **Plan** 실행. 기존 설정의 서버 1대 추가만 있는지, 의도하지 않은 변경·삭제가 없는지 확인.
5. **Apply**에서 해당 Plan을 선택해 실제 생성 시도.
6. 용량 부족이면 스택을 보관하고 중단. 성공하면 서버 실행 상태·개인 키 짝·SSH 접속을 확인.

**Destroy(스택이 관리하는 자원을 삭제하는 작업)는 재시도 버튼이 아니다.** 무작정 누르지 않는다.

이 문서 작성 과정에서는 위 재시도를 실행하지 않았다. 자동 재시도나 정기 확인을 새로 설정하지도 않았다.

### B. Oracle 서버를 확보한 뒤 서비스 이전을 검토할 때

1. ARM용 실행 이미지와 AWS·Oracle 배포 대상 분리를 준비한다.
2. 운영 데이터와 분리한 시험용 DB·환경으로 시작한다.
3. AWS 외부 서버용 접근 권한, 파일·메일 등 필요한 연결과 비용을 확인한다.
4. 소량 로그인 → 10 VU → 종료 후 회복을 확인한다.
5. 안정성이 확인돼야 원래 목표인 **50 → 100 → 150 → 200 → 300 VU**를 단계별로 시험한다.
6. 데이터 복원·백업·보안·도메인·암호화 통신·문제 발생 시 되돌리는 방법까지 검증한 다음 실제 이전 여부를 결정한다.

서버 확보만으로 성능 개선이나 300 VU 통과를 선언하지 않는다. 기존 AWS를 먼저 종료하거나 도메인을 먼저 바꾸지 않는다.

### C. Oracle 확보를 기다리기 어려울 때

기존 AWS의 메모리를 늘리는 비용과 중단 시간을 별도로 비교해 결정할 수 있다. 다만 **유료 증설·Oracle 유료 전환·기존 서버 종료는 아직 승인받아 실행한 일이 아니다.** 기다리는 동안 서비스 개발 자체까지 멈출 필요는 없다.

## 15. 마지막으로 꼭 기억할 여섯 문장

1. **준비 실패와 동시 조회 실패는 다르다.** 이번 50명 조회는 시작하지 못했다.
2. **메모리 대기의 근거는 찾았지만, 모든 지연의 원인을 100% 증명한 것은 아니다.**
3. **스왑 설정 10은 해결책으로 채택하지 않았다.** 60으로 되돌렸다.
4. **Oracle 가입·네트워크 준비·설정 저장은 완료했지만, A1 서버 확보는 실패했다.**
5. **Plan 성공은 자리 확보가 아니다.** 마지막 Apply는 `Out of host capacity`로 실패했다.
6. **기존 AWS는 유지한다.** Oracle 이전·상위 부하 시험·유료 증설·자동 재시도는 각각 별도 확인과 결정이 필요하다.
